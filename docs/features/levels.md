# Levels

The shared level core (`shared/levels/`), its four environments, git (`shared/levels/git/`), Debugging (`shared/levels/debugging/`), the review environment of Working with AI (`shared/levels/review/`) and Web fundamentals' (`shared/levels/web/`, the Debugging sandbox with a prediction, an editable server.js and a modelled browser), and their levels. Pure TypeScript: no Vue, DOM or Nuxt imports. Tests: `test/unit/levels/` (Debugging's in `test/unit/levels/debugging/`, plus `e2e/debugging-levels.spec.ts` in a real browser; the review environment's in `test/unit/levels/review/`, plus `e2e/ai-review.spec.ts`).

## Environments (ADR 0007, update 2026-11-13)

The core is track-agnostic: levels, goals, hints, debrief, practice tasks, sessions and their counts, teammate events, undo and reset, progress, tracks and chapters, Continue and next up, the skill radar. It is generic over an **environment**: the state a level runs on (`S`), what the history records per counted action (`R`) and one solution step (`Step`). Git is one environment, in its own place: the git model in `shared/git/`, the git environment in `shared/levels/git/` (`types.ts`, `engine.ts`, `commands.ts`, `checks.ts`, the levels).

- **The core never imports an environment**: `types.ts`, `engine.ts`, `progress.ts`, `track.ts`, `radar.ts`. Only the registry (`tracks.ts`) and the barrel (`index.ts`) bring the tracks together. `test/unit/levels/core.test.ts` checks those imports and plays a level of a tiny counter environment (not git) through the core: goals, events, hints, undo, reset, its best run by its own measure, progress.
- **Generic types**: `ScenarioOf<S, R, Step, T>`, `PracticeTaskOf`, `LevelOf`, `SessionOf<S, R>`, `Goal<S, R>`, `GoalContext<S, R>`, `TeammateEvent<S>`, `TeammateTrigger<S>`, `SessionSnapshot<S, R>`.
- **Registering an environment**: an environment adds its types to the core's `Environments` interface by declaration merging (Debugging: `debugging: { state, record, step, fields }`, where `fields` are what its levels add to the shared ones, `sandbox` and `teaches`; git adds none, so its types did not change) (`declare module '../types'` with `interface Environments { git: { state, record, step } }` in `shared/levels/git/types.ts`). `Level`, `Scenario`, `PracticeTask` and `Session` are the union over the registered environments (today git's alone, so they are exactly git's); `Level<'git'>` is one environment's (`GitLevel`, `GitScenario`, `GitPracticeTask`, `GitSession`). A level's `track` is its environment's id, so `isGitLevel(level)` (and later Debugging's guard) tells them apart.
- **Core functions** (`shared/levels/engine.ts`): `startSession(level)`, `act(session, level, { commands, execute, reload?, falseAlarms? })` (one counted action: snapshot, before-events, execute, record, after-events, goals; `commands` are what `beforeCommand` triggers match, `reload` also counts a reload, `falseAlarms` adds a sent review's new false alarms to the session's count, which it sets even when it is 0), `undoLast(session, level)` (null when there is nothing to undo; returns the record it took back), `restart(session, level)` (a new attempt, hints kept, and a review track's false alarms), `takeHint(session, level)` (`{ session, number, total, text, revealed }`). They report data; the environment words it (git: `Undid: <line>`, `Hint 2/3: ...`).
- **The git environment** (`shared/levels/git/engine.ts`): `startLevel`, `submit` (trainer commands typed in the terminal, else a counted git/shell line), `saveFile`, `saveEditor`, `playStep`, `TRAINER_COMMANDS`; a line's commands for triggers come from the git tokenizer (`commandsIn`). `CommandRecord` (`{ line, exitCode }`), `SolutionStep` (a line or `{ save }`), `TerminalLine` and `SubmitResult` are git's types.
- **Best run per track**: `Track.bestRun` is a `RunMeasure`, the run counters in order; fewer wins, each later one breaks a tie. Git `fewestCommands` (`['commands', 'hints']`, the rule so far), Debugging `fewestHintsThenReloads` (`['hints', 'reloads']`), Working with AI `fewestHintsThenFalseAlarms` (`['hints', 'falseAlarms', 'rounds']`), Web fundamentals `fewestWrongPredictions` (`['wrongPredictions', 'hints', 'reloads']`). A track without one gets `fewestCommands`. `useProgress().record` passes the level's track's measure to `recordSolve`.
- **The play page** follows the same split (docs/features/ui.md, "Play page"): `usePlaySession` and `PlayFrame` are shared, `useGitPlay`, `GitPlay` and `GitWorkbench` are git's, `useDebuggingPlay` and `DebuggingPlay` Debugging's.
- **The core never imports Debugging either**: `core.test.ts` refuses `./git`, `./debugging` and `./review` in the core files.
- **The review environment** (ADR 0008, since 0.3.3) registers the track `ai`: `ai: { state: ReviewState, record: ReviewRecord, step: ReviewStep, fields: ReviewFields }` (see "The review environment" below). It reuses Debugging's shop files (`debugging/bakery.ts`) and its `BackendSpec` type, and nothing of its engine; Run the PR reuses the Debugging sandbox on the page's side.
- **Web fundamentals** (ADR 0009, since 0.4.1) registers the track `web` on Debugging's state and records: `web: { state: DebugState, record: DebugRecord, step: WebStep, fields: WebFields }` (`WebFields` = Debugging's plus `prediction`; `DebugState.predicted` and the record `{ kind: 'predict' }` are optional and never used by a Debugging level). So Debugging's engine (typed on `SandboxLevel`, the shape both share) and its play page run these levels as they are; see "The Web fundamentals environment" below.

## Public API (`shared/levels/index.ts`)

## Engine rules

The core's rules, as the git environment uses them (a Debugging level runs through the same core with its own actions; there a reload also counts in `reloads`).

- **Pure and immutable**: every call returns a new session; a session is plain JSON (the UI may store it as is).
- **Output** is `TerminalLine[]`: git's `OutputLine`s plus two markers the UI interprets, `{ kind: 'clear' }` and `{ kind: 'edit', path }` (open the editor panel).
- **Trainer commands** are handled before git and are not counted, recorded or undoable. Matched on the trimmed line, any case:
  - `undo`: restores the previous snapshot (git state, history, fired events). Prints `Undid: <line>`, or `Nothing to undo.`
  - `reset`: back to the setup as a new attempt (history, undo stack, events, `solved` and `commandCount` cleared). Revealed hints stay revealed and counted.
  - `hint`: reveals the next hint (`Hint n/3: ...`, `Hint 1/1: ...` for a practice task, kind `hint`) and counts it; after the last it repeats it.
  - `help`: lists trainer, git and shell commands.
  - `clear`: returns the clear marker. `edit <file>`: returns the edit marker (`usage: edit <file>` otherwise).
- **Empty line**: no-op.
- **Counted commands** (anything else, and `saveFile`), in this order:
  1. Snapshot for undo (oldest dropped beyond 200).
  2. `beforeCommand` events fire if any command in the line (split at `&&` and `;`, whitespace collapsed, redirect targets ignored) equals the prefix or starts with it plus a space. `git push` matches `git   push -u origin x` and `git add . && git push`, not `git pushy` or `echo "git push"`.
  3. The line runs (`run` from the git model).
  4. It is recorded in `history` as `{ line, exitCode }` and `commandCount` goes up.
  5. `afterCommands: N` events fire once the history (the current timeline) has N entries, `when` events once their check passes on the new state.
  6. Goals are recomputed; `solvedNow` is true on the first transition to all goals met. `solved` then stays true for the attempt and the session stays playable.
- **Events** fire once per timeline: `firedEvents` is part of the snapshot, so an undo that rewinds past an event lets it fire again. Each firing returns a `Notice` (`{ eventId, author, text }`).
- **Counts**: `history` is the current timeline (undo shortens it); `commandCount` is the effort of the attempt and includes undone commands. Progress uses `commandCount`.

## Tracks and chapters

`shared/levels/track.ts` (types and helpers) and `shared/levels/tracks.ts` (the registry). Play order, chapter numbers and scenario numbers are derived from the chapter lists, never written by hand.

- **Track**: `{ id, title, scope (one line), tagline (one line for its home card, may be empty), description (the home card's pitch), status: 'live' | 'coming', cheatSheet (its path, or null), bestRun (its run measure, see Environments), chapters }`. Everything the home page, the nav and the track page show about a track comes from here, so a new live track needs data only. `tracks` lists them in home page order: Git, Debugging, Working with AI (live since 0.3.3, complete since 0.4.0, with its cheat sheet) and Web fundamentals (live since 0.4.1: chapter 1 Same-origin & CORS, chapter 2 Cookies & sessions since 0.4.2, chapters 3 to 7 coming, no cheat sheet yet), then Framework deep dives (coming: no chapters, no levels, not playable; the tests pin coming tracks to no chapters). Debugging has seven chapters (ADR 0007), all live since 0.2.14, with a cheat sheet since 0.2.15 (`/debugging/cheat-sheet`): 1 Reading errors, 2 Network, 3 Elements & CSS, 4 State & async, 5 Breakpoints & stepping, 6 Performance, 7 Incidents. Colours: slot = chapter number - 1. `defineTrack` numbers the chapters and throws for a level of another track, a level listed twice, a coming track with levels, or a practice task that does not follow its scenario.
- **Chapter**: `{ id (unique in its track, also the section anchor: /git#merging), trackId, number, title, description (one line), colour (a slot of the branch palette, 0-7), levels }`. `levels` is the play order: each scenario followed by its practice tasks. A chapter without levels is *coming*: shown with its description only.
- **Git chapters**: 1 Basics (5 scenarios, 6 practice tasks), 2 Branching (5 scenarios, 6 practice tasks), 3 Merging (5 scenarios, 5 practice tasks), 4 Rewriting history (4 scenarios, 4 practice tasks), 5 Teamwork & remotes (5 scenarios, 5 practice tasks), 6 Undo & recovery (5 scenarios, 7 practice tasks), 7 Disasters (5 scenarios, 6 practice tasks), 8 Workflows (5 scenarios, 7 practice tasks). No git chapter is coming any more. Colours: slot = chapter number - 1; slot 7 exists only for chapters, so branch colours in the graph did not move.
- **Numbers**: a scenario is `chapter.position` counting scenarios only, e.g. `1.2` for Stage only what belongs together, `3.3` for Merge conflict (`levelNumber`, `LevelPlace.number`). A practice task has no number (`number: null`); `LevelPlace.scenario` names its scenario and that scenario's number. `placeName(place)` is the text form: "3.3 Merge conflict", or the title alone for a practice task. The ids and URLs (`git-04-merge-conflict`, `/git/04-merge-conflict`, `/git/practice-stage-one-file`) never change when a level moves or gets renumbered.
- **Counting both kinds**: "n of N solved" for a chapter and a track, **next up** and **Continue** count scenarios and practice tasks alike: a practice task is a level you solve like any other, so leaving one out would make the counts lie.
- **Next up**: the first unsolved entry in play order (`nextUp`), a scenario or a practice task. **Continue** (`continueTarget`, `{ place, reason, at }`): the entry you last played while it is unsolved (`reason: 'resume'`, with the time), else next up (`'next'`); once nothing in the track is unsolved, the first entry flagged "practise again" in play order (`'practise'`); null when everything is solved and nothing is flagged. `practiseAgainIn(chapter, progress)` is the chapter menu's "Practise again". `trackToContinue` picks the track for the home page: the live track of the last played entry, else the first live track with a solve.

## Two kinds: scenarios and practice tasks

ADR 0006 (`docs/adr/0006-git-v1-practice-and-progress.md`). `Level = Scenario | PracticeTask`, told apart by `kind`.

- **Scenario** (`kind: 'scenario'`): a story, goals, three hints, a debrief. Numbered.
- **Practice task** (`kind: 'practice'`, "Practice" in the UI, never "drill"): one short task of 1-3 commands, about 30 seconds, one goal (a few at most, ADR 0006), one hint, a one-line `why` shown once solved, "Next" and "Again" instead of a debrief. No number.
- **Where a practice task belongs**: it names its scenario in `practises` *and* is listed in the chapter right after that scenario (after the scenario's other practice tasks). The level file says what it trains; the chapter list stays the one place for the order; `defineTrack` checks that both agree, so a moved line fails at start-up instead of drawing a practice task under the wrong scenario. `nextLevel` therefore goes scenario, its practice tasks, next scenario.
- **Difficulty** (`1 | 2 | 3`, drawn as filled dots) and **minutes** (an estimate; a practice task about `0.5`, shown as "~30 s") on every entry.

## Writing levels

The rules are in ADR 0006, "Writing levels"; in short:

- Precise and clear: compact, but never leave out what the learner needs (a file name, a branch name, how many commits). If a goal checks it, the story or task says it.
- File contents and code comments read like a real project other people work on: the Corner Bakery website (the habit tracker only in Basics 1.1's practice tasks), comments that say why ("Agreed with the shop team: orders from 50 euros ship for free"), teammates by name.
- Friendly and personal: we are their friends who help and teach. Second person, no blame, the debrief explains *why*.
- Fictional people and teams only (Maya, Jonas, Ben; a bakery), never real companies; fake keys only (`test-key-not-real-0000`).

## Progress

`shared/levels/progress.ts`, tests in `test/unit/levels/progress.test.ts`.

```ts
Progress = { version: 3, levels: { [id]: LevelProgress } }
LevelProgress = {
  solved: boolean,            // stays true once solved; only a reset clears it
  best: Run | null,           // by the track's measure (git: fewest commands, ties broken by fewest hints)
  latest: Run | null,         // the most recent solve
  practiseAgain: boolean,     // "solved, but I don't own it yet"; only a solved entry can carry it; a new solve clears it
  lastPlayed: number | null,  // ms since epoch, when you last typed a command in it
  fewestHints: number | null  // the fewest hints any solve revealed (for the skill radar); only goes down; null unsolved
}
Run = { commands: number, hints: number, reloads?: number, falseAlarms?: number, rounds?: number, wrongPredictions?: number }  // reloads: Debugging and Web fundamentals, falseAlarms: Working with AI only, rounds: its steer levels only (chapter 7), wrongPredictions: Web fundamentals only; git runs have none
```

- `recordSolve(progress, id, session, measure = fewestCommands)` stores the run (`runOf(session)`: `commands` = counted actions of the attempt, `hints`, and `reloads` when the session counted any) as `latest` and, when it is better by the track's measure (`isBetterRun(run, than, measure)`), as `best`, and lowers `fewestHints` when the run used fewer hints; replaying never removes `solved` or the flag. `fewestHints` is kept apart from `best` because the best run is chosen by commands first: a short solve with every hint can become the best run after a longer clean one, and the radar must still count the clean one. An unsolved session changes nothing. `recordPlay` sets the entry's `lastPlayed` (the play page calls it for every line typed and every editor save); `lastPlayed(progress)` is the newest one, for Continue.
- `setPractiseAgain(progress, id, flag)`; `resetEntries(progress, ids)` drops entries completely (solved, runs, flag, last played): an entry, a chapter, a track or everything.
- `readProgress(text)` is strict: broken JSON (`json`), not an object with `levels` (`shape`) or an unknown version (`version`) is an error, so the backup upload can say why and change nothing. Inside valid data a malformed entry (no boolean `solved`) is dropped and a broken field falls back to its blank value (a broken run to null, a non-boolean flag to false, a flag on an unsolved entry to false); an unsolved entry is kept only while it has a `lastPlayed`. A `lastPlayed` more than a day ahead of now (`MAX_FUTURE_MS`; `readProgress(text, now)`) is made up and becomes null. `levels` is built without a prototype and `__proto__` is skipped; every lookup by id goes through `entryOf` (own entries only). Ids this version does not know are kept stored (forward compatibility) but never win Continue: `lastPlayed(progress, isKnown)` skips them and `continueTarget` / `trackToContinue` pass the ids of their track(s). `parseProgress(text)` wraps it for storage: anything unreadable is empty progress.
- **`fewestHints` in version 3** (added in 0.2.5, no version bump): data from before has no such field, so `readEntry` takes the fewest hints of the stored best and latest run; a stored value is kept but never above what the runs show; a broken value falls back to the runs; an unsolved entry has none. It needs no level data, so it is exact wherever progress is read (storage, backup upload). Why not version 4: the field is additive and derivable from version 3 data, so backup files stay readable both ways (0.2.4 reads a 0.2.5 file and ignores the field; a version 4 file would be refused there as an unknown version). What 0.2.4 data cannot tell: a clean solve that was neither the best nor the latest run; such an entry counts half until a clean replay.
- **`reloads` in version 3** (added in 0.2.7, no version bump): an optional count in a run, read when it is a count and left out otherwise. Git runs never have it, so their stored form did not change and a 0.2.6 file reads and writes back byte for byte (`core.test.ts`); 0.2.6 reading a newer file keeps each run's commands and hints and ignores the field. A missing `reloads` compares as 0.
- **`falseAlarms` in version 3** (added in 0.3.3, ADR 0008, no version bump): an optional count in a run, like `reloads`: read when it is a count, left out otherwise, a missing one compares as 0. A review track's session sets it with its first sent review (`act`'s `falseAlarms`), so every run of a Working with AI level has it. 0.3.2 data and backups load and write back byte for byte, and 0.3.2 reads a 0.3.3 file (still version 3; it keeps each run's commands, hints and reloads and ignores the new field); `core.test.ts` pins both ways.
- **`rounds` in version 3** (added in 0.3.9, ADR 0008 "chapter 7", no version bump): the same kind of optional count, set by a steer level's first request Sous answers (`act`'s `rounds`), kept across Reset like false alarms; the Working with AI measure breaks a tie of hints and false alarms with it, and a track row shows it only for a run that has it (`bestRunCounters(measure, run)`).
- **`wrongPredictions` in version 3** (added in 0.4.1, ADR 0009, no version bump): the same kind of optional count, set by a Web fundamentals level's first answer (`act`'s `wrongPredictions`: 1 for a wrong answer, 0 for a right one) and kept across Reset like false alarms (the answer was shown). It is the first counter of the track's measure (`fewestWrongPredictions`: wrong predictions, then hints, then reloads). 0.4.0 data and backups load and write back byte for byte, and 0.4.0 reads a 0.4.1 file (still version 3; it keeps each run's other counts and drops this one) (`test/unit/levels/web/engine.test.ts`).
- **Migration on read**: version 1 and 2 entries `{ solved, hintsUsed, commands, bestCommands }` become `latest: { commands, hints: hintsUsed }` and `best: { commands: bestCommands, hints: hintsUsed }` (the hints of the old best run were never stored, so it takes the latest run's hints); `fewestHints` is the old `hintsUsed`; unsolved old entries are dropped; version 2's `lastPlayed: { levelId, at }` moves onto that entry (creating an unsolved one if needed).
- Storage is the UI's adapter (`grindstone:progress` in localStorage); the backup file is the same JSON (`serializeProgress`).

## Skill radar

`shared/levels/radar.ts`, tests in `test/unit/levels/radar.test.ts`; ADR 0007. One radar per track, an axis per chapter in chapter order: `trackRadar(track, progress)` returns `RadarAxis { chapter, value, total, solved, share, coming }`.

- **Credit per level** (`levelCredit`), scenarios and practice tasks alike: 1 once a solve did without the level's last hint (`fewestHints < level.hints.length`: fewer than 3 for a scenario, 0 for a practice task), 0.5 while every solve revealed it (also a solved entry without `fewestHints`, which only broken data has), 0 unsolved. Playing without solving counts nothing. **A track with predictions** (Web fundamentals, ADR 0009): its best run is chosen by wrong predictions first, then hints, so it is the cleanest solve there was; the level counts 1 once that run had no wrong prediction and did without the last hint, else 0.5 (a better run never has more wrong predictions, nor more hints at the same count, so this too only goes up). Why: a prediction-only practice task is solved by any answer, so without it a wrong guess would fill the radar like knowing.
- **Axis value** = the sum of its levels' credits; `share` = value / the chapter's level count. Replays can raise it, nothing lowers it (`fewestHints` only goes down). A reset drops the entries and their credit with them.
- **Coming chapter** (no levels): `coming: true`, value, total and share 0; drawn dashed.
- `isRadarEmpty(axes)`: nothing solved in the track (the picture shows its outline only). `radarGain(before, after, chapterId)`: the chapter's old and new value, null when it did not change (the debrief's line). `formatCredit(value)`: `4.5`, `5` (never `5.0`).
- **The overview radar** (ADR 0008, home page): `overviewRadar(tracks, progress)`, one axis per **live** track in registry order, each a chapter-shaped group of all the track's levels (`id` and `title` the track's, `colour` the slot of its place among the live tracks: Git 0, Debugging 1, Working with AI 2, Web fundamentals 3), with the same credit per level. Coming tracks are left out (they have nothing to practise, and their axes would only dent the shape); four live tracks since 0.4.1.
- How it is drawn: `docs/features/ui.md`, "Skill radar".

## The Debugging environment

ADR 0007; `shared/levels/debugging/`. A level is a small real app (index.html, one stylesheet, plain JavaScript ES modules) set in Corner Bakery's ordering site, run by the browser in a sealed iframe (how: docs/features/ui.md, "Sandbox and bridge"). The environment itself stays pure: the browser runs the app, and what it saw comes back as data, over a port only the bridge holds (since 0.3.1; the app's own code can't post a result, `done`, or anything else the page reads, and the probes read the page with the browser's functions taken before the app ran: docs/features/ui.md, "Sandbox and bridge").

- **State** (`DebugState`): `files` (the app's files as saved, by path; a reload runs these), `observed` (what the check run of the last reload saw, an `Observation`; null before the first reload), `picked` (find tasks: the line you clicked last, or in chapter 7 the deploy you named, `{ deploy }`), `checked` (the files the last reload ran; absent before it; colleague events read it).
- **Counted actions** (`DebugRecord`): `saveDebugFile` (the editor's Save; only files the app has), `reload(session, level, observation)` (counted, and also in `reloads`), `pickLine` (find tasks: a click on a line in the editor or a frame in a trace; returns a `PickVerdict`, right or why not), and in chapter 7 `rollback(session, level, deployId)` (a deploy's files become the saved files; nothing for an unknown deploy) and `pickDeploy` (a find task whose answer may be a deploy; `deployVerdict`). The run's measure is the track's: fewest hints, then fewest reloads. Saves, rollbacks and clicks count as actions but not as reloads.
- **Goals read only what the app did** (`checks.ts`), never the code's text, so any working fix counts: `probeGoal(id, label, probe, expected)` (a probe read exactly this after the last reload, in a check run that finished: one that hung proves nothing), `probesGoal(id, label, { probe: expected, … }, { clean? })` (several probes in one goal, so a guard such as "the message still shows" never passes on its own at the start; an expected value is exact, or a bound on a number, `{ atMost: 1 }` / `{ atLeast: 5 }` (`meets`; chapter 6: "at most 1 request"); `clean`: and no error in the check run either, so a fix that leaves an uncaught `AbortError` behind does not count, 4.2), `probeAtLeast(id, label, probe, min)` (a number, e.g. a contrast ratio), `noErrorsGoal()` (the check run finished, through loading and every probe, with no uncaught error, unhandled rejection or `console.error`), `foundGoal(label, target)` (find tasks). Goals change only on a reload (or a click): a Save keeps what the last reload saw.
- **Probes** (`SandboxSpec.probes`): scripted looks at the app that run in the check run once it has loaded, in order, on the same page: `{ click: selector, times?, settle? }` (like a customer; `times: 2` clicks twice back to back, a double click; then the app gets 20 ms to react, and with a backend until every request it sent is answered, at most 3 s; `settle: false` goes on after the 20 ms while the answers are on their way, a customer who clicks on), `{ type: selector, value }` (typing: the field's value becomes `value`, then an `input` and a `change` event, then 20 ms; answers are not waited for), `{ wait: ms }` (a customer's pause, at most `MAX_PROBE_WAIT_MS`, 2 s; nothing is waited for), `{ settle: true }` (until every request is answered, at most 3 s, then 20 ms: what the customer sees once the page is quiet; chapter 4's races are `type`, `wait`, `type`, `wait`, `settle`, then a read), `{ text: selector }` (whitespace collapsed), `{ count: selector }`, and with a backend `{ requests: 'POST /api/orders' }` (how many requests went there: a path on the shop, or a whole URL; the query does not count) and `{ sent: 'POST /api/orders', json?: 'items.0.quantity' }` (the last body sent there, or the JSON value at that path; null when there is none; a number stays a number, so `3` and `"3"` differ). **Layout probes** (chapter 3), from the browser's own layout: `{ tap: selector }` (a tap where a finger would: at the element's centre, scrolled into view vertically, on whatever is on top there, so a covering element gets it), `{ style: selector, property }` (a computed value: `'none'`, `'rgb(122, 62, 18)'`), `{ visible: selector }` (`'visible'`, or why not: `'display: none'` (also `'display: none on section.basket'`), `'in a closed details'` (since 0.4.6: browsers keep its boxes), `'visibility: hidden'`, `'opacity: 0'`, `'no size'`, `'off screen'`: its centre is outside the page's width or above it), `{ hit: selector }` (what a tap at its centre lands on: `'itself'` (it or something inside it), else the element on top, `'div.toast-area'`; `'no box'`, `'off screen'`, `'nothing'`), `{ overflows: selector }` (`'overflows'` when it is wider inside than its box, else `'fits'`; `html`: the page scrolls sideways), `{ contrast: selector }` (its text colour against the backgrounds behind it over a white page, WCAG's ratio, two decimals; colours the browser computes as `rgb()`/`rgba()`, background images ignored). **Typing like a customer** (chapter 6): `{ keys: selector, value, gap? }` (letter by letter: per letter a `keydown`, the letter added with an `input` event unless the keydown was prevented, a `keyup`, then `gap` ms, 80 by default; no `change`, never the focus) and `{ press: selector, key }` (a `keydown` and a `keyup`; Enter in an `<input>` also commits it with a `change`, as in the browser; no form is submitted, the sealed frame has none). **Performance probes** (chapter 6, levels with `sandbox.performance`; see "The profile" below): `{ changes: selector }` (how many nodes of the page the app changed inside the first element that matches since this probe started: elements and non-blank texts added or removed, one per attribute or text set; from a MutationObserver), `{ work: 'load' | 'here' }` (units of work, the statements the app's code ran: until the loaded page was quiet, or since this probe started; the check run counts only when a probe reads it), `{ waited: 'load' | 'here' }` (server time on the server's clock, in ms: until the loaded page was quiet, or since this probe started). **Widths**: a check run's frame is a phone, 390 × 700 (`CHECK_VIEWPORT`); a probe with `width` (3.4: 1024, a laptop) runs in a frame of that width after it (`checkFrames`: one frame per width, the phone's first), and `mergeObservations` puts them together (finished when all did, each error once, every probe, the first frame's logs). A probe's value is its last read; one that finds nothing has no value (`probeErrors`). "No errors in the Console after a reload" therefore includes the errors the goals' own clicks cause (1.1: Add throws), so it fails on the starting files.
- **The observation** (`Observation`): `finished`, `errors` (`{ kind, text, source }`; `kind` is `error`, `rejection`, `console` or `network`, the browser's own line for a failed request, which the Console shows red too), `probes`, `probeErrors`, `logs`. Built by `observe(messages)` from the messages that came over the check run's own port (`bridgeLink`): the bridge's alone.
- **Solutions** (`DebugStep`): `{ save: path, replace: [from, to] }` (the file with the first occurrence replaced; `editedText` throws when the text is not there), `'reload'` (the check run on the saved files), `{ pick: path, line }`, and in chapter 7 `{ rollback: deployId }` and `{ pickDeploy: deployId }`. `playSolution(level, run)` replays them; `run` is the check (a real browser in `e2e/debugging-levels.spec.ts`, the table of `test/unit/levels/debugging/expected.ts` in the unit tests).
- **Level fields** (`DebugFields`): `sandbox: { page, open, probes, find?, backend?, elements?, debugger?, performance? }` (the address bar's path, the file the editor opens first, the probes; a find task's `FindTarget`: `path`, `lines` (any counts, the first is the solution's), `wrong` (why a click on a known wrong line is not it, by `'path:line'`), `otherwise`; the fake backend, see below; `elements: true` for the Elements panel, see below; `debugger: true` for the Debugger and its recording, see below; `performance: true` for the Performance panel and its profile, see below; `logs` and `deploys` for the Logs and Deploys panels, see below; a find target's `deploys`, the deploys that count as its answer, with `deploy:<id>` keys in `wrong`), a scenario's `teaches` (the error, status, CSS feature, stepping lesson, what made it slow or what the incident teaches, its tag on the track page: `TypeError`, `404`, `CORS`, `z-index`, `@media`, `call stack`, `debounce`, `bisect`) and, in chapter 7, its `report` (the colleague's message it opens with).
- **Two kinds of practice task**: **find** (`sandbox.find`, no probes, the editor is read-only, the solution is one click on a line: in the editor, a Console link or a request's Sent from link; the goal ticks on the right line) and **quick fix** (one line to change, probes and goals like a scenario, solution: the edit and one reload).
- **Colleague events** (chapter 7 only; see "Colleague events" below): the core's teammate events, with its generic triggers.

### The fake backend

ADR 0007, update 2026-11-13 (chapter 2); `shared/levels/debugging/backend.ts`, tests in `test/unit/levels/debugging/backend.test.ts`. A level declares its server in `sandbox.backend`; the bridge answers the app's `fetch` with it inside the sealed frame, for the app you see and for every check run, each load with a fresh one (a sequence starts over). Nothing leaves the frame: its Content-Security-Policy still refuses every request (`connect-src 'none'`), and anything that is not `fetch` (an image, `XMLHttpRequest`) is refused as before.

- **Routes** (`BackendRoute`): `{ method? (GET), path, query?, body?, respond }`. `path` is `/api/menu` on the shop's own address (`https://cornerbakery.shop`) or a whole URL on another origin; routing ignores the query unless the route has a `query` pattern (below). `body` is a regular expression's source: only requests whose body matches take the route (2.3's server reads `"quantity":3` differently from `"quantity":"3"` and from a missing field), else the next route for the address does. `query` is one too, tested on the query as sent without `?` (`q=cro`): 4.2's search answers `^q=cro$` slowly and `^q=croi` fast, so the answer and its delay depend on the request and a race is the same on every run. `respond` is one answer or a list answered call by call, whose last answer repeats (2.2: a `500`, then a `201`).
- **Answers** (`BackendAnswer`): `{ status, json? | text?, headers?, delay? }` or `{ fail: 'network', delay? }`. The status must be one in `STATUS_TEXT` (its reason phrase becomes `statusText`), `json` sets `content-type: application/json; charset=utf-8` (`text`: `text/plain`), the level's headers win; `delay` defaults to 30 ms (`DEFAULT_DELAY_MS`), at most 3 s. `backendConfig` checks all this (the level tests run it on every level) and hands the frame plain data.
- **What the app gets**: a real `Response` (`ok`, `status`, `statusText`, `headers`, `json()`, `text()`, `url`, `type` `basic` or `cors`) after the delay; `fetch` rejects only as the browser would: `TypeError: Failed to fetch` (made where `fetch` was called, so its trace points at the app's line) for a failed connection or a CORS refusal, `fetch`'s own `TypeError` for a request it refuses (a body on a GET, an address it can't parse), the signal's `AbortError` when aborted. An unknown path on the shop answers `404` with the server's HTML error page (Express's "Cannot GET /api/products"), so `response.json()` fails the way it does for real ("Unexpected token '<'"); an unknown host fails to connect (`net::ERR_NAME_NOT_RESOLVED`).
- **CORS, like the browser**: a request to another origin is refused unless its answer has `Access-Control-Allow-Origin` with `*` or the shop's origin. A request that needs a preflight (a method other than GET, HEAD, POST, or a header that is not safelisted, e.g. `Content-Type: application/json`) also needs `Access-Control-Allow-Methods` / `-Headers` (the route's answer stands in for the preflight's). `mode: 'no-cors'` gets an opaque answer (status 0, empty body). The Console gets Chrome's lines: "Access to fetch at '…' from origin 'https://cornerbakery.shop' has been blocked by CORS policy: …" (the reason, as Chrome words it), then `GET … net::ERR_FAILED 200 (OK)` (without the status after a refused preflight).
- **The browser's own lines** (`netlog` messages): a 4xx or 5xx answer logs `GET https://cornerbakery.shop/api/products 404 (Not Found)`, a failed connection `GET … net::ERR_CONNECTION_REFUSED`; each links the line that sent the request. They count as errors for "No errors in the Console", which is why a level whose server keeps failing on purpose (2.2) has no such goal.
- **For the Network panel** the backend posts each request when it is sent (`request`: method, URL, headers as the browser sets them, the body as text, the call stack) and its answer when it arrives (`response`: status, headers, body, `failure` `cors` / `network` / `aborted`, the time); a CORS refusal shows the status the server sent but no body. A body that is not text shows as `(binary, n bytes)`, form data as `name=value&…`, an object as `[object Object]` (what the browser sends).
- **For probes** it counts requests by address (`count`) and keeps the last body sent there (`sent`). That record lives in an object without a prototype and is written and read only with built-ins the backend took when it was made (before the app's code ran; the URL's own getters, string methods, `JSON.parse`, and a JSON writer of its own that asks nothing for a `toJSON`), so a built-in the app replaced can't change what those probes read. The routes come as data without prototypes too (the bridge's copy of its config): an `Access-Control-Allow-Origin` the app puts on `Object.prototype` is no header of the server's.

### The Elements panel

ADR 0007, update 2026-11-13 (chapter 3); `shared/levels/debugging/css.ts`, `elements.ts` and `inspector.ts`, tests in `test/unit/levels/debugging/css.test.ts`, `elements.test.ts`, `messages.test.ts` and `e2e/debugging-elements.spec.ts`. A level with `sandbox.elements` gets the panel (how it looks: docs/features/ui.md, "Elements"). The work is split so the cascade is pure and tested: **the browser says what matches, Grindstone works out the rest from the level's own CSS**.

- **The page's rules** (`css.ts`): `styleSheets(files)` lists the stylesheets in document order as the browser applies them (each `<link rel="stylesheet">` to a level file except a `disabled` one, each `<style>` block of index.html from the line it starts on; nothing inside `<!-- -->`; a `media` attribute becomes a condition of every rule of that sheet, linked to its line in index.html), `parseCss` reads each into `CssRule { path, line, selector, selectors, conditions, declarations }` (the line of the selector and of every declaration, the `@media` / `@supports` conditions around it with their lines), `cssRules(files)` all of them in cascade order (at most `MAX_CSS_RULES`, 2000). Forgiving like the browser: comments, strings, `!important`, custom properties with blocks; other at-rules (`@keyframes`, `@font-face`, `@layer`, `@container`) and nested rules are skipped; broken text never throws. It runs on the page's main thread twice per load, so it is linear in the text (no per-character trims or backtracking regexes), reads at most `MAX_CSS_LENGTH` (300,000 characters) of a sheet and follows `@media` / `@supports` and `:is(…)`-like selectors `MAX_CSS_NESTING` (32) deep; `css.test.ts` times hostile inputs (100 KB of whitespace, 200 KB without a `{`, 40,000 spaces before `!important`, 5000 nested `@media` and `:is(`, thousands of unclosed tags). `specificity(selector)` (ids, classes, types; `:is`/`:not`/`:has` take their most specific argument, `:where` counts nothing, `:nth-child(… of S)` adds S, legacy `:before`), `longhandsOf` (what a shorthand sets: `margin`, `background`, `border`, `font`, `flex`, `overflow`, `inset` …), `isInherited` (`color`, `font*`, `visibility`, `pointer-events`, `white-space`, custom properties …).
- **What the bridge gets** (`sandboxDocument(files, { elements: true })`, the app you see only, never a check run): the rules' selectors, conditions and declarations, the linked stylesheets' names (their `href` is a data URL in the frame) and the computed properties to read (`COMPUTED_PROPERTIES`: display, visibility, opacity, position, z-index, pointer-events, color, background-color, width, height, min-width, overflow, text-overflow, white-space).
- **The inspector in the frame** (`INSPECTOR_SOURCE`, part of the bridge, plain JavaScript in a string): a **snapshot** of the DOM (`dom`: elements in document order with their parent, tag, at most 12 attributes cut at 120 characters, their own text cut at 80, `shown` (it has a box) and `overflows` (wider inside than its box); at most `MAX_DOM_NODES`, 600; what Grindstone put on the page is left out, a stylesheet's data URL shows as its file, a module script as its `src`) after each load and on request (Refresh, a pick); **inspect** (`inspected`: for the element and each ancestor up to `<html>`, which rules match through which selectors (`matchMedia` / `CSS.supports` for their conditions, `element.matches` per selector), its style attribute; the declarations `CSS.supports` refuses; the box (content size, padding, border, margin); the computed values; scroll and client sizes); **highlight** (DevTools' four boxes and a label, in a closed shadow root on top of everything, `pointer-events: none`, following scrolls); **pick mode** (`hovered` while the pointer moves, `picked` after a fresh snapshot on the click, `pickEnd` on Escape; the click and the presses around it never reach the app).
- **The cascade** (`elementStyles(rules, inspected)`): the style attribute first (`element.style`), then the matching rules from the most specific and latest; each declaration `active`, `overridden` (it wins for nothing it sets: by !important, the style attribute, specificity, order, a later declaration in the same rule; a shorthand only when everything it sets lost) or `invalid` (the browser refuses it); `missing` lists the `var(--x)` without a fallback that nothing on the element or above it defines. **Inherited**: each ancestor with inherited declarations (only those), nearest first; struck through when something nearer sets it.
- **The tree** (`treeRows(nodes, expanded)`, `startExpanded` (`<html>`, `<body>` and what is in it open, the head closed), `treeMove` (WAI-ARIA tree keys), `withAncestors`, and `nodePath` / `nodeAtPath` to find the selected element again in the next snapshot, also after a reload), `nodeLabel` (`button#order.order`), `boxNumber` (a dash for 0).
- **Messages** (`readBridgeMessage`): `dom`, `inspected`, `hovered`, `picked`, `pickEnd`, each plain data with caps (a snapshot over 600 elements is cut and marked `truncated`; tags, attribute names and numbers checked; a malformed one is dropped whole). The page asks with `dom`, `inspect` (with a `seq`), `highlight` and `pick`, which the bridge takes only over the page's port (like Console input).

### The recording

ADR 0007, update 2026-11-13 (chapter 5); `shared/levels/debugging/instrument.ts`, `recorder.ts`, `recording.ts` and `condition.ts`, tests in `test/unit/levels/debugging/instrument.test.ts`, `recording.test.ts`, `condition.test.ts`, and in a browser `e2e/debugging-breakpoints.spec.ts`, `e2e/debugging-instrumented.spec.ts` and `e2e/debugging-levels.spec.ts`. A level with `sandbox.debugger` gets the Debugger (how it looks: docs/features/ui.md, "Debugger"). Nothing is paused: Record reloads the app you see with its code **instrumented**, the run is recorded step by step, and the panel moves through what already happened. The check runs (the goals) never run instrumented code, and no other level ever does.

- **Instrumentation** (`instrumentFiles(files)`, loaded lazily with acorn, its own chunk): every JavaScript file is parsed with acorn (ES latest, modules) and only has text inserted, never a line break, so every line, stack trace, Console link and find answer stays where it was. Before each statement a step call (`__gs$.on&&__gs$.s(point, call, [()=>a, ()=>b, …])`: the point's number, the running call's token and a reader per variable it can see); a loop's test gets one every round; a braceless body gets braces; a function body a `try`/`finally` that tells the recorder the call started and ended; `await x` and `yield x` become `__gs$.r(call, await __gs$.w(call, x))` (the call is paused, then back); an arrow's expression body becomes a block that returns it; a module's top level is a call of its own ("(anonymous)", like Chrome), its first call after a hashbang (at the start of line 2). A `for` statement whose test starts on its line is marked `testFollows` (a breakpoint stops at the test, see Stepping). What each point can see is worked out from the syntax tree: block scopes (let, const, class, a loop's variables, catch), the function's own (parameters, `var`, function declarations, `this` but not in an arrow), each enclosing function's (Closure) and the module's (imports and top-level names), innermost first, a shadowed name only once, at most `MAX_SCOPE_NAMES` (64). The **points** (file, line, column, function, scopes) and **functions** (name as JavaScript infers it: a declaration, `const f = () =>`, a method, `get total`) stay on the page; the frame only posts numbers and values. A file is left as written (and runs without steps, the Debugger says why) when acorn can't read it (a syntax error, which then fails in the browser as before), it is over `MAX_INSTRUMENT_SOURCE` (100,000 characters), nests over 400 levels (acorn's own "Not enough stack space" too), uses the name `__gs$`, the app passes `MAX_POINTS` (5000) statements, or a body the `try` would break (`clash`: in a block a function's own function declarations are lexical, so a `var` of the same name anywhere in that body, or a function declared twice in it, would become a SyntaxError). Linear; never throws. `withoutInstrumentation(text)` gives code back as written (exact for whole files: the tests round-trip every level's files; its lexer tells a regex literal from division by what comes before the `/`, so `/[)]/` or `/}/` stay as they are; linear on hostile text): Firefox and Safari quote code in some error messages (`(In 'slots.map(…)')`), and the Console shows those through it during a recording.
- **The recorder** (`RECORDER_SOURCE`, part of the bridge, run only in a recorded load as the global `__gs$`, set up before any module runs): a call stack from the calls it is told about (a call starts, ends, waits, is back; after the code that runs now has finished, a microtask clears it, which also catches a module's top level and a call that threw past an `await`), a call back from an `await` keeps the frames that started it as **async** frames. At each step it reads each variable (a reader that throws is a variable in its temporal dead zone: `<uninitialized>`) and keeps it as plain data (`RecordedValue`): strings cut at 200 characters (with their full length), objects `maxDepth` (3) levels below the variable and `maxEntries` (40) properties or `maxItems` (50) items wide, with an id per object and a cycle as a reference; a getter is never called (`(...)`), functions (`ƒ applyDiscount(total)`), elements (`button.add`), errors, dates, regexps and promises are one line; at most `maxNodes` (400) values opened per step. Only built-ins captured before the app ran are used. A Proxy can't be told from its target, so its traps run while it is read (`getPrototypeOf` for each `instanceof`, `ownKeys`, `getOwnPropertyDescriptor` per property; a trap that throws ends that value's entries): a known limit (ADR 0007). It posts the steps in batches (`steps`, 100 at a time or after 50 ms, never a message per step) and stops on its own (`recordEnd`) after `maxSteps` (2000: "the most it keeps") or once reading values has taken `maxMs` (3 s in all: "too slow"), or on the page's Stop (`recordStop`, over the page's port only); the app runs on (the inserted calls are a property check once it stopped).
- **Reading steps** (`readSteps`, in `readBridgeMessage`): a `steps` message is kept only when every step is well formed (`[point, call, frames, asyncAt, values]`, whole numbers, the value shapes above, at most 500 steps a message, 40 frames, 80 values, 6 levels and 1200 values a step, texts cut at 500); else it is dropped whole. The page keeps steps only while it is recording (or waiting for the last ones after Stop, at most 600 ms), only those whose point, functions and number of values fit the instrumentation (`fittingSteps`), at most `maxSteps`.
- **Stepping** (pure, `recording.ts`): `stepInto` (the next step), `stepOver` (the next step of the same call, past the calls its line makes, and after an `await` where the function goes on; when the call has no more steps, the first step after it ended), `stepOut` (the first step whose stack no longer has the call), `stepBack`; `nextHit` / `previousHit` (Resume to the next or previous step a breakpoint stops at, its condition holding; none: the end or the start, and the panel says so), `hitCounts`, `atBreakpoint` (a step on the line that is not a second statement of that line right after the first in the same call, so a loop's line stops once per round; a `testFollows` step never stops and stands aside for its test, so a `for` line stops at the test every round, round 0 with `i` in the Scope), `frameStep` (a caller's values: its own last step up to now), `scopeAt` / `scopeValues`, `recordedLines`. Previews like the browser's Scope: `valuePreview` (`"Rye loaf"`, `24.999999999999996`, `(3) [{…}, {…}, {…}]`, `{name: 'Rye loaf', grams: 0.75}`, `Map(1) {'croissant' => 2.4}`), `valueChildren` (an array also its `length`), `isExpandable`, `valueTone`.
- **Conditions** (`compileCondition(text)`, `condition.ts`, lazily loaded with the instrumentation): read with acorn as one expression (at most 300 characters) and evaluated by Grindstone on a step's recorded values: names (innermost scope first), `this`, literals, template literals, arrays of values, member access (also optional), `!`, `typeof`, arithmetic, comparisons, `&&`, `||`, `??`, `? :`, and calls of a few pure built-ins (`isNaN`, `Number`, `String`, `Boolean`, `parseInt`, `parseFloat`, `Number.isNaN`, `Number.isInteger`, `Math.round` and its kin, `Array.isArray`, a string's `startsWith`, `includes`, `toLowerCase`, …, a number's `toFixed`, an array's `includes`, `indexOf`, `at`). Refused when read: assignments ("A condition can't change values: use === to compare"), other calls, `new`, functions, `delete`, regexp literals, `constructor` and `__proto__`. At a step where it reads what the recording did not keep (an object too deep, a cut string, a getter, a name the step can't see: "unknown is not defined at this step", Chrome's "Cannot read properties of undefined (reading 'name')") it does not hold. `===` on objects is identity (their ids); other operators on objects are refused (they would run the app's `valueOf`). Never throws.

### The profile

ADR 0007, update 2026-11-13 (chapter 6); `shared/levels/debugging/recorder.ts` (counting), `profile.ts` and the bridge's page watch and server clock (`bridge.ts`, `backend.ts`), tests in `test/unit/levels/debugging/counting.test.ts`, `profile.test.ts`, `backend.test.ts`, and in a browser `e2e/debugging-performance.spec.ts` and `e2e/debugging-levels.spec.ts`. A level with `sandbox.performance` gets the Performance panel (how it looks: docs/features/ui.md, "Performance"). The numbers are **counted, never timed**, so the same run gives the same numbers in Chromium, Firefox and WebKit and on CI.

- **Work** (the cost model): one unit is one statement of the app's code that ran, from chapter 5's instrumentation (same `instrumentFiles`, same inserted text) with the recorder **counting** instead of reading values (`countingLimits('check' | 'profile')`, `profile: 1 | 2` in its limits): a unit goes to the function running it (**self**) and once to every function on the call stack (**total**; a recursive one too; the 256 innermost calls only, so a call below a deeper recursion misses those units in its total); **calls** are counted when a function starts. A built-in (`sort`, `find`'s own loop, `toFixed`) counts as part of the statement that calls it, and a callback it calls counts as its own function under the caller. Counting stops at `PROFILE_LIMITS.maxWork` (1,000,000 units; the app runs on).
- **Renders**: what the app changed on the page, from a MutationObserver the bridge starts once the page is parsed (`readyState` `interactive`, before any module runs). A change counts **nodes**: the elements and non-blank texts a `childList` record adds or removes, or one for an attribute or a text set. The counting recorder looks at the observer's records (`takeRecords`) before each statement and when a call ends, waits or comes back, so a change belongs to the statement that ran since the last look (a call's current statement; a callback a built-in calls makes its own); a **render** is a call of a function whose own statements changed the page, counted once per call. What changes the page outside the app's code (the browser, a check run) belongs to nothing.
- **The server's clock**: time moves only when an answer arrives, to the moment its request went out plus its scripted delay (`hooks.sent`, `hooks.arrived`, `hooks.aborted` of the fake backend). A request sent when the clock says 400 starts at 400, whatever real time it is; requests sent together start together, so `Promise.all` shows side by side and awaits in turn show as stairs. In a Performance level a check run's "quiet" also needs 50 ms without a request sent or answered, so the moment between an answer and the next request of a waterfall is not taken for the end.
- **Actions** (a recorded profile only): the page's load, then each click, typing (`input`), `change`, Enter (`keydown`) or form the bridge sees in the frame (capturing listeners set before the app's); the events of one press in one task (a checkbox's click, input and change) are one action. An action counts everything that ran from it until the next one (answers arriving meanwhile included), with when it started on the server's clock, its label (a button's text, a field's value cut at 40, `checked`, `Enter`) and the requests sent during it. At most `maxActions` (100); later ones count into the last (`more`).
- **What the frame posts** (`count: 'profile'`, Record): a `profileTick` (work so far) at most every 250 ms while recording, and the **profile** once, at Stop or at the cap: `{ reason, work, actions: [{ kind, target, label, at, work, more, fns: [[fn, calls, self, total]], dom: [[point, updates, nodes]], renders: [[fn, renders, nodes]], requests }], requests: [[id, start, end]] }`, at most 500 rows a table (the first ones), 200 requests. A check run (`count: 'check'`) posts nothing: its `work` probes read the count.
- **Reading it** (`readProfile`, in `readBridgeMessage`): whole numbers up to 10⁹, the action kinds above, texts cut (target 120, label 60), the caps above; anything else drops the profile whole; never throws. `fittingProfile` keeps only rows whose function or point the instrumentation has.
- **The panel's tables** (pure): `functionRows(profile, map, action)` (one action or all of them, null: the most total first, then self, then file and line; a file's top level is `module`), `renderRows` (the most nodes first, each function with its lines that changed the page), `requestRows(profile, entries, action)` (in order sent, times from the view's start; `after`: in the same action, sent the moment that request's answer arrived, a waterfall; `repeats`: an earlier request of the recording with the same method, address and body), `timelineEnd`, `profileSummary` (work, renders, nodes, requests, server time until the last answer), `profileLines` (every line the panel links: functions, changed lines, Sent from; find tasks are answered there).
- **Counted check runs**: a level whose probes read the work (`needsCounting`) runs its check instrumented to count (the play page loads the chapter 5 tools for it); any other probe reads what it reads as written, and the levels e2e checks that every chapter 6 app does the same counted as written (values, errors, requests). A file that runs as written (instrument.ts skipped it: a syntax error, a clash, the recorder's name …) leaves every `work` probe without a value and says why (`withUncounted`), so leaving code out of the count never passes a goal. A counting check run's policy has no `'unsafe-eval'` (`COUNTING_CSP`): `eval`, `new Function` and string timers would run code nothing counts, so there they fail (the Console of the app you see keeps eval). Still not counted (known limits): a module the app makes at runtime from a blob, and a `<script>` written into index.html or added by the app (inline scripts must run: the bridge is one). The recorder can't be switched off by the app's code (`on` is a getter, the api frozen); a counting check run stopped any other way reads no number. A profile whose request ids repeat, or that has more than the recorder keeps, is dropped whole.

### The logs

ADR 0007, update 2026-11-13 (chapter 7); `shared/levels/debugging/logs.ts`, the backend's request ids and reports (`backend.ts`), tests in `test/unit/levels/debugging/logs.test.ts`, `backend.test.ts`, `messages.test.ts`, and in a browser `e2e/debugging-incidents.spec.ts` and `e2e/debugging-levels.spec.ts`. A level with `sandbox.logs` (it needs a backend) gets the Logs panel (how it looks: docs/features/ui.md, "Logs").

- **The level's logs** (`LogsSpec`): `now` (the server's clock when the app loads, `'09:41:00.000'`), `firstRequest` (the id of a load's first request: 4127 makes `req-4127`, each request after it counts up), `history` (what the server logged before you came, oldest first, at most `MAX_LOG_HISTORY` (200) lines of `{ at, level, route, request, message, stack? }`; `incident-shop.ts` has short ways to write them: `accessRow`, `deployRow`, `pastLines`). An answer of the backend may script what the server logs while it answers (`BackendReply.log`: `{ level, message, stack? }`, `{body}` in a message is the request's body cut at 300 characters, `{query}` its query). `checkLogs` checks all of it (times as `HH:MM:SS.mmm`, oldest first and not after `now`, request ids before the first of a load, routes as `METHOD /path`, levels, messages up to 2000 characters, stacks up to 12 lines); the level tests run it on every level.
- **Request ids and the server's reports**: in a level with logs every answer of the shop's own server carries `x-request-id: req-<n>` (another origin's server is not the shop's, and a failed connection reached no server), so a page can show it to the customer; and the backend posts a `serverlog` when it answers: numbers only (the request's id, which route and answer, the status, when on the server's clock, how long it took). `readBridgeMessage` keeps it when every number is whole and in range. The page builds the lines itself from the level's data and the request it already has (`liveEntries`): the answer's scripted lines, then the **access line** (`POST /api/orders 500 Internal Server Error · 40 ms`; level error for a 5xx, warn for a 4xx, else info). The report carries no text; what the request sent (method, path and query, body) comes from the frame through the request message, each cut at 300 characters. A forged report can only repeat the level's own lines for a request of this load, once per request (a second report for an id is dropped), at most `MAX_LOG_LINES` (500) a load. Why build them on the page: the lines are level data, unit-tested; the frame stays the one that says what happened, not what it means.
- **The server's clock** (`clockText`): a line's time is `now` plus when its answer went out, on the chapter 6 rule (an answer at its request's start plus its delay; time moves only then), so the same run reads the same times in every browser.
- **Stacks**: a stack line `at fn (file.js:14:9)` (or `at file.js:14:9`) whose file is one of the app's links its line (an error a customer's browser reported to the server, 7.1's find task); server code (`server/orders.js`) stays text: you can read it, not run it.
- **Filtering** (`filterLogs`): a level and worse (all, warnings and errors, errors) and a text anywhere in the time, route, request id, message or stack, in any case; linear.

### The deploys

ADR 0007, update 2026-11-13 (chapter 7); `shared/levels/debugging/deploys.ts`, tests in `test/unit/levels/debugging/deploys.test.ts`, `incidents.test.ts`. A level with `sandbox.deploys` gets the Deploys panel (docs/features/ui.md, "Deploys").

- **A history** (`deployHistory(base, specs)`): the files before the first deploy listed, and each deploy as `{ id (7 hex digits), author, at, message, edits }` whose edits replace the first occurrence of a text (like a solution's saves). It keeps every version's files (`Deploy.files`); a level's starting files are the live (newest) one's (`liveFiles`), which the level tests check. It throws for an id that is not 7 hex digits or listed twice, an unknown file, a text that is not there, a deploy that changes nothing, more than `MAX_DEPLOYS` (8). The base is not a version you can roll back to.
- **Diffs** (`deployChanges`): each changed file with git's line diff (`diffLines`, `splitLines` from `shared/git/diff.ts`, the same LCS as `git diff`) grouped into git's hunks with three lines of context (`@@ -1,3 +1,4 @@`), every line with its number before and after and `at`, the line of the file after the deploy to show for it (a removed line: where it was).
- **Finding a line again** (`lineIn(from, line, to)`): where a line of one text is in another (the longest common subsequence; a line that is gone maps to the place after the last line kept before it), so a diff line opens where it is in the saved code now, also after your edits or a rollback. The code is whatever the player typed: past `MAX_MAP_CELLS` (4,000,000 lines times lines) a line keeps its number instead of freezing the page.
- **Versions**: `versionOf(history, files)` names the newest deploy whose files are exactly these (the panel's "your saved code"), `differingPaths` what a rollback changes.
- **Roll back** (the engine's `rollback`): every file becomes the deploy's (also files you changed that the deploy didn't touch: a rollback deploys a whole version), as one counted action like a save. The play page puts the files in the editor too and asks first (what changes, which files hold your own saved code, which unsaved edits are dropped). When the saved code was no version of the list, it keeps a copy, and **Undo roll back** (`restoreFiles`, counted like a save; only a file set with exactly the app's files) brings it back; a save after the rollback drops the copy, so Undo never throws a newer save away.
- **The files a check ran**: `reload(session, level, observation, ran)` records them as `checked` (the play page passes the files the check started with), so a save made while the check ran is not taken for checked code.

## The review environment

ADR 0008; `shared/levels/review/`, tests in `test/unit/levels/review/` (`diff.test.ts`, `checks.test.ts`, `engine.test.ts`, `levels.test.ts`), `test/unit/ui/review-view.test.ts` and `e2e/ai-review.spec.ts`. A level is a **pull request** by **Sous**, Corner Bakery's scripted coding assistant: no model is called, everything Sous writes is level data.

- **Level fields** (`ReviewFields`): `pr` (`{ number, title, branch, description (paragraphs), claims (a list), fixes? (the **linked issue** it says it fixes: `{ number, title, author, body }`, shown with the pull request, not a place to comment), base, head }`: the files before and after it; the diff is computed from them), `issues` (the **planted issues**: `{ id, path, lines?: [start, end] (lines after the pull request), removed?: [start, end] (lines it removed, numbered before it), also? (other places a comment may point at it, such as the line that adds a value a `switch` never handles, or the claim it breaks: `claimAt(pr, index)`), categories (the ones that count), title (a short line for a comment's feedback), explanation (for the debrief) }`), `tempting?` (places that look wrong and aren't: `{ path, lines? or removed?, why }`), `verdict` (`'request-changes'` when there is an issue, `'approve'` when there is none), `reason?: true` (a verdict practice task: the review needs a one-line reason), `run?` (`{ page, open, backend?, baseBackend? }`: the pull request runs in the Debugging sandbox, on a scripted server when its page makes requests, main on `baseBackend` where the pull request changes what the server answers), a scenario's `teaches` (its tag on the track page: `off-by-one`, `wrong variable`, `inverted condition`, `missing case`, `units`; chapter 2 `empty case`, `refactor`, `test report`, `linked issue`, `stale cache`; chapter 3 `no assertion`, `mocked`, `test bent to the bug`, `untested edge`, `snapshot`; chapter 4 `invented method`, `ignored option`, `invented import`, `removed API`, `made-up package`; chapter 5 `HTML injection`, `secret in code`, `missing check`, `trusting the client`, `whose data`; chapter 6 `reformat`, `unrelated change`, `rewrite`, `two in one`, `unasked feature`).
- **The diff** (`diff.ts`): `pullRequestDiff(base, head)` is git's line diff (`diffLines`, `splitLines` of `shared/git/diff.ts`) file by file in path order (unchanged files left out; `status` added, deleted or modified), grouped into git's hunks with three lines of context (`DIFF_CONTEXT`), every row `{ kind: same | add | del, text, old, new }`; `reviewDiff(level)` works it out once per level. A comment sits on one stretch of rows of one hunk, at most 12 (`MAX_COMMENT_LINES`); its **place** is the lines those rows have on each side (`CommentPlace { path, head: { start, end } | null, base: … | null }`; an unchanged row has a line on each side). `placeOf(file, hunk, from, to)`, `placeRows(file, place)` (strict: exactly one stretch), `canonicalPlace(diff, place)` (the rows with a line in it, when they are one stretch, and every line they have), `placeFor(diff, spot)` (a level's spot as a comment's place), `locate`, `rowIn`.
- **The description as numbered lines** (since 0.3.4, ADR 0008 "chapter 2"): `descriptionFile(pr)` is Sous's description as a file nobody changed, path `DESCRIPTION_PATH` (`'description'`; shop files always have an extension): each paragraph one line, then each claim one line, one hunk of unchanged rows (the number on both sides). `commentTargets(pr)` (`reviewTargets(level)`) is everywhere a comment can sit, the description first, then `diffOf(pr)`; `addComment` and solution steps take places in it, so a comment on a claim is a comment like any other (`{ comment: 'description', lines: claimAt(pr, 1).lines, … }`). `claimAt(pr, index)` is the line of a claim (after the paragraphs) as a spot, `paragraphAt(pr, index)` a paragraph's; a level names the claims an issue breaks, and the paragraphs that state the same, in its `also`, and a claim that holds can be a tempting spot. Every line of every description is audited in `levels.test.ts` (`DESCRIPTION_TRUTH`: the issue whose falsehood it states, or null when it holds), and a pull request that needs changes always makes a claim that holds, so flagging the whole description is never free. `reviewDiff(level)` stays the files only (the pull request's "files changed").
- **Categories** (`CATEGORIES`): bug, security, missing test, false claim, invented API (since 0.3.6: a function, option, export or package that doesn't exist, or a deprecated call; a real API used the wrong way is a bug), scope, unclear. In chapter 1 every issue accepts bug (plain bugs; most also false claim, with the claim they break), so there the category barely grades; from chapter 2 on an issue accepts the kind it is (a false claim, a missing test, an invented API, security, scope) and not always bug, and `levels.test.ts` fails a later chapter whose every issue accepts bug, and any issue outside chapter 4 that accepts invented API. Chapter 5's holes accept `security` (and false claim where the description says it is safe), never bug; its blankets include security comments. Chapter 6's extras accept `scope` (and false claim where the description says nothing else changes; a rewrite `unclear` too), never bug, and a bug hidden among them accepts bug, never scope (a value changed silently inside a reformat or a rename accepts both: *Formatting only*, *Renamed, and raised*); `levels.test.ts` fails any issue outside chapter 6 that accepts scope, and the blankets include scope comments (alone, with bug, with false claim). **Verdicts** (`VERDICTS`): approve, request changes.
- **State** (`ReviewState`): `comments` (`{ id, path, head, base, category, text }`; ids only go up), `nextId`, `sent` (the last review sent: its verdict, summary, its comments as they were and its `ReviewResult`; null before the first), `alarmed` (comment ids already counted as false alarms), `reviews` (how many were sent).
- **Counted actions** (`engine.ts`): `addComment(session, level, draft)` (refused, nothing counted, when its lines are not one stretch of the diff, the category is unknown or the text is over 500 characters; kept with every line its rows have), `editComment(session, level, id, { category, text })` (its lines stay, as on GitHub), `deleteComment`, `submitReview(session, level, verdict, summary)` (a verdict task refuses one without a reason, `refused: 'reason'`; the summary is trimmed and cut at 500). You can send as often as you like; the comments stay.
- **What a review found** (`checks.ts`, `checkReview(level, comments, verdict)`, `commentFeedback`): a planted issue is **found** when a comment touches its lines (`touches`: a head line of the comment in `lines`, or a base line in `removed`; or one of its `also` places, `touchesIssue`) with a category it accepts, and the comment is **focused**: at most `FOCUS_SLACK` (2) of its rows belong to no planted issue, and at most `FOCUS_SLACK` to issues its category doesn't fit (rows of another issue count as its own only when its category fits that issue too, so one comment over two issues side by side finds both when it fits both; since 0.3.8, ADR 0008 "chapter 6": a bug comment over a reformat's twelve lines with the one lost line among them is not focused on the bug, it is wide; before, no issue's rows counted, and a bug comment anywhere over a scope issue found the bug in it). The two counts are apart, so every comment of chapters 1 to 5 grades as it did (review of chapter 6: checked for every place and category). The rows that make a wide comment broad are still only those of no issue at all: more of them than the slack, some changed. A focused comment on an issue with another category is **near** (not found, not a false alarm). A wider comment over an issue and lines of context is **wide** ("narrow it down": not found, not a false alarm); a wider one that also covers changed (+/-) rows with nothing wrong in them is **broad**, a false alarm. A comment that touches no issue is a false alarm too; on a tempting spot it gets that spot's `why`. **On the description** only `false-claim` fits (what is wrong with a line of it can only be that it isn't true; another kind on a broken claim is near), and the comment must sit on the false lines alone (`DESCRIPTION_SLACK` = 0: a line of the description is a whole statement, with no context around it); a line that holds counts like a fine change, so one over a false claim and lines that hold is broad, a false alarm ("most of the lines this comment covers hold"), and never says a problem is there (Opus review, 2026-11-14: a comment over the whole description was a free hint). So a claim issue is found by a `false-claim` comment on the claim, or on the code lines that break it. Why the focus rule: a review of 12-row comments over every hunk, each of the kind bug, found every issue of chapter 1 with no false alarm (Opus review, 2026-11-14); `levels.test.ts` replays that blanket (12 and 10 rows, every comment full size, over the description too, of the kind bug, false claim, or both on every stretch, and from the later chapters missing test, invented API, security and scope, alone or with bug, security or scope with false claim) on every level and none is solved, and in every scenario any tiling blanket that solves costs false alarms; a false-claim comment on every claim (or every line of the description) and nothing else costs at least one false alarm on every level, and one comment over the whole description solves none. `verdictRight`: the level's verdict, and an approval with comments is not (`flaggedApproval`: every comment flags a problem, and an approval says there is none). **Solved**: every issue found and the verdict right. What a comment or the summary says is never read.
- **Goals** (`reviewGoals({ issues, verdictTask? })`): "Find the problems in the diff (n)" (how many, never where) and "Send your review with the right verdict", both from the last sent review; a verdict task has one goal, the whole review ("Approve it or request changes, with a one-line reason").
- **The run's measure**: fewest hints, then fewest **false alarms**: each comment that was a false alarm in a sent review counts once per attempt (sending it again, or editing it, adds nothing; deleting it and writing a new one counts again). **Reset keeps them**, like hints (the core's `restart` carries `falseAlarms`): the feedback names the comments that found something, so a review sent again after Reset would otherwise copy the answer for free. Play again (a fresh attempt) starts at 0, as it does for hints. Comments, edits and reviews are counted actions but cost nothing in the best run.
- **Solutions** (`ReviewStep`): `{ comment: path, lines? or removed?, category, text }` (on the rows with those lines of the description or the diff, `placeFor`; a step that is not one stretch throws) and `{ submit: verdict, summary? }`. `playReviewStep`, `playReviewSolution(level)` (synchronous: nothing runs in a browser).
- **The Tests panel** (since 0.3.5, ADR 0008 "chapter 3"): a pull request's files may include **test files** (`*.test.js`, `isTestFile`), which Run the PR's Tests panel runs; the diff shows and grades them like any file. No level field: a pull request that runs and has test files gets the panel. **The runner** (`test-runner.ts`, `TEST_RUNNER_SOURCE`, JavaScript in a string like the bridge) gives the test files Jest-style globals: `test` (and `it`), `expect` with `toBe`, `toEqual` (deep, as Vitest's: `Object.is` for every value, so -0 is not 0, and a property set to `undefined` counts as none), `toBeCloseTo(n, digits = 2)`, `toContain`, `toThrow(substring or pattern?)`, `toBeTruthy`, `toBeFalsy`, `toHaveBeenCalled`, `toHaveBeenCalledTimes`, `toHaveBeenCalledWith`, `toMatchInlineSnapshot(text)` (the value as text, a string as is, against the snapshot without its first and last blank lines and common indentation), each also as `.not`; `vi.fn(impl?)` (`.mock.calls`, `.mockReturnValue`, `.mockImplementation`) and `vi.spyOn(object, name)` (put back after each test). No `describe`, hooks, fake timers or module mocks. Every matcher that runs is a **check** of its test, so the panel can say a test passed without checking anything (`expect(total)` alone). Failures read like Jest's ("expect(received).toBe(expected)", "Expected: 8.39", "Received: 8.399999999999999"; `toBe` on equal objects adds "use toEqual"). Tests run one after another, async ones awaited. **Caps** (`TEST_LIMITS`): 100 tests a run (the rest counted as left out), names 200 characters, messages 2000, stacks 4000, a printed value 300 (objects 3 levels and 20 entries deep, cycles as `[Circular]`); a thrown non-error is printed ("Thrown: \"out of flour\""). **Where they run** (`test-sandbox.ts`): `planTests(files)` lists the test files, the modules they import (each after the ones it imports, relative imports pointed at placeholders) and the files that can't run (an import of a file that isn't there, "Failed to load ./split.js from split.test.js: no such file.", or a circle of imports). `testDocument(plan, token)` is a sealed frame's document with the sandbox's policy and the **test bridge** only: it hands the page its two ports (the same hello and token as the app's bridge), makes a blob URL per module (its imports pointed at those before it: a worker has no import map) and starts the runner in a classic **worker** (a module worker can't start in the frame's opaque origin; a classic one can `import()` blob modules), which reports over a port only the bridge holds. A **watchdog** gives each test 2 s (`testMs`) and each file's load 3 s (`loadMs`): a step that says nothing for that long is "did not finish", the worker is stopped and a fresh one goes on from the next test (a file that hung loading is left out), at most 5 times (`maxRestarts`), so an endless test blocks neither the frame nor Grindstone. A test's result (and a file's report) is held until the worker says anything after it: a test that ends but leaves work running (a timer, an un-awaited loop) and so keeps the worker from the next test is "did not finish" with `leaked` (a failed one stays failed, with `leaked`), and a fresh worker goes on from the next test (review of 2026-11-14: the run used to end there, the rest unlisted). The bridge passes on plain data, cut, as `testFile`, `test` and `testsDone` messages, which `readBridgeMessage` reads again with the same caps; `readTestRun(messages, plan, finished)` keeps only the plan's test files, each test once, at most 100, maps where each test is (`test(...)`'s stack) and where it failed (its test file's frame, else the first of the pull request's files) to lines, and names blob URLs as files in messages; `testSummary` counts passed, failed, did not finish and files that could not run. **The two sides** (`testRunFiles(pr, side)`): This PR runs the pull request's tests on its own files, main runs them on main's code (main's files with the pull request's test files on top), so a test that passes on main too is seen not to prove the change, and one changed to the bug fails there. A test is level data, never the player's: a test that fakes its own result is nothing a player can write, so the runner guards liveness and size, not integrity (its built-ins are the worker's). Tested on Node with the very source (`test-runner.test.ts`, `test-sandbox.test.ts`, and every chapter 3 pull request's tests in `levels.test.ts`, linked as `data:` modules by `run-tests.ts`) and in Chromium (`e2e/ai-review.spec.ts`); the watchdog was also checked by hand in Firefox and WebKit.
- **Steer levels** (since 0.3.9, ADR 0008 "chapter 7", `steer.ts`, tests in `test/unit/levels/review/steer.test.ts` and `test/unit/ui/steer-view.test.ts`): you write the review that makes Sous fix it. A level with `steer` (`SteerSpec`: `rounds`, `problems`, `start`, `tempting?`) has **rounds**: round 1 is Sous's pull request (`pr`, whose `issues` and `tempting` are round 1's, worked out by `steerScenario` / `steerPractice`), and a request for changes before the last round is answered by **Sous's commit**, the next round. A **problem** (`SteerProblem`) names its place by text, not lines (`at: { path, text }` in the round's file, or `removed` text of main's file; `also`; `breaks` claims and `says` paragraphs it makes false), since commits move lines; `steerRound(level, commits)` works a round out from the commits alone (the files, the open problems as planted issues, the fine places whose text is still there and no open problem covers), once per level and commits. What a commit does is scripted by the review's comments, matched as any review (`checkReview` on the round, `sousAnswers`): per open problem in the level's order, the first comment that **finds** it gets its `fix` (`SteerReaction`: `edits` replacing text or reverting a file to main's, `becomes` problems in its place, none for a fix, and Sous's `reply`); else the first that is **near** (its lines, a kind that doesn't fit) gets the `misread` scripted for that category, a plausible **wrong fix** (`as: [categories]`; the problem is replaced by what `becomes` says), or nothing (`shrug`) for a kind none names; per fine place with an `overreach`, the first false alarm on it makes Sous “fix” the fine code (a new small problem). Every other comment is answered too: too wide to tell which line (`unsure`) or a false alarm elsewhere (`nothing`) changes nothing. The session keeps only `commits: SteerCommit[]` (`{ review, answers }`); its state's `comments` and `sent` are the current round's (a commit moves the review into it, and the next round starts empty). A request for changes without a comment is refused (`'comments'`); one in the last round is graded as a review, with no commit. **Goals** (`steerGoals`), both decided by an approval so no round tells whether Sous got it right before you look: "Steer Sous to fix the problems (n)" (the approved round has nothing open) and "Approve it once it is right, by round N" (solved: approved, nothing open, no comments). A request for changes meets neither, also in the last round, where `checkReview` grades a review that finds every open problem as solved (the round's verdict is request changes): the page says the rounds are used up. **The run's measure** gets a third count, `rounds` (commits Sous pushed in the attempt; kept across Reset like false alarms, since a wrong fix showed which comment misled it; Play again starts at 0): fewest hints, then false alarms, then rounds (`fewestHintsThenFalseAlarms` is `['hints', 'falseAlarms', 'rounds']`; a review level's run has none, so it compares as before, no new progress version). Every path ends in a defined state: `steer.test.ts` walks every round a level can reach (each problem's fix and wrong fixes, each overreach, in every combination) and checks that its files apply, every open problem and fine place sits where a comment can, and one right comment per problem fixes them all while a round is left; steered blankets (every kind, 1 to 12 rows, every round) never solve one without false alarms.
- **World** (`shop.ts`): Debugging's order page, stylesheet, products and money helper (`orderSite`), with a basket that keeps one line per product and its quantity (`BASKET_CART`: `itemCount`, `basketTotal`), `SUMMARY_APP` (Add, then the summary is drawn again) and `shopFiles(files, page)`; since 0.3.7 `serverShop(files, { whoAmI?, imports?, main?, header? })` (`header` since 0.3.8: more lines under the tagline, 6.2's opening hours), the shop whose menu comes from the server (Debugging's `networkSite` and `MENU_JS`, an app.js that puts the server's names and prices in with `textContent`, optionally “Signed in as Sam” from `/api/me`), for chapter 5's pull requests that change the server's code too: a `server/…` file is shown and graded like any other and never loaded by the page. ## The Web fundamentals environment

ADR 0009, since 0.4.1; `shared/levels/web/`, tests in `test/unit/levels/web/` and `e2e/web-levels.spec.ts`, `e2e/web-play.spec.ts`, `e2e/web-cookies.spec.ts`, `e2e/web-auth.spec.ts`, `e2e/web-caching.spec.ts`, `e2e/web-event-loop.spec.ts`, `e2e/web-accessibility.spec.ts`. ### The CORS model

`shared/levels/web/cors.ts` (`CORS_SOURCE`, plain JavaScript in a string like the bridge, run in the frame by the web backend for every request; `test/unit/levels/web/cors.test.ts` runs that very source on Node, each rule beside the Fetch Living Standard's text it follows, and every refusal's wording). Pure: methods, header lists (`[name, value]` pairs), a credentials mode in; plain data out.

- **Simple or preflighted**: a CORS-safelisted method is `GET`, `HEAD` or `POST`; a CORS-safelisted request-header is `Accept` (no CORS-unsafe byte), `Accept-Language` / `Content-Language` (their character set) and `Content-Type` whose essence is `application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain`, each value at most 128 bytes, and all of them together at most 1024 (`isSafelistedHeader`, `unsafeHeaderNames`: lower case, sorted, once each). A cross-origin request in `cors` mode with another method or an unsafe header is preflighted (`needsPreflight`).
- **What a request carries** (`requestHeaders`): forbidden request-headers are dropped without a word (`Origin`, `Cookie`, `Host`, `Sec-*`, `Proxy-*`, … and `X-HTTP-Method-Override` with a forbidden method), and in `no-cors` mode every header that is not a no-CORS-safelisted one (the Headers object's "request-no-cors" guard). The backend adds the `Origin` (a CORS request, or any that isn't `GET`/`HEAD`) and the session cookie.
- **The preflight** (`preflightHeaders`): `OPTIONS` with `Accept: */*`, `Access-Control-Request-Method` and, when there are any, `Access-Control-Request-Headers` (the unsafe names joined with `,`, no space), plus the `Origin`; never a cookie, never the page's headers.
- **The CORS check** (`check`), in Chromium's order: `*` passes without credentials and is refused with them (before anything else); no `Access-Control-Allow-Origin` fails; a value that is not the request's origin fails, told apart as several values (a space or comma: two headers are combined with `, `), a value that is no URL to Chrome (no scheme: `cornerbakery.shop`), or another origin (`https://cornerbakery.shop/` with its slash, `null`, `foo:bar`); with credentials, `Access-Control-Allow-Credentials` must be exactly `true`. A header's value is read without spaces and tabs at its ends, as the HTTP layer reads it (`"https://cornerbakery.shop "` and `"true\t"` pass).
- **The preflight's answer** (`checkPreflight`): the CORS check first, then an ok status (200–299; "It does not have HTTP ok status."), then `Access-Control-Allow-Methods` and `-Headers` parsed as tokens (unparseable: "Cannot parse …"), then the method (listed exactly as written, safelisted, or `*` without credentials), `Authorization` (named, never by `*`), and every unsafe header (named in any case, or `*` without credentials).
- **What the page sees** (`exposedHeaders`): of a readable cross-origin answer, the CORS-safelisted response headers and those `Access-Control-Expose-Headers` names (`*` only without credentials), never `Set-Cookie`.
- **Chrome's words** (`reason`, `consoleLine`): "Access to fetch at '…' from origin '…' has been blocked by CORS policy: " and the reason, with "Response to preflight request doesn't pass access control check: " for a refused preflight's Allow-Origin, Allow-Credentials and status, and " Have the server send the header with a valid value." after the three Allow-Origin value errors, as Chromium 158 says them (no "If an opaque response serves your needs…" tail on any message any more; Debugging's chapter 2 lines from 0.2.9 still have it).
- **Built-ins taken first**: the model, the web backend and the server's host take every built-in the decision path and the probes use (string and pattern functions, the URL's and the Request's getters, Headers' `forEach`, the Promise, the Worker's `postMessage`, `terminate` and its events' getters, `addEventListener`) when the bridge makes them, before any of the app's code runs, and walk lists by index (no array method of the data is called). An app that replaces `URL.prototype.origin`, `MessageEvent.prototype.data` or a Worker's `onmessage` to read another origin's answer gets nothing from it (`e2e/web-levels.spec.ts`); what it changes is only what it shows itself (CoreHub #522's class, unchanged).

### The cookie model

ADR 0009 chapter 2, since 0.4.2; `shared/levels/web/cookies.ts` (`COOKIE_SOURCE`, JavaScript in a string like the CORS model, run in the frame by the web backend; `test/unit/levels/web/cookies.test.ts` runs that very source on Node, each rule beside the text of RFC 6265bis, and Chrome's words). A parser and a **jar** (one per load, on the scripted clock: `WEB_CLOCK`, Tuesday 17 November 2026, 09:41 GMT, standing still for the whole load).

- **Parsing a Set-Cookie line** (`parse`, 5.6): a control character (or, as Chrome, a tab inside a name, value or attribute) refuses the line; the name-value pair up to the first `;`, split at the first `=` (none: a nameless cookie), trimmed; empty name and value refused; name and value over 4096 characters together refused. Attributes in any case, the last of each wins, an unknown one or a value over 1024 characters ignored: `Expires` (the cookie-date algorithm of 5.1.1: tokens in any order, two-digit years, impossible dates fail; a year before 1601 is 1601, as Chromium clamps it, so the cookie is long expired), `Max-Age` (whole seconds, a leading `-` or `+` as Chromium reads it; it wins over Expires), `Domain` (without its leading dot, lower case; the last one wins, an empty one too, which makes the cookie host-only, as in Chromium), `Path` (only when it starts with `/`, else the default-path), `Secure`, `HttpOnly`, `SameSite` (`None`, `Strict`, `Lax` in any case; anything else is not set). Linear, capped at 16,384 characters, never throws.
- **Storing** (`store`, 5.7): a `Domain` that is a public suffix (here: a host's last label, `shop`) or that the host does not domain-match (`cheap-flour.example`, a sibling `promo.cornerbakery.shop`) is refused (`InvalidDomain`); without one the cookie is **host-only**. A missing Path gets the **default-path** (the request path up to its last `/`: `/auth/login` gives `/auth`). `Secure` only from https (`SecureOnly`); from document.cookie never `HttpOnly` (`HttpOnlyFromScript`) and never in place of an HttpOnly cookie (`OverwriteHttpOnly`); a cookie that is not `None` from a cross-site answer that is no top-level navigation is refused (`SameSiteStrict`, `SameSiteLax`, `SameSiteUnspecifiedTreatedAsLax`); `None` needs `Secure` (`SameSiteNoneInsecure`); an insecure line may not replace a Secure cookie (`OverwriteSecure`, "Leave Secure Cookies Alone"). The same name, domain, host-only flag and path replace a cookie; as Chromium does, the old creation time is kept only when the value is the same (a new value is a new cookie: a later place in the header's order, a new Lax+POST window); an expiry in the past (`Max-Age=0`, an old `Expires`) deletes it. Expiries are capped at 400 days (Chrome). **Chrome's limits**: 180 cookies per site, then the 30 used longest ago go; 3300 in all, then 300.
- **What a request carries** (`forRequest`, 5.8.3): only with credentials; the cookies of the URL's site, each sent or why not: `DomainMismatch` (a host-only cookie of another host of the site), `NotOnPath`, `SecureOnly`, then SameSite by the context the backend gives (same-site: the initiator's site is the URL's; a top-level navigation): a cross-site request gets `None`; a cross-site top-level `GET` also `Lax` (and a cookie without SameSite, which is Lax); `Strict` never. **Lax+POST** (Chrome, `kSameSiteDefaultChecksMethodRigorously` off): a cookie set without SameSite at most 2 minutes ago still goes with a cross-site top-level `POST` (`laxAllowUnsafe`). The header is in the draft's order: longer paths first, then the earlier created.
- **document.cookie** (`document`, `write`): the page's cookies without the HttpOnly ones (a same-site, top-level context), and writes through `store` as a "non-HTTP" API. `readable(origin)` and `steal(origin)` are what a script on that origin could read on any of its paths (Path is no protection from a script of the same origin, 8.5): names, and as a Cookie header.
- **Sites** (`siteOf`): the scheme and the registrable domain, schemeful: `https://api.cornerbakery.shop` and `https://promo.cornerbakery.shop` are one site, `http://cornerbakery.shop` is another, `cornerbakery.shop.cheap-flour.example` belongs to `cheap-flour.example`.
- **Chrome's words** (`reason(problem, kind)`), from DevTools' `front_end/core/sdk/NetworkRequest.ts` as shipped (code marks without backticks, typographic apostrophes, most without a final full stop): for a blocked Set-Cookie ("This attempt to set a cookie via a "Set-Cookie" header was blocked because it had the "SameSite=None" attribute but didn’t have the "Secure" attribute, which is required in order to use "SameSite=None"") and for a cookie a request did not carry ("This cookie was blocked because it had the "SameSite=Lax" attribute and the request was made from a different site and wasn’t initiated by a top-level navigation"). Where Chrome says nothing, Grindstone's own words say so: a document.cookie write it ignores ("document.cookie can't set an HttpOnly cookie: the browser ignores the write."), a cookie sent only by Lax+POST ("Sent anyway: …").
- **Built-ins taken first**, as in the CORS model: the URL's getters, string and pattern functions, `Date.UTC`; lists walked by index. **No inherited setter or getter reaches it** (since the review of 2026-11-17): every list element is defined with a descriptor that has no prototype (an assignment to a new index would run a setter the app put on `Array.prototype` or `Object.prototype`, and `defineProperty` reads `get`/`set` through the chain too), the fields of a context or a parse result that may be left out are read as the object's own only, and the jar hands out copies, never its cookies. The CORS model, the web backend (its requests' specs are built whole, its answers' `fail` read as own) and the server's host do the same.

### The storage model

ADR 0009 chapter 3, since 0.4.3; `shared/levels/web/storage.ts` (`STORAGE_SOURCE`, JavaScript in a string like the cookie model, run in the frame by the web backend; `test/unit/levels/web/storage.test.ts` runs that very source on Node beside the HTML standard's "Web storage" and WebIDL's text). The sealed frame's opaque origin has no storage (the browser's own throws), so in a level whose `WebSpec` has `storage` the bridge defines `window.localStorage` and `window.sessionStorage` before the app runs, not configurable, as the model's.

- **Areas**: one per origin and kind (`localStorage`; `sessionStorage` per origin of the page's one tab), each a list of keys in the order first set (an overwrite keeps the place) and string values. A level's `storage` items are what the browser kept from before; each load starts from them (a Reload is a new visit, as with cookies).
- **The page's object**: a Proxy over the area with Storage.prototype as its prototype (`instanceof Storage`, `[object Storage]`), as Chrome has it: an item reads, lists (`Object.keys`, `for…in`, `JSON.stringify`, `Object.entries`) and is set like a property, unless its name is one of Storage.prototype's own members (`getItem`, `length`, `clear` …): those stay the members, and assigning to one is an ordinary assignment (a method gets an own property, `length` stays). A name from Object.prototype (`toString`, `__proto__`) hides no item (WebIDL would hide it; Chrome doesn't). `delete` removes an item; an accessor descriptor is refused; the prototype can be set. Storage.prototype gets the model's `getItem`, `setItem`, `removeItem`, `clear`, `key` and the `length` getter (the browser's own refuse a Proxy): "Illegal invocation" on anything else, Chrome's words for a missing argument, keys and values through ToString (a Symbol throws).
- **Quota**: Chromium's 10 MiB per area counted as UTF-16, so 5,242,880 code units of keys and values; past it `setItem` throws a `QuotaExceededError` ("Failed to execute 'setItem' on 'Storage': Setting the value of 'k' exceeded the quota.") and keeps what it had.
- **Hardened like the cookie jar**: every built-in it uses (Proxy, Reflect, WeakMap's members, String, Number) is taken when the bridge makes it; lists are written with descriptors without a prototype; the handler and every descriptor it returns have no prototype; the areas hand out copies. A member the app replaces on Storage.prototype changes what its own calls do, never an area, a probe or the panel.
- **The Application panel** gets every area that holds anything after each change (`storage` messages, at most every 50 ms, with the scripted clock's time for the tokens' expiry), at most 200 items an area, texts cut at 300.

### The thief

ADR 0009 chapter 3, since 0.4.3; in the web backend (`copy`, `issued`, `replay`). What an attacker does with what it got, from outside the browser (as curl would: no CORS, no SameSite, no Max-Age), so the goals can ask whether a session can be **taken** rather than whether one script read one thing:

- **What it has** (`using`): `'script'`, what a script on the page could take at that moment: `document.cookie`, every item of the page's own localStorage and sessionStorage, and of every request the page's code sent its headers (an `Authorization`, a custom header) and query, and every answer it could read (a token in the login's body); `'browser'` (a `copy`): the browser's cookies for the API, HttpOnly ones too; a site's origin: every value that reached that site's server (the widget's "analytics", URL-decoded); `issued`: the Set-Cookie values and body strings of a sign-in some minutes ago.
- **What it tries**, name- and value-blind: the cookies it has (those the browser would send to that path, in the browser's order: longer paths first, then the older); each header set the page sent, alone and with those cookies; each string it found as `Authorization: Bearer …` (alone and with the cookies), as a raw Cookie header when it has an `=`, and under each cookie name the API uses (it can sign up and see the names); each query. A string read as JSON gives its strings, not itself; token-shaped strings (`header.payload.signature`) first, at most 40 tries. **Sent exactly as the page sends a request to the API** (since the review of 2026-11-18): the headers its code set in a Headers object's order, then its `Origin`, the cross-origin `Referer` (`https://cornerbakery.shop/`), the cookies; no body, no user agent (the page sends none either); and server.js gets `req.headers` in one fixed order (by name) whoever sent them. So a server.js can't tell the thief by how it sends; only what was taken decides. Known limit: it replays what it took word for word, so a server that accepts each request only once with a counter the page sends beside the token (a one-time nonce) refuses it: a non-fix the model doesn't catch (a real thief with a script on the page would take the counter too). The value: the first 2xx status, else the last, or 'failed'. A copy keeps the cookies an answer gives it (a rotated refresh token), as a thief would. `forge`: each JWT it has made up without the secret (its `exp` 30 days on; with its old signature, and as alg none).
- **Shown**: a scene's replay with `show` posts a `replay` message: the Server panel's line under server.js's access line (who, what it sent, the answer, the token's claims).


`shared/levels/web/sites.ts`: a site Lena opens while she is signed in (`OtherSite`: `origin`, `path`, `title`, `role` `attacker`, `mail` or `other`, `intro` lines, `actions`, `noReferrer`, `hidden`). Its **actions** run in order through the web backend, the same cookie and CORS models as the page's: `{ img }` (a no-cors GET with the cookies an image may carry), `{ fetch, method?, credentials?, mode?, body? }` (a form body), `{ form, method, fields }` (a form that submits itself: a top-level navigation, a POST's body urlencoded) and `{ link, text }` (Lena clicks it: a top-level GET). A form or a link ends the page. `sitePage(site)` writes its HTML from those very actions (the Other site panel shows it, read-only). A `hidden` site has no panel and no text names it: the CSRF guards' `bread-offers.example`, the attack again with `<meta name="referrer" content="no-referrer">` (no Referer; `Origin: null` on its POST). Another site's server answers anything with 200 ("ok"), so a leak arrives somewhere.

### The cache model

ADR 0009 chapter 4, since 0.4.4; `shared/levels/web/cache.ts` (`CACHE_SOURCE`, JavaScript in a string like the cookie model, run in the frame by the web backend; `test/unit/levels/web/cache.test.ts` runs that very source on Node beside RFC 9111's text and Chrome's code). Two caches on the scripted clock (the scene's and probes' `{ later }` age them): **Lena's browser's HTTP cache**, a private cache read as Chrome's network stack reads an answer, and **the CDN** in front of the API, a shared cache as RFC 9111 has it.

- **Cache-Control** (`directives`, RFC 9111 5.2): names in any case, a value quoted or not, the first of a name wins (4.2.1).
- **Freshness** (`lifetime`): in the browser as Chromium's `GetFreshnessLifetimes`: `no-cache`, `no-store`, `Pragma: no-cache` ("for backwards compat") and `Vary: *` make an answer stale at once whatever max-age says; then `max-age`, then `Expires` minus `Date` (or the time it arrived), then 10 % of the time since `Last-Modified` for a 200, 203 or 206 without `must-revalidate`; 300, 301, 308 and 410 are fresh for ever; else 0. At the CDN (4.2.1): `no-cache` (qualified or not) stale at once, `s-maxage` before `max-age`, then `Expires` (an invalid one, `0`, is in the past: 5.3), then the 10 % heuristic for a status that allows one; `Pragma` means nothing to it. A delta-seconds over 2147483648 is that; an invalid one is stale.
- **Age** (`age`, 4.2.3 as Chrome's `GetCurrentAge`): the `Age` an answer came with or how much older than its `Date` it arrived, whichever is more, plus how long it has been kept. A copy is fresh while its lifetime is more than its age.
- **What may be kept** (`refusal`, 3 and 3.5): only the answer to a `GET`; never `no-store`; at the CDN never `private`, and an answer to a request with `Authorization` only with `public`, `s-maxage` or `must-revalidate`; only with a lifetime of its own or a status a heuristic may use (a 302 without max-age is not kept). Chrome keeps no `Set-Cookie` with a copy; the CDN does (RFC 9111 doesn't forbid it).
- **Vary** (4.1): a copy answers only a request with the same values of the headers its `Vary` names (a missing header is a value too, whitespace around commas normalised; `*` never matches). The browser keeps one copy an address (a new answer replaces it), the CDN one for each set of values; the newest that matches answers.
- **Revalidation** (4.3): a stale copy with a validator is asked about with `If-None-Match` (its ETag) and `If-Modified-Since` (its Last-Modified); a 304 **freshens** it (3.2, 4.3.4): the 304's headers replace the copy's (Chrome's copy keeps its own ETag, Content-Type, Content-Encoding and the other headers `HttpResponseHeaders::Update` doesn't update, and any `x-content-` or `x-webkit-` one; the CDN's everything but Content-Length), and its age starts again. A cache answers a client's own condition itself (4.3.2): `If-None-Match` by weak comparison (`*` matches), else `If-Modified-Since` against Last-Modified.
- **Invalidation** (4.4): a non-error answer to an unsafe request (`POST`, `PUT`, `DELETE`, `PATCH`) takes the address's copies away, in both caches.
- **The browser's side** (in the web backend): a page request's `cache` mode as Fetch's HTTP-network-or-cache fetch reads it: `default` uses a fresh copy without a request and revalidates a stale one; `no-cache` revalidates even a fresh one and adds `Cache-Control: max-age=0`; `reload` and `no-store` add `Pragma: no-cache` and `Cache-Control: no-cache` (each unless the page set one), `reload` keeps the answer, `no-store` neither uses nor keeps; `force-cache` and `only-if-cached` use any copy, stale or not (`only-if-cached` needs `mode: 'same-origin'`: the browser's own TypeError, else `net::ERR_CACHE_MISS` without a copy). A condition the page sets itself (`If-None-Match` …) makes a default request `no-store` (Fetch), so the page gets the 304 itself; a `Cache-Control` or `Pragma` the page sets is read as Chromium does (`no-cache`: fetch anew, `max-age=0`: revalidate). Only a `GET` looks for a copy. The preflight, when one is needed, goes first (Fetch's order). A copy is still checked by CORS for the page that gets it (4.4's lesson).
- **The CDN's side**: every request to the API from anyone (Lena's page, another customer, a probe, the thief) passes it; a fresh copy is a **HIT** (with its `Age` and `x-cache: HIT`); a stale one with a validator is revalidated with the CDN's own condition (**REVALIDATED** on a 304); otherwise it asks server.js with the client's own conditions taken out, so it gets a whole answer to keep (**MISS**) or not (**PASS**, why in its log), and then answers the client's condition itself. Anything but a `GET` is a PASS. It ignores a request's own `Cache-Control` (RFC 9111 makes `no-cache` and `max-age` in a request a preference; most CDNs ignore them), so a page's `cache: 'no-store'` changes nothing there, but a forwarded `Cache-Control: no-cache` still reaches server.js, where Express then ignores the condition. Its **log** (who, what, outcome, status, the copy's age, a note) is the Application panel's.
- **Hardened like the cookie jar**: every built-in taken when the bridge makes it, lists written with descriptors without a prototype, copies and directives in objects without a prototype, optional fields read as own only, copies handed out; at most 100 copies a cache (the oldest go) and 200 log lines.

### The event loop model

ADR 0009 chapter 5, since 0.4.5; `shared/levels/web/loop.ts` (`LOOP_SOURCE`, JavaScript in a string like the cookie model, run by the bridge in the frame before any of the app's code; `test/unit/levels/web/loop.test.ts` runs that very source on Node with a window that has no DOM, beside the HTML standard's event loop and timer text). How the browser orders the page's work, as the HTML standard has it and Chrome runs it, **real where every engine already agrees and scripted where they don't**:

- **Microtasks are the browser's own**: promise reactions, `await`, `queueMicrotask` and MutationObserver callbacks run in the engine's own microtask checkpoint (the ECMAScript and HTML rules every engine follows).
- **Tasks and frames are scripted** (`setTimeout`, `setInterval`, `clearTimeout`/`clearInterval`, `requestAnimationFrame`/`cancelAnimationFrame`, `MessageChannel`, `window.postMessage`, a customer's tap): a queue by the time each may run, then the order queued. A timer's delay is a long (fractions dropped, a negative or NaN is 0); one set from a timer nested more than five deep waits at least 4 ms (the standard's timer initialization steps; an interval goes one level deeper each run). A message is a task now; a port starts with `onmessage` or `start()` and keeps what came before (structured clone; transfer lists ignored). After each task, when the clock has passed a frame (every 16 ms: a 60 Hz screen, rounded) and something needs painting (a rAF callback waits, or the page changed: a MutationObserver record), the frame runs: its rAF callbacks in order (those asked for during it wait for the next), then **style, layout and paint** (a finite transition or animation that is running also asks for frames, until one is painted at or after its end; an endless one doesn't): the browser's real style and layout are forced right there, so CSS transitions start exactly where a frame would start them, then the **snapshot** of the level's watched elements (`loop.watch`: displayed, visible, with a box; their text), and the transitions and animations that started; each frame keeps its time, and the computed opacity of the watched elements that keep one (`opacity: true`), apart from the panel's items. Each customer's tap keeps its time too. Nothing needs painting: no frame.
- **Each unit of work is a callback of its own of one real event** (in a check run a private MessagePort with 256 listeners): the browser runs the microtasks after each listener because it dispatched the event, and renders nothing in the middle of it, so the browser's real style is computed only where the model says (a frame, or the page forcing it). A batch ends after a frame, where a real browser may render too. **The app you see** (since the review of 2026-11-19) runs its batches in 1,024 native `requestAnimationFrame` callbacks of the next real frame instead: each gets the browser's microtask checkpoint, all run before that real frame works out its style, and a batch moves the scripted clock at most to the next model frame (that frame included), so a model frame's callbacks and paint always come before the real style, as in a check run; what comes later waits in real time (at most a minute at a time: the clock then moves on a minute). A frame out of sight gets no real frames: after 100 ms the batch goes by the port.
- **A customer's tap** (the probes' and the scene's `click`): it lands on what is on top at the element's centre (the browser lays out the page to find it; in the app you see, out of sight on a phone, the element itself), 5 ms after a frame, and the click goes as the browser dispatches it: its path (capturing, at the target capturing listeners first, bubbling), each object's listeners taken when the event gets there (a listener added further up during the tap runs; one added to the same object waits), one listener per unit (so the microtasks run after each), `once`, `removeEventListener`, `stopPropagation`, `stopImmediatePropagation`, an `on…` handler and `return false`. A handler (`onclick`, a port's or the window's `onmessage`) runs where it was first set among the listeners and keeps that place when replaced (the DOM's order); one set by an attribute in the page's HTML comes first. A bare `addEventListener(…)` (no `this`) is the window's, as in the browser. `element.click()` and `dispatchEvent` from the page's code stay the browser's own: every listener first. The model keeps every listener the page adds (by target and type) to do this: `addEventListener` and `removeEventListener` are the model's, the browser's own still dispatching through a wrapper.
- **The clock moves only by work**: each unit takes 10 µs, and each read of the clock (`performance.now()`, `Date`, Intl's default date) another 10 µs, so code that waits on the clock (`tablet.js`'s `busy(900)`, the levels' stand-in for real work) takes that long on it and delays the next frame. The page's `Date` tells 09:41:00 on Tuesday 17 November 2026 plus that clock. A check run's clock moves only while a probe drives it (and the load: until the page is quiet, at most 1 s); the app you see runs on by itself, waiting in real time (a frame for a real frame), so it looks like the page would. In a check run every transition and animation that started is paused and set to its time on the scripted clock at each frame, before the frame works out styles (the real clock hardly moves there).
- **Forced layouts**: reading a size or position (`offsetTop/Left/Width/Height/Parent`, `client…`, `scroll…` and setting `scrollTop`/`scrollLeft`, `getBoundingClientRect()`, `getClientRects()`, `scrollIntoView()`, `scrollIntoViewIfNeeded()`, `scrollTo/By()`, `focus()` of an HTML or SVG element, `innerText`, a Range's rects, `elementFromPoint(s)`, the window's `scrollX/Y`, `pageX/YOffset`, `innerWidth/Height` and `scroll/To/By()`, a mouse event's `offsetX/Y`, an image's `x`, `y`, `width`, `height`, the `visualViewport`'s `offsetLeft/Top`, `pageLeft/Top`, `width`, `height` and `scale`, and of `getComputedStyle()`'s result, or a map `computedStyleMap()` gave (its `get`, `getAll`, `has` of such a value; iterating it, `entries`, `values`, `forEach` or `for…of`, reads them all), the values Chrome resolves from the layout (`layout_dependent` in Chromium's css_properties.json5: `width`, `height`, `inline-size`, `block-size`, the insets, margins and paddings, `transform`, `transform-origin`, `translate`, `perspective-origin`, the grid's templates); `checkVisibility()` needs the style only, `computedStyleMap()` itself nothing) while the page changed since the last layout is one, counted where it happened (the panel merges a run of the same read). Any other computed value (an opacity, a colour, a min or max size) needs the style alone, which the model doesn't count. In a check run every read counts (nothing but the page's code reads its layout there: the bridge and the model use the browser's own functions, taken first). In the app you see a read counts while the page loads (its script, the microtasks it queued, its load event), inside a unit, or in the real event a batch or a browser's event runs in, so a test tool's or DevTools' reads later on are not the page's; no stack is read, so the page can't hide its reads (`Error.stackTraceLimit = 0`), and the play page's e2e turns trace snapshots off (they read the layout while the page loads). The readers are the model's on the prototypes, not configurable; a frame of the page's own is cross-origin in the sealed frame, so the browser's own readers are out of reach.
- **Left out on purpose**: `requestIdleCallback`, `scheduler` (Chrome's `postTask`/`yield`) and `BroadcastChannel` are not there (Safari has neither of the first two; a frame of one tab has no other end).
- **The Event loop panel** gets the timeline as it grows (`loop` messages: from where the last ended, at most 200 entries a message, 1,000 a load, then a note; times at most 1e9 ms): tasks (the page's script, a timer with its delay and whether it was clamped, a message, a tap, an event of the browser's, Console input), listeners, rAF callbacks, frames (number, what they painted, what started), forced layouts (the read, how many in a row) and the page's Console lines, `sync` or `microtask` (after its task: the bridge knows where the page's code is, and the page's module script calls a fresh, one-shot name when its synchronous part is over). At most 20,000 units a load and 2,000 pending tasks at once (cancelled ones are dropped first; the queue is a binary heap): then the loop stops for good and says so (something keeps queueing work). At most 500 animations are followed a load (then a note). The page's other clocks tell the scripted time too: `performance.now()`, `Date`, an event's `timeStamp`, `document.timeline.currentTime`.
- **Hardened like the cookie jar**: every built-in it uses taken before the app runs (the DOM's getters, `getAnimations`, the Animation's members, the MutationObserver's, the event's), records and lists without a prototype, arrays filled with `defineProperty`, what goes to the page built whole. Setters on the prototypes, patched style readers, a silenced MutationObserver, replaced timers or a patched `getAnimations` change only what the app gets itself (`e2e/web-levels.spec.ts`, three browsers).

### The accessibility model

ADR 0009 chapter 6, since 0.4.6; `shared/levels/web/a11y.ts` (`A11Y_SOURCE`, JavaScript in a string like the event loop model, run by the bridge in the frame before any of the app's code; `test/unit/levels/web/a11y.test.ts` runs that very source on happy-dom beside the specs' text; what needs a real browser's styles runs in `e2e/web-levels.spec.ts` and `e2e/web-accessibility.spec.ts` in three browsers). What a screen reader gets from the page and what a keyboard does on it, **real where every engine agrees, modelled where they don't**:

- **The tree is computed from the real DOM and the browser's computed styles**, after the specs as Chrome implements them. **Roles**: an explicit `role`'s first token the model knows (abstract and unknown ones skipped, `presentation` is `none`), else HTML-AAM's implicit role (links only with `href`, `section` and `form` a region or form only with a name, `header`/`footer` banner and contentinfo only outside sectioning elements, `li` a listitem only in a list, an `img` with `alt=""` none, `input` by type with `list` a combobox, `select` a combobox or with `multiple`/`size` a listbox, a details' first `summary` a button, `output` a status, an inline `svg` an img when it has a name, else nothing); `none` is ignored on what can take focus or carries a global ARIA attribute (the presentational role conflict). **Left out of the tree**: `aria-hidden="true"` on it or an ancestor (`false` never undoes it), `inert`, `display: none` (also `hidden`) on it or an ancestor, inside a closed `<details>` (but its summary), `visibility: hidden` (its children decide for themselves), `head`, `script`, `style`, `template`, `input type=hidden`; everything outside the model's modal dialog; and, while focus is inside a dialog with `aria-modal="true"`, everything outside it (Chrome's rule: Tab still goes there). **Names** (the Accessible Name and Description Computation 1.2): `aria-labelledby` (each id's text, hidden content too; an empty result goes on), `aria-label`, the host language (labels, Chrome's `placeholder` before `title` for a text field, `alt`, an input button's `value` or "Submit", a fieldset's legend, a figure's caption, a table's caption, an SVG's `<title>`), the content for roles that take their name from it (button, link, heading, checkbox, radio, option, tab, cell, …, with CSS `::before`/`::after` content and an embedded field's value), then `title`. **Descriptions**: `aria-describedby`, `aria-description`, a `title` that isn't the name. **Values and states**: a text field's value, a select's option; checked (native or `aria-checked` on a role that has it: checkbox, radio, switch, menu items; nowhere else), expanded (`aria-expanded` on a role that has it, a summary's details), pressed (`aria-pressed` on a button), selected, disabled (`:disabled` or `aria-disabled`), invalid (`aria-invalid` other than false), required, a heading's level.
- **Focus is the model's**: `focus()` and `blur()` of HTML and SVG elements, `document.activeElement` and a dialog's `showModal()`, `show()` and `close()` are the model's, installed before the app runs; the browser's own focus never moves (a check run must not take the keyboard from Grindstone, and engines disagree about focus in a frame that isn't focused). What can take focus: a link or area with `href`, a button, input (not hidden), select, textarea, iframe, a details' first summary, `audio`/`video` with controls, an editing host, anything with a valid `tabindex` (the HTML standard's integer rules); never a disabled control, inert content or what isn't rendered. `focus()` on anything else does nothing, as in a browser. Moving focus dispatches `blur`, `focusout`, `focus`, `focusin` (Chrome's order, `relatedTarget` set; a listener that moves focus again wins). When the focused element stops being focusable focus falls back to the page (the HTML standard's focus fixup): hidden, disabled or inert, with `blur` and `focusout` (the focusing steps for the viewport, which Chrome fires too; a listener may put focus somewhere else), and the element becomes the **starting point**; removed, with no event (the standard; Chrome fires `blur` before it removes the element, which the model can't) and no starting point. The model's fixup comes at the next MutationObserver delivery (or a probe's look), the standard's at the next rendering update. The page's own `focus()`, `showModal()`, `show()` and `close()` run the fixup alone: they never take the task's pending changes early, so the changes a handler makes around a `focus()` still reach the reader together, at the next delivery (since the re-check of 2026-11-20).
- **The Tab order** (the sequential focus navigation order): positive `tabindex` values first, smallest first and in page order among equals, then everything else in page order; `tabindex="-1"` never; of a radio group only the checked radio (none checked: the first). Tab from the focused element; with nothing focused, from Chrome's sequential focus navigation starting point (the next element after where focus was, in page order) or the top; past the last stop Tab **leaves the page** (the browser's own controls, the reader says so), and the next Tab starts at the top. Shift+Tab the other way.
- **The keyboard is the model's** (`isTrusted` false, the same in every engine): keydown on what has focus (else the body), what the browser does by default unless the keydown was prevented, keyup. Enter clicks a button (also `input` button, submit, reset, image, a summary) or a link with `href` (only `:disabled` stops it: `aria-disabled` doesn't, as in Chrome); Space clicks a button or a summary, and checks a checkbox or radio, on keyup (unless keyup was prevented too); a div, a span with `role="button"` or anything else gets neither. Escape fires `cancel` on the model's topmost modal dialog and, not prevented, closes it. Arrows are dispatched with no default action. No `keypress`, no implicit form submission (the sealed frame submits no form).
- **Dialogs**: `showModal()` opens the dialog in place (the `open` attribute, no top layer or `::backdrop`), makes everything outside it inert for focus, Tab and the tree, and focuses its `autofocus` element, else its first focusable one, else the dialog (which then keeps focus while it is open, a non-modal one too); `close()` removes `open`, fires `close` a task later and puts focus back where it was before (when it was modal or focus was inside it), as the HTML standard has it.
- **Live regions after Chrome**: a MutationObserver the bridge makes before the app runs takes the page's changes, and the model reads them at **update boundaries** (since the re-checks of 2026-11-20): a task of its own a frame (16 ms) after the first change, as Chrome updates its tree once a frame, and not before the page's short timers (a frame or less) set while the update is open have run, the ones they set too (the page's `setTimeout` and `clearTimeout` are the model's, counting them; at most 200 ms), so a timer that runs late on a busy machine still folds in; or a probe's read, a key or a mark. Never in the middle of one: a microtask, an `await`, a `focus()`, the page's own MutationObserver or its short timers, nested 0 ms ones included, split nothing; a later write, an answer from the network, is a new update. At each boundary, a change inside a live region (`aria-live` polite or assertive, nearest wins, `off` stops; role `status`, `log`, `alert`; an `output`) is announced when that region was live and shown at the previous delivery: what was added (text, or an added element's text), or with `aria-atomic` (implicit on `alert` and `status`) the whole region; removals say nothing. A part of such a region that was left out of the tree at the previous delivery and is shown now (`hidden`, a class, a style, `aria-hidden` taken away) is an addition too (Chrome; NVDA and JAWS read it), said once even when its text changed in the same moment. A region inserted together with its text, or made live (or itself shown) in the same moment as its text, says nothing; the one exception, as in Chrome, is a `role="alert"` that appears (inserted or shown) with text, which is read at once. Nothing is announced while the page loads.
- **The reader** says, at the task boundary too (where focus is then, read once with the name it has then: focus moved and a label set in one task is the new name, said once), as lines (`ReaderLine`: kind, text, the modelled key it followed, whether a probe was running): when focus moves (`dialog` for each dialog it entered, then `focus`: name, role, value, states, description; a focusable element with no role and no name reads its text), when the focused element's checked, expanded, pressed or selected state changes (`state`) or its name (`name`), what a live region announces (`polite`, `assertive`), and Tab leaving the page (`leave`). Each line keeps the last modelled key pressed before it ('Tab', 'Enter'; a timer's announcement after Enter too), '' once a check run's typing, click or focus move came after the key (since the review: a re-check while typing is no answer to Enter), 'user' after a real click or key in the app you see, '' before any.
- **The app you see** runs the same model; a real click or key there that moves the browser's focus (a trusted `focusin` right after a trusted pointer or key event) moves the model's focus too, and the reader follows; any other real focus event is kept from the page. A ring drawn over the page (in a closed shadow root, never clickable) shows where the model's focus is. A check run draws nothing (the ring's host is there all the same, with the same attributes, which never change; only the box in its closed shadow root moves or hides, so the page can't tell a check run by it) and keeps every real focus event from the page.
- **The Accessibility panel** gets the reader's lines as they come (`reader` messages: from where the last ended, at most 20 a message, 300 a load) and the tree only when it asks (`a11yTree`, answered with an `a11y` message: at most 400 rows, 40 levels deep and containers nested 200 deep (the reader clamps a deeper row's depth rather than dropping the tree), the focused one marked, and what the reader says for what has focus): after the load, a moment after the reader spoke, on Refresh, after one of its keys, and every 1.5 s while the page is visible. Its keys send `key` messages (the app you see only).
- **Hardened like the event loop model**: every built-in it uses taken before the app runs (the DOM's getters and methods, `getComputedStyle`, the event constructors, `dispatchEvent`, `click`, the MutationObserver's, String's and RegExp's functions), records and lists without a prototype, arrays filled with `defineProperty`, only text posted. Patched `getAttribute`, `matches`, computed styles, `textContent`, `activeElement`, `focus`, `click`, `dispatchEvent`, the keyboard's events, a silenced MutationObserver, setters on the prototypes or String's functions change only what the app gets itself (`e2e/web-levels.spec.ts`, three browsers).

### What the model simplifies

As the git model does for git: the rules a level needs, exactly; the rest left out, and said so.

- **No redirects** (a CORS request that is redirected), **no Private Network Access**, **no partitioned cookies** (CHIPS). Chapters 1 to 3 have no cache, so `Vary: Origin` is advice there; chapter 4's caches read `Vary` (see "The cache model").
- **Caching** (chapter 4): no `stale-while-revalidate` or `stale-if-error` (a stale copy is revalidated or fetched anew, never served while it is), no `immutable` (Chrome only skips revalidating it on a reload, which the page here never does), no `Range`/206, no `HEAD` copies, no memory cache and no back/forward cache, no `Clear-Site-Data`, no purging the CDN by hand, no cache size limit beyond 100 copies, the sealed frame's own `location.origin` is `null` (a page can't build an address per origin from it), no cache partitioning by top-level site (only the page's own requests use the browser's cache: other sites' pages and the probes from other origins don't), one copy an address in the browser whatever the request's credentials mode, and a `Vary` mismatch in the browser is a miss (Chrome revalidates the copy instead). Another customer's browser keeps nothing between its requests. The CDN ignores a request's own `Cache-Control` (allowed by RFC 9111; a CDN may honour it) and keeps answers with `Set-Cookie` (many refuse to). No server sends `Date`, so an answer is as old as the time it arrived; `Age` counts in whole seconds. Express's ETag and 304 come only in a level with a cache (chapters 1 to 3 have none, as before; real Express sends one everywhere), and `app.set('etag', fn)` is refused (true, false, `'weak'` and `'strong'` are taken).
- **No preflight cache**: every preflighted request sends its own preflight (a real browser may reuse one for `Access-Control-Max-Age`, 5 s by default in Chrome).
- **`Range` is never safelisted** (the spec safelists a simple byte range).
- **Methods in Allow-Methods are compared as written**, as the Fetch spec says (a browser that still matches them case-insensitively would allow `delete` for `DELETE`; no level depends on it).
- **`*` in Allow-Headers never covers `Authorization`**, as the Fetch spec says; Chromium 158 lets it cover `Authorization` too when the request has no credentials. No level depends on it (1.4 is credentialed, where `*` is only a name).
- **Cookies** (since 0.4.2 a real jar, see "The cookie model"; chapter 1's single session cookie is gone): **no Public Suffix List** (a host's last label is its public suffix: `co.uk`, `github.io` would be wrong; every host here has a one-label suffix), **no cookie prefixes** (`__Secure-`, `__Host-`), **no partitioned cookies** (CHIPS) and **no third-party cookie blocking** (as if the user allowed them), no `Priority`, no IP addresses as hosts, no `localhost` exemption from Secure. **The clock stands still** during a load (`WEB_CLOCK`): a cookie that expires in a minute is still there a minute later; every cookie set in a load is "a moment ago" for Lax+POST, a seeded one as old as the level says. Garbage collection drops the cookies used longest ago (Chrome also prefers to drop non-Secure ones first).
- **Only `fetch`** from the page: `XMLHttpRequest`, images and forms are refused by the frame's policy as in Debugging. Other sites' images, forms and links are modelled (see "Other sites"), not run; a site's page is its actions, not a page that runs code. `mode: 'same-origin'` to another origin fails with Chrome's line; `no-cors` gets an opaque answer (status 0, empty body) and refuses a method that isn't simple.
- **No Fetch Metadata** (`Sec-Fetch-Site` and the rest are not sent, so a server can't check them here), and the Referer follows `strict-origin-when-cross-origin` (or `no-referrer` for a page that says so) only.
- **The network is instant and in order**: each exchange takes `WEB_DELAY_MS` (20 ms) plus server.js's own time; requests sent together are answered in the order server.js finishes them.
- **Storage** (chapter 3): Chrome's behaviour where it differs from WebIDL: an item named like an `Object.prototype` member (`toString`, `__proto__`) reads and lists as an item; an assignment to one of Storage.prototype's own members (`getItem = …`) makes an own property, and `length = …` changes nothing (a TypeError in strict code); the prototype can be set. Left out: Chrome's exact words for every TypeError. One tab, so sessionStorage is per origin of that tab and no `storage` event fires (it only fires in other tabs); no IndexedDB, Cache Storage or Storage Buckets; no storage partitioning by top-level site (as no partitioned cookies); the key order is the order keys were first set (Chrome's is its own); the quota counts every area alone (Chrome's per-origin total across kinds is not modelled). Each load starts from the level's items: a Reload is a new visit with what the browser kept, as with cookies, never what the last load wrote.
- **Tokens** (chapter 3): HS256 only, a string secret only (no key objects, no RS256 and the rest), object payloads only; `verify` checks no `audience`, `issuer`, `subject` or `jwtid` (`sign` writes them). `crypto.randomUUID()` in server.js is scripted: the same ids on every run, in a version 4 UUID's form (a real server's are random). `require` knows `express`, `jsonwebtoken`, `cookie-parser` (no signed cookies) and `crypto` (`randomUUID` only).
- **The real time is mostly out of reach** in a level with `time`: the page's and server.js's `Date`, `new Date().constructor.now()`, `Intl.DateTimeFormat`'s `format()` and `formatToParts()` without a date, and `performance.timeOrigin` (plus `performance.now()`) all tell the scripted time. Still real: `Temporal.Now` where a browser has it, and the pace of timers.
- **The clock moves only when a level says** (chapter 3, `{ later }`): it jumps, as across a laptop's sleep; timers in the page and in server.js run on real time and don't fire early. The page's and server.js's `Date` tell the scripted time only in a level whose `WebSpec` has `time` (chapters 1 and 2 keep the real one in server.js; their clock stands still). Two sign-ins in the same scripted second sign the same token unless it carries an id (`jwtid`: 3.4 and 3.5's do).
- **The event loop** (chapter 5): in the app you see, more than 1,024 units before the next model frame go on in the next real frame, whose style comes in between (a check run is never affected; no level comes near it). Chrome's order where the standard leaves it open: one task queue for timers, messages and taps (by the time each may run, then the order queued; Chrome may run a message before an earlier 0 ms timer, Firefox and Safari differ again; no level depends on it), a frame every 16 ms only when something needs painting (CSS animations alone don't ask for frames here), the frame at the first task boundary past it (no rendering opportunity is missed or skipped otherwise). A task takes no time but its 10 µs and the clock reads its code makes. The clamp is the standard's (more than five deep, 4 ms). A customer's tap is a click only (no pointerdown, mousedown, pointerup, mouseup), never trusted (`isTrusted` is false, an app could tell it from a real one), and toggles no checkbox and follows no label: no level needs it. ResizeObserver, IntersectionObserver, `transitionend`/`animationend`, image and fetch events, workers and `fetch` itself stay on the browser's real clock (the levels use none of them). A forced layout is a read after a MutationObserver record: a stylesheet changed through the CSSOM, an input's value or a font loading makes none; a forced style (a computed opacity or colour) is not counted at all. Scrolling by a fragment (`location.hash`) is not counted. Opacity is not part of a frame's items (a transition moves it); a watched element that keeps one has it beside them, read only by `faded`. Still on the real clock: `performance.mark()`, `measure()` and the timeline's entries, and the animations of the app you see. Top-level `await` in the page's script ends its synchronous part late for the panel's sync/microtask marks. A frame's snapshot needs the element to be displayed, visible and with a box; off screen still counts as painted.
- **Accessibility** (chapter 6): no shadow DOM (a shadow root's content is neither in the tree nor in the Tab order), no `aria-owns`, `aria-activedescendant`, `aria-busy` or `aria-relevant` (additions and text only), no native validity in the tree (only `aria-invalid`), a closed `<select>`'s options and a field's contents are not rows; inline SVG is an img when named, else left out (Chrome: graphics-document); a role's required states (`aria-checked` on a checkbox) default to false. The keyboard: no `keypress`, no arrow keys in radio groups, selects or sliders, no implicit form submission, no access keys; a check run's mouse `click` moves no focus (as in Safari). Focus: the browser's own never moves, so `:focus` and `:focus-visible` never match in the frame (a visible focus style isn't checked), and `autofocus` does nothing (Chrome ignores it in a cross-origin frame too); the starting point is lost when its element is removed (Chrome keeps the place); a removed focused element fires no `blur` (the standard's rule; Chrome fires one before the removal); the fixup runs at the next MutationObserver delivery, not the next rendering update. `showModal()` has no top layer or `::backdrop` and `:modal` doesn't match. Live regions: a region is live from the MutationObserver delivery after it appears, Chrome's from its next accessibility update (usually the next frame). An update is a frame (16 ms from the first change): what the page's timers write within it folds in (the same in the three engines, timers firing by their deadlines), a write more than about a frame later is a new update, which Chrome may still fold into the same one when its frame came late; a rewrite more than 60 ms after the last change (about 150 ms, which real readers do pick up) lands after the probe's look at Enter and is no answer to it. Known limits, not rules a level teaches. In Firefox the app you see, while it is out of sight (another tab on a phone), gets no computed style at all: the model then takes only the `hidden` attribute for not rendered (CSS that hides by a class shows once the app is in sight again; check runs are always in sight). The reader is one generic voice (name, role, value, states, description), not any real screen reader's words; browse mode (reading with the arrow keys) is not modelled.
- **The thief is a model of what a script or a copy can carry off**: it reads strings, not code paths (a token a page derives anew for every request would hide from it), tries a fixed set of placements (Bearer, a Cookie, a header the page sent, a query), and sends no body. A script on the page can also act as Lena while she is there (3.2): the goals check that with the page's own requests (`arrived`), not with the thief.

### The server (`server.js`)

`shared/levels/web/server.ts`. The level's API server is a file of the level, written like a small Node server with Express (`const express = require('express')`, `app.get('/menu', (req, res) => …)`), which the learner reads and fixes. It is learner code, so it runs where the app's code runs, never on Grindstone's page: in a **worker** inside the sealed frame (its opaque origin and Content-Security-Policy hold there too: no network, no storage, no parent).

- **The runtime** (`SERVER_RUNTIME_SOURCE`, tested on Node with this very source in `server.test.ts`): `express()` and `express.json()`; `app.get/post/put/patch/delete/options/head/all(path, …handlers)` with `:params` (a trailing slash optional), `app.use([path], …handlers)`, `next()`, `next(error)` and error handlers (four parameters); Express 5's own answers: an `OPTIONS` no route answers gets `200` with `Allow` (and `HEAD` beside `GET`) and no CORS headers, an unknown path its 404 page ("Cannot GET /x"), a thrown error or a rejected async handler a 500 with the error's message (headers set before it are kept, as Express's finalhandler does), a body `express.json()` can't read a 400; without `express.json()` (or for another content type) `req.body` stays undefined. This subset's `express.json()` takes no options (`type`, `limit`): given some, it says so in the Server panel and still reads `application/json` only, so a page that sends JSON as `text/plain` to dodge the preflight is still not understood (1.2). `req`: `method`, `url`, `path`, `query`, `params`, `headers` (lower case, repeated ones joined with `, `), `get(name)`, `body`, and with `cookie-parser` (since 0.4.3) `cookies` (each value URI-decoded, a `j:` value read as JSON, the first of a name wins) and an empty `signedCookies`. `res`: `status`, `set` (also an object, or an array for several values), `header`, `setHeader`, `append`, `get`, `removeHeader`, `vary`, `type`, `json`, `send`, `end`, `sendStatus`, and since 0.4.2 `cookie(name, value, options)` and `clearCookie(name, options)` (as Express 5 with the cookie module writes them: the value URI-encoded, `Path=/` unless given, `maxAge` in ms as `Max-Age` in seconds with `Expires` that far from the scripted clock, the attributes in the module's order, an unknown `sameSite` a TypeError; `clearCookie` expires it in 1970) and `redirect([status,] url)` (a Location; the browser here follows no redirect); `express.urlencoded()` reads a form's body (`application/x-www-form-urlencoded`) into `req.body`, a name given twice as a list; a header name that is no token, a value with anything but a tab, visible ASCII and Latin-1 (a line break, a ☕: Node's `ERR_INVALID_CHAR`, "Invalid character in header content"), more than 40 headers, a status outside 200–599 (also as `res.statusCode = 99`, where it is set: "Invalid status code: 99") or a body over 100,000 characters throw as Node or Express would (a 500 and an error in the Server panel naming the line); a second answer throws "Cannot set headers after they are sent to the client". Every answer logs an access line (`OPTIONS /orders 204`). Since 0.4.3 `require('jsonwebtoken')` (see "Tokens"), `require('cookie-parser')` and `require('crypto')` (a scripted `randomUUID`); each request carries the scripted moment it is answered at, which `res.cookie`'s Expires and the tokens' `iat` and `exp` count from, and in a level with `time` server.js's `Date` tells that time too (the prelude sets it). Since 0.4.4, in a level with a cache, `res.send` (and so `res.json` and `res.sendStatus`) gives a body **Express's ETag** (the `etag` package: `W/"` + the body's UTF-8 length in hex + `-` + the first 27 characters of its SHA-1 in base64 + `"`, an own SHA-1 checked against Node's crypto) unless the route set one, and answers a conditional `GET` or `HEAD` whose answer is 2xx with **304** when `req.fresh` (the `fresh` package: `If-None-Match` names the ETag, W/ or not, or `*`; else `If-Modified-Since` is not before `Last-Modified`; never when the request says `Cache-Control: no-cache`); a 204 or 304 loses `Content-Type` and its body, as Express 5's `res.send` does (also in chapters 1 to 3, where a 204 no longer carries a Content-Type). `res.end`, Express's 404 page, its error pages and its OPTIONS answer carry no ETag. Express's own OPTIONS answer is now its router's (since 0.4.4, all chapters): the methods sorted and joined with `, ` (`GET, HEAD`), `Content-Type: text/plain; charset=utf-8` and `X-Content-Type-Options: nosniff`. A copy from the disk cache sends nothing: no cookie, and the Network panel shows the headers that would have gone without the Cookie (Chrome's provisional headers). `app.set('etag', false | true | 'weak' | 'strong')`, `app.get('etag')`, `app.enable`/`disable`; `req.fresh`, `req.stale`.
- **The worker** runs the prelude (one line: the runtime, `require('express')`, the console sent to the Server panel, the message listener), a line break, then server.js as written, so server.js's line N is the worker's N + 1 and errors name server.js's own lines. An error at server.js's top level (an unknown module, a typo) is a **crash**, as Node would stop: every request then fails to connect. A promise rejected with nobody to catch it is reported in the Server panel ("Unhandled rejection: …", with its line); Node would stop, this server goes on. A syntax error never reaches the prelude: Chromium reports it on the Worker with its line, Firefox and WebKit say nothing to the frame, so the frame compiles server.js once more with `new Function` (never calling it) for the engine's own message and line.
- **The host in the frame** (`SERVER_HOST_SOURCE`, part of the web backend): makes the worker from a blob on the first request (with the Worker's own `postMessage` and `terminate`, taken before the app runs), reads what it posts field by field (the worker runs learner code: status 200–599, at most 40 headers whose values are tab, visible ASCII or Latin-1 only, each without spaces and tabs at its ends, a body cut at 100,000 characters, at most 300 lines for the Server panel, each cut at 500; an answer the page's `Response` still can't carry fails that fetch with "Failed to fetch", never the page), and runs the **watchdog** (`SERVER_LIMITS`): a request server.js has not answered in 1 s (a loop that never ends, a route that never sends an answer) fails (`net::ERR_EMPTY_RESPONSE`), the worker is stopped and a fresh one starts with the next request (server.js runs again from its top, its state with it), at most 3 times a load; then it stays down. The worker never gets the load's token (CoreHub #522 stays as narrow as it was).
- **Each load gets its own server**, the app you see and every check run alike, so a basket line removed in one load is back in the next.

### The web backend

`shared/levels/web/backend.ts`: `webConfig(spec, files, page)` (TypeScript: checks the level's `WebSpec` and makes plain data for the frame) and `WEB_BACKEND_SOURCE` (in the bridge, in place of Debugging's backend when the config has `web`; run on Node by `backend.test.ts` with the level's server.js in-process, `test/unit/levels/web/helpers.ts`). It has Debugging's backend interface (`fetch`, `pending`, `count`, `sent`) plus `read`, `arrived` and `from`.

- **`WebSpec`**: `api` (the API's origin, `https://api.cornerbakery.shop`; another origin than the page's, no path), `server?` (the file with its code; none: nothing answers there and there is no Server panel), `shop?` (the shop's own server: fixed answers per method and path, Debugging's answer data, with no CORS headers, on the page's origin and on `alsoOn` origins, `https://www.cornerbakery.shop`, `https://cornerbakery.shop:8443`: each another origin for the page), `session?` (`{ name, value }`, chapter 1: Lena's cookie at the API, now a seed: `name=value; Secure; HttpOnly` from `/login` 29 minutes before the page loaded, through the cookie model), and since 0.4.2 `cookies?` (more seeds: a URL, a Set-Cookie line, minutes ago), `sites?` (other sites, see "Other sites"), `scene?` (probe steps that act, `click`, `settle`, `wait`, `type`, `visit`, run in every load once the page is ready, before a check run's probes: Lena signs in, opens another site) and `application?` (the Application panel: the frame posts the jar after every change, `cookies` messages, at most every 50 ms), and since 0.4.3 `storage?` (Web Storage with these items, see "The storage model") and `time?` (the clock moves: `{ later }`; the page's and server.js's `Date` follow it; a scene's click then also waits until no request started or ended for 50 ms, so the clock never moves between an answer and the page's next request), and since 0.4.5 `loop?` (`{ watch }`: the page runs on the modelled event loop, see "The event loop model"; the elements each frame's snapshot looks at, by selector and name, with their text or not; such a level has no `server` and no Network or Server panel, its `api` only for the spec). `webConfig(spec, files, page, path, marker)` takes the page's path for document.cookie and the Referer, and (chapter 5) the fresh name the page's script calls when it is done (`loopMarker()`, made per load by `sandboxDocument`, which appends the call to the page's module script on its own line). An unknown host fails as `net::ERR_NAME_NOT_RESOLVED`.
- **A request**: built with the browser's own `Request` (so `fetch`'s own TypeErrors are the browser's), its headers through `requestHeaders`, the `Origin` and the cookie added; posted to the Network panel (`request`, `preflightFor: null`); when it needs one, the preflight first (its own `request` message with `preflightFor` the request's id, the same initiator; its answer as a `response`); a refused preflight stops it there ("POST … net::ERR_FAILED", the request's `response` with `failure: 'cors'`, no status, and the `reason`); else the request goes to server.js (or the shop's server), and the answer is checked: refused, the page gets `TypeError: Failed to fetch`, the Console Chrome's two lines, and the Network panel the status, headers and body the server sent with the reason. Readable: a real `Response` (`type` `cors`, only the exposed headers; `basic` on the page's own origin), whose `json()`/`text()`/… mark the request read for the `read` probe. A 4xx/5xx logs its browser line, as in Debugging.
- **`from(probe, then)`**: the same exchange as a page on another origin would make it (its own `Origin`; the cookies that origin's site context lets go), with nothing posted to the panels and nothing kept; the probes `fetchFrom` use it.
- **Cookies** (since 0.4.2): every request asks the jar for its cookies (only with credentials: `include`, `same-origin` to the page's own origin, a navigation always; never a preflight), its message lists each cookie of the URL's site sent or why not, and every answer's Set-Cookie lines go into the jar before the CORS check (a refused answer's cookie is kept, as Fetch stores it in "HTTP-network fetch"), each stored or why not (an answer to a request without credentials: "Not stored: …"). A same-origin answer shows the page every header but Set-Cookie. Requests carry a **Referer** (`strict-origin-when-cross-origin`: the page's address to its own origin, the origin alone to another). `visit(origin, then)` runs a site's actions (`sendAs`, the same rules, each request tagged with its site and kind, `site` and `destination` in the messages), `navigate`, `carried`, `leaked`, `readable` and `stolen` answer the chapter 2 probes, and `documentCookie()` / `writeCookie(value)` are the frame's document.cookie (the bridge defines it on the document before the app runs, not configurable). Since 0.4.3: `storage(proto)` (the page's two Storage objects, Storage.prototype getting the model's members), `date` (the scripted Date the bridge puts on the window), `quietFor()`, `later`, `copy`, `issued` and `replay` (see "The thief"); every page request remembers the headers its code set and, once read, the answer it could read. Since 0.4.4 (chapter 4) `WebSpec.cache` (`{ cdn?, seeds? }`: the browser's cache, a CDN in front of the API, and copies kept from before the load, `{ into: 'browser' | 'cdn', url, request?, by?, status?, headers, body, minutesAgo }`; a CDN seed only on the API) turns on the browser's cache in the page's `fetch` (the cache mode and Fetch's headers, a copy used without a request, a revalidation whose 304 freshens the copy and hands the page the copy as a 200, an unsafe request's answer taking the copy away), the CDN in front of server.js (`throughCdn`), Express's ETag in server.js, `cache` messages for the Application panel (both caches' copies with their age, lifetime, freshness, ETag, Cache-Control, who fetched them and their uses, and the CDN's log, at most every 50 ms) and the probes `fromCache`, `notModified`, `reached` and `other`. ## Level file format

Scenarios: one file per scenario in `shared/levels/<track>/NN-slug.ts`, exporting a `Scenario`. Practice tasks: grouped per chapter in `shared/levels/<track>/practice/<chapter>.ts`, each exporting a `PracticeTask`.

| Field | Content |
| --- | --- |
| `id` | a scenario `<track>-NN-slug` (`git-04-merge-conflict`), a practice task `<track>-practice-slug` (`git-practice-stage-one-file`); the URL is the id without the track |
| `track`, `kind`, `title` | `'git'` or `'debugging'`, `'scenario'` or `'practice'`, a short title |
| `difficulty`, `minutes` | 1-3; the time estimate (a practice task about 0.5) |
| `story` | scenario: 1-3 short paragraphs (joined with a blank line), second person, the situation and what to do |
| `task`, `practises`, `why` | practice task: the task in one or two sentences (one line); the id of its scenario; one line on why it works, shown once solved |
| `setup` | `() => S`, the environment's state; git: a `GitState` built with `repo()` / `folder()` from the git model; Debugging: `{ files, observed: null, picked: null }`, the files from `orderSite()` (`bakery.ts`) plus the level's own; must be deterministic |
| `sandbox`, `teaches` | Debugging only, see "The Debugging environment" |
| `pr`, `issues`, `tempting`, `verdict`, `reason`, `run`, `teaches` | Working with AI only, see "The review environment" |
| `goals` | `{ id, label, check({ state, history }) }`; `label` is one checklist line (`backticks` become code) |
| `teammates` | optional `{ id, author, trigger, apply, notice }`; `trigger` is `{ afterCommands: n }`, `{ beforeCommand: 'git push' }` or `{ when: state => boolean }` (right after the command that makes the check pass, e.g. your branch reached origin); `apply` usually calls `teammateCommit` or `teammateMerge` on origin |
| `hints` | a scenario: exactly three (nudge, concept, exact commands in backticks); a practice task: one |
| `debrief` | scenario: `{ title, paragraphs }`, 2-4 short paragraphs on why it works |
| `solution` | the steps that solve it (a practice task: 1-3), `SolutionStep = string \| { save: string }`: a terminal line, or saving the file git waits for in the editor with this text (`rebase -i`: the todo list, then the message); the tests replay them through `playStep` |

Goal helpers for git levels live in `shared/levels/git/checks.ts`: `conflictFullyResolved(state, rev)`, `treeOf`, `treeHasConflictMarkers`, `changedIn(state, rev)` (paths a commit changed against its first parent), `gitInvocations(history)` (every `git ...` command, also inside chains), `ran(history, command, matches?)` (a successful `git <command>` in the history), `hasFlag(args, short, long?)` (also bundled: `-am` has `-a`), `isBareForcePush`, `isLeasePush`, `isMergeOf(state, rev, first, second)` (a merge commit with exactly these parents), `ranAfter(history, command, after, matches?)` (e.g. a `git log` after the last `git merge`), `ranBefore(history, before, matches)` (a matching command before the first successful one of `before`, e.g. a look before the sync), `logRevisions(args)` (what a `git log` includes and excludes, as typed: `a..b`, `^a`), `logsOnlyOn(args, on, notOn)` (`git log origin/main..main` and its spellings) and `committedOn(state, id, branch)` (HEAD's reflog shows the commit made on that branch, also after the branch is deleted). `ignoreMatcher` from the git model checks a committed `.gitignore`.

Conventions:

- Goals check outcomes in the state, not the commands typed. Use `history` only when the *how* is the lesson (level 6: `--force-with-lease`, never a bare `--force`) or when the command changes nothing (`diff`, `log`: "You looked at both sides").
- A goal that is trivially true at the start is fine when it guards against a wrong path (e.g. "no merge commits", "dist/ and .env are still on your disk"), but it must be listed in the test's `initialGoals` table.
- Every scenario has at least one wrong path in the test's `wrongPaths` table (the obvious shortcut that must not solve it), and every practice task its obvious one.
- Conflict files are written in the solution with `echo ... >` and `echo ... >>` (chained with `&&`), since the editor panel is UI-only.
- A solution that needs a commit id computes it from the deterministic setup (1.4 Read the history, the todo lists of 4.4 and its practice task).
- Editor steps of `git rebase -i` are `{ save: text }` in the solution, one per file git opens: `['git rebase -i main', { save: 'reword 1a2b3c4 ...
fixup ...' }, { save: 'Add gift cards to the shop' }]`. In the app they are Start rebase and Save message; each counts as one command, like the line it replaces.

## Adding a level

1. Add a row for it to `initialGoals` in `test/unit/levels/git-levels.test.ts` (goal ids and their value at the start, in play order) and its wrong paths to `wrongPaths`: red.
2. Write the file (a scenario in `shared/levels/<track>/NN-slug.ts`, a practice task in `practice/<chapter>.ts` with `practises` set) and add it, in one line, to its chapter's `levels` in that track's `index.ts` (plus the import): a practice task right after its scenario. Its number (`3.3`, or none), its place in the play order, its row and lane on the track page and its commands follow from that.
3. `pnpm test`: the shared tests check shape (per kind), a deterministic setup, the start state, and that replaying `solution` solves the level exactly on its last line. `test/unit/levels/tracks.test.ts` pins the chapter of every level; add the new id there.
