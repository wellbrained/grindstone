# Levels

The shared level core (`shared/levels/`), its two environments, git (`shared/levels/git/`) and Debugging (`shared/levels/debugging/`), and their levels. Pure TypeScript: no Vue, DOM or Nuxt imports. Tests: `test/unit/levels/` (Debugging's in `test/unit/levels/debugging/`, plus `e2e/debugging-levels.spec.ts` in a real browser).

## Environments (ADR 0007, update 2026-11-13)

The core is track-agnostic: levels, goals, hints, debrief, practice tasks, sessions and their counts, teammate events, undo and reset, progress, tracks and chapters, Continue and next up, the skill radar. It is generic over an **environment**: the state a level runs on (`S`), what the history records per counted action (`R`) and one solution step (`Step`). Git is one environment, in its own place: the git model in `shared/git/`, the git environment in `shared/levels/git/` (`types.ts`, `engine.ts`, `commands.ts`, `checks.ts`, the levels).

- **The core never imports an environment**: `types.ts`, `engine.ts`, `progress.ts`, `track.ts`, `radar.ts`. Only the registry (`tracks.ts`) and the barrel (`index.ts`) bring the tracks together. `test/unit/levels/core.test.ts` checks those imports and plays a level of a tiny counter environment (not git) through the core: goals, events, hints, undo, reset, its best run by its own measure, progress.
- **Generic types**: `ScenarioOf<S, R, Step, T>`, `PracticeTaskOf`, `LevelOf`, `SessionOf<S, R>`, `Goal<S, R>`, `GoalContext<S, R>`, `TeammateEvent<S>`, `TeammateTrigger<S>`, `SessionSnapshot<S, R>`.
- **Registering an environment**: an environment adds its types to the core's `Environments` interface by declaration merging (Debugging: `debugging: { state, record, step, fields }`, where `fields` are what its levels add to the shared ones, `sandbox` and `teaches`; git adds none, so its types did not change) (`declare module '../types'` with `interface Environments { git: { state, record, step } }` in `shared/levels/git/types.ts`). `Level`, `Scenario`, `PracticeTask` and `Session` are the union over the registered environments (today git's alone, so they are exactly git's); `Level<'git'>` is one environment's (`GitLevel`, `GitScenario`, `GitPracticeTask`, `GitSession`). A level's `track` is its environment's id, so `isGitLevel(level)` (and later Debugging's guard) tells them apart.
- **Core functions** (`shared/levels/engine.ts`): `startSession(level)`, `act(session, level, { commands, execute, reload? })` (one counted action: snapshot, before-events, execute, record, after-events, goals; `commands` are what `beforeCommand` triggers match, `reload` also counts a reload), `undoLast(session, level)` (null when there is nothing to undo; returns the record it took back), `restart(session, level)` (a new attempt, hints kept), `takeHint(session, level)` (`{ session, number, total, text, revealed }`). They report data; the environment words it (git: `Undid: <line>`, `Hint 2/3: ...`).
- **The git environment** (`shared/levels/git/engine.ts`): `startLevel`, `submit` (trainer commands typed in the terminal, else a counted git/shell line), `saveFile`, `saveEditor`, `playStep`, `TRAINER_COMMANDS`; a line's commands for triggers come from the git tokenizer (`commandsIn`). `CommandRecord` (`{ line, exitCode }`), `SolutionStep` (a line or `{ save }`), `TerminalLine` and `SubmitResult` are git's types.
- **Best run per track**: `Track.bestRun` is a `RunMeasure`, the run counters in order; fewer wins, each later one breaks a tie. Git `fewestCommands` (`['commands', 'hints']`, the rule so far), Debugging `fewestHintsThenReloads` (`['hints', 'reloads']`). A track without one gets `fewestCommands`. `useProgress().record` passes the level's track's measure to `recordSolve`.
- **The play page** follows the same split (docs/features/ui.md, "Play page"): `usePlaySession` and `PlayFrame` are shared, `useGitPlay`, `GitPlay` and `GitWorkbench` are git's, `useDebuggingPlay` and `DebuggingPlay` Debugging's.
- **The core never imports Debugging either**: `core.test.ts` refuses `./git` and `./debugging` in the core files.

## Public API (`shared/levels/index.ts`)

## Engine rules

The core's rules, as the git environment uses them (a Debugging level runs through the same core with its own actions; there a reload also counts in `reloads`).

- **Pure and immutable**: every call returns a new session; a session is plain JSON (the UI may store it as is).
- **Output** is `TerminalLine[]`: git's `OutputLine`s plus two markers the UI interprets, `{ kind: 'clear' }` and `{ kind: 'edit', path }` (open the editor panel).
- **Trainer commands** are handled before git and are not counted, recorded or undoable. Matched on the trimmed line, any case:
  - `undo`: restores the previous snapshot (git state, history, fired events). Prints `Undid: <line>`, or `Nothing to undo.`
  - `reset`: back to the setup as a new attempt (history, undo stack, events, `solved` and `commandCount` cleared). Revealed hints stay revealed and counted.
  - `hint`: reveals the next hint (`Hint n/3: ...`, `Hint 1/1: ...` for a practice task, kind `hint`) and counts it; after the last it repeats it.
  - `help`: lists trainer, git and shell commands.
  - `clear`: returns the clear marker. `edit <file>`: returns the edit marker (`usage: edit <file>` otherwise).
- **Empty line**: no-op.
- **Counted commands** (anything else, and `saveFile`), in this order:
  1. Snapshot for undo (oldest dropped beyond 200).
  2. `beforeCommand` events fire if any command in the line (split at `&&` and `;`, whitespace collapsed, redirect targets ignored) equals the prefix or starts with it plus a space. `git push` matches `git   push -u origin x` and `git add . && git push`, not `git pushy` or `echo "git push"`.
  3. The line runs (`run` from the git model).
  4. It is recorded in `history` as `{ line, exitCode }` and `commandCount` goes up.
  5. `afterCommands: N` events fire once the history (the current timeline) has N entries, `when` events once their check passes on the new state.
  6. Goals are recomputed; `solvedNow` is true on the first transition to all goals met. `solved` then stays true for the attempt and the session stays playable.
- **Events** fire once per timeline: `firedEvents` is part of the snapshot, so an undo that rewinds past an event lets it fire again. Each firing returns a `Notice` (`{ eventId, author, text }`).
- **Counts**: `history` is the current timeline (undo shortens it); `commandCount` is the effort of the attempt and includes undone commands. Progress uses `commandCount`.

## Tracks and chapters

`shared/levels/track.ts` (types and helpers) and `shared/levels/tracks.ts` (the registry). Play order, chapter numbers and scenario numbers are derived from the chapter lists, never written by hand.

- **Track**: `{ id, title, scope (one line), tagline (one line for its home card, may be empty), description (the home card's pitch), status: 'live' | 'coming', cheatSheet (its path, or null), bestRun (its run measure, see Environments), chapters }`. Everything the home page, the nav and the track page show about a track comes from here, so a new live track needs data only. `tracks` lists them in home page order: Git and Debugging (live), then Working with AI, Web fundamentals, Framework deep dives (coming: no chapters, no levels, not playable; the tests pin coming tracks to no chapters). Debugging has seven chapters (ADR 0007), all live since 0.2.14, with a cheat sheet since 0.2.15 (`/debugging/cheat-sheet`): 1 Reading errors, 2 Network, 3 Elements & CSS, 4 State & async, 5 Breakpoints & stepping, 6 Performance, 7 Incidents. Colours: slot = chapter number - 1. `defineTrack` numbers the chapters and throws for a level of another track, a level listed twice, a coming track with levels, or a practice task that does not follow its scenario.
- **Chapter**: `{ id (unique in its track, also the section anchor: /git#merging), trackId, number, title, description (one line), colour (a slot of the branch palette, 0-7), levels }`. `levels` is the play order: each scenario followed by its practice tasks. A chapter without levels is *coming*: shown with its description only.
- **Git chapters**: 1 Basics (5 scenarios, 6 practice tasks), 2 Branching (5 scenarios, 6 practice tasks), 3 Merging (5 scenarios, 5 practice tasks), 4 Rewriting history (4 scenarios, 4 practice tasks), 5 Teamwork & remotes (5 scenarios, 5 practice tasks), 6 Undo & recovery (5 scenarios, 7 practice tasks), 7 Disasters (5 scenarios, 6 practice tasks), 8 Workflows (5 scenarios, 7 practice tasks). No git chapter is coming any more. Colours: slot = chapter number - 1; slot 7 exists only for chapters, so branch colours in the graph did not move.
- **Numbers**: a scenario is `chapter.position` counting scenarios only, e.g. `1.2` for Stage only what belongs together, `3.3` for Merge conflict (`levelNumber`, `LevelPlace.number`). A practice task has no number (`number: null`); `LevelPlace.scenario` names its scenario and that scenario's number. `placeName(place)` is the text form: "3.3 Merge conflict", or the title alone for a practice task. The ids and URLs (`git-04-merge-conflict`, `/git/04-merge-conflict`, `/git/practice-stage-one-file`) never change when a level moves or gets renumbered.
- **Counting both kinds**: "n of N solved" for a chapter and a track, **next up** and **Continue** count scenarios and practice tasks alike: a practice task is a level you solve like any other, so leaving one out would make the counts lie.
- **Next up**: the first unsolved entry in play order (`nextUp`), a scenario or a practice task. **Continue** (`continueTarget`, `{ place, reason, at }`): the entry you last played while it is unsolved (`reason: 'resume'`, with the time), else next up (`'next'`); once nothing in the track is unsolved, the first entry flagged "practise again" in play order (`'practise'`); null when everything is solved and nothing is flagged. `practiseAgainIn(chapter, progress)` is the chapter menu's "Practise again". `trackToContinue` picks the track for the home page: the live track of the last played entry, else the first live track with a solve.

## Two kinds: scenarios and practice tasks

ADR 0006 (`docs/adr/0006-git-v1-practice-and-progress.md`). `Level = Scenario | PracticeTask`, told apart by `kind`.

- **Scenario** (`kind: 'scenario'`): a story, goals, three hints, a debrief. Numbered.
- **Practice task** (`kind: 'practice'`, "Practice" in the UI, never "drill"): one short task of 1-3 commands, about 30 seconds, one goal (a few at most, ADR 0006), one hint, a one-line `why` shown once solved, "Next" and "Again" instead of a debrief. No number.
- **Where a practice task belongs**: it names its scenario in `practises` *and* is listed in the chapter right after that scenario (after the scenario's other practice tasks). The level file says what it trains; the chapter list stays the one place for the order; `defineTrack` checks that both agree, so a moved line fails at start-up instead of drawing a practice task under the wrong scenario. `nextLevel` therefore goes scenario, its practice tasks, next scenario.
- **Difficulty** (`1 | 2 | 3`, drawn as filled dots) and **minutes** (an estimate; a practice task about `0.5`, shown as "~30 s") on every entry.

## Writing levels

The rules are in ADR 0006, "Writing levels"; in short:

- Precise and clear: compact, but never leave out what the learner needs (a file name, a branch name, how many commits). If a goal checks it, the story or task says it.
- File contents and code comments read like a real project other people work on: the Corner Bakery website (the habit tracker only in Basics 1.1's practice tasks), comments that say why ("Agreed with the shop team: orders from 50 euros ship for free"), teammates by name.
- Friendly and personal: we are their friends who help and teach. Second person, no blame, the debrief explains *why*.
- Fictional people and teams only (Maya, Jonas, Ben; a bakery), never real companies; fake keys only (`test-key-not-real-0000`).

## Progress

`shared/levels/progress.ts`, tests in `test/unit/levels/progress.test.ts`.

```ts
Progress = { version: 3, levels: { [id]: LevelProgress } }
LevelProgress = {
  solved: boolean,            // stays true once solved; only a reset clears it
  best: Run | null,           // by the track's measure (git: fewest commands, ties broken by fewest hints)
  latest: Run | null,         // the most recent solve
  practiseAgain: boolean,     // "solved, but I don't own it yet"; only a solved entry can carry it; a new solve clears it
  lastPlayed: number | null,  // ms since epoch, when you last typed a command in it
  fewestHints: number | null  // the fewest hints any solve revealed (for the skill radar); only goes down; null unsolved
}
Run = { commands: number, hints: number, reloads?: number }  // reloads: Debugging only; git runs never have it
```

- `recordSolve(progress, id, session, measure = fewestCommands)` stores the run (`runOf(session)`: `commands` = counted actions of the attempt, `hints`, and `reloads` when the session counted any) as `latest` and, when it is better by the track's measure (`isBetterRun(run, than, measure)`), as `best`, and lowers `fewestHints` when the run used fewer hints; replaying never removes `solved` or the flag. `fewestHints` is kept apart from `best` because the best run is chosen by commands first: a short solve with every hint can become the best run after a longer clean one, and the radar must still count the clean one. An unsolved session changes nothing. `recordPlay` sets the entry's `lastPlayed` (the play page calls it for every line typed and every editor save); `lastPlayed(progress)` is the newest one, for Continue.
- `setPractiseAgain(progress, id, flag)`; `resetEntries(progress, ids)` drops entries completely (solved, runs, flag, last played): an entry, a chapter, a track or everything.
- `readProgress(text)` is strict: broken JSON (`json`), not an object with `levels` (`shape`) or an unknown version (`version`) is an error, so the backup upload can say why and change nothing. Inside valid data a malformed entry (no boolean `solved`) is dropped and a broken field falls back to its blank value (a broken run to null, a non-boolean flag to false, a flag on an unsolved entry to false); an unsolved entry is kept only while it has a `lastPlayed`. A `lastPlayed` more than a day ahead of now (`MAX_FUTURE_MS`; `readProgress(text, now)`) is made up and becomes null. `levels` is built without a prototype and `__proto__` is skipped; every lookup by id goes through `entryOf` (own entries only). Ids this version does not know are kept stored (forward compatibility) but never win Continue: `lastPlayed(progress, isKnown)` skips them and `continueTarget` / `trackToContinue` pass the ids of their track(s). `parseProgress(text)` wraps it for storage: anything unreadable is empty progress.
- **`fewestHints` in version 3** (added in 0.2.5, no version bump): data from before has no such field, so `readEntry` takes the fewest hints of the stored best and latest run; a stored value is kept but never above what the runs show; a broken value falls back to the runs; an unsolved entry has none. It needs no level data, so it is exact wherever progress is read (storage, backup upload). Why not version 4: the field is additive and derivable from version 3 data, so backup files stay readable both ways (0.2.4 reads a 0.2.5 file and ignores the field; a version 4 file would be refused there as an unknown version). What 0.2.4 data cannot tell: a clean solve that was neither the best nor the latest run; such an entry counts half until a clean replay.
- **`reloads` in version 3** (added in 0.2.7, no version bump): an optional count in a run, read when it is a count and left out otherwise. Git runs never have it, so their stored form did not change and a 0.2.6 file reads and writes back byte for byte (`core.test.ts`); 0.2.6 reading a newer file keeps each run's commands and hints and ignores the field. A missing `reloads` compares as 0.
- **Migration on read**: version 1 and 2 entries `{ solved, hintsUsed, commands, bestCommands }` become `latest: { commands, hints: hintsUsed }` and `best: { commands: bestCommands, hints: hintsUsed }` (the hints of the old best run were never stored, so it takes the latest run's hints); `fewestHints` is the old `hintsUsed`; unsolved old entries are dropped; version 2's `lastPlayed: { levelId, at }` moves onto that entry (creating an unsolved one if needed).
- Storage is the UI's adapter (`grindstone:progress` in localStorage); the backup file is the same JSON (`serializeProgress`).

## Skill radar

`shared/levels/radar.ts`, tests in `test/unit/levels/radar.test.ts`; ADR 0007. One radar per track, an axis per chapter in chapter order: `trackRadar(track, progress)` returns `RadarAxis { chapter, value, total, solved, share, coming }`.

- **Credit per level** (`levelCredit`), scenarios and practice tasks alike: 1 once a solve did without the level's last hint (`fewestHints < level.hints.length`: fewer than 3 for a scenario, 0 for a practice task), 0.5 while every solve revealed it (also a solved entry without `fewestHints`, which only broken data has), 0 unsolved. Playing without solving counts nothing.
- **Axis value** = the sum of its levels' credits; `share` = value / the chapter's level count. Replays can raise it, nothing lowers it (`fewestHints` only goes down). A reset drops the entries and their credit with them.
- **Coming chapter** (no levels): `coming: true`, value, total and share 0; drawn dashed.
- `isRadarEmpty(axes)`: nothing solved in the track (the picture shows its outline only). `radarGain(before, after, chapterId)`: the chapter's old and new value, null when it did not change (the debrief's line). `formatCredit(value)`: `4.5`, `5` (never `5.0`).
- How it is drawn: `docs/features/ui.md`, "Skill radar".

## The Debugging environment

ADR 0007; `shared/levels/debugging/`. A level is a small real app (index.html, one stylesheet, plain JavaScript ES modules) set in Corner Bakery's ordering site, run by the browser in a sealed iframe (how: docs/features/ui.md, "Sandbox and bridge"). The environment itself stays pure: the browser runs the app, and what it saw comes back as data, over a port only the bridge holds (since 0.3.1; the app's own code can't post a result, `done`, or anything else the page reads, and the probes read the page with the browser's functions taken before the app ran: docs/features/ui.md, "Sandbox and bridge").

- **State** (`DebugState`): `files` (the app's files as saved, by path; a reload runs these), `observed` (what the check run of the last reload saw, an `Observation`; null before the first reload), `picked` (find tasks: the line you clicked last, or in chapter 7 the deploy you named, `{ deploy }`), `checked` (the files the last reload ran; absent before it; colleague events read it).
- **Counted actions** (`DebugRecord`): `saveDebugFile` (the editor's Save; only files the app has), `reload(session, level, observation)` (counted, and also in `reloads`), `pickLine` (find tasks: a click on a line in the editor or a frame in a trace; returns a `PickVerdict`, right or why not), and in chapter 7 `rollback(session, level, deployId)` (a deploy's files become the saved files; nothing for an unknown deploy) and `pickDeploy` (a find task whose answer may be a deploy; `deployVerdict`). The run's measure is the track's: fewest hints, then fewest reloads. Saves, rollbacks and clicks count as actions but not as reloads.
- **Goals read only what the app did** (`checks.ts`), never the code's text, so any working fix counts: `probeGoal(id, label, probe, expected)` (a probe read exactly this after the last reload, in a check run that finished: one that hung proves nothing), `probesGoal(id, label, { probe: expected, … }, { clean? })` (several probes in one goal, so a guard such as "the message still shows" never passes on its own at the start; an expected value is exact, or a bound on a number, `{ atMost: 1 }` / `{ atLeast: 5 }` (`meets`; chapter 6: "at most 1 request"); `clean`: and no error in the check run either, so a fix that leaves an uncaught `AbortError` behind does not count, 4.2), `probeAtLeast(id, label, probe, min)` (a number, e.g. a contrast ratio), `noErrorsGoal()` (the check run finished, through loading and every probe, with no uncaught error, unhandled rejection or `console.error`), `foundGoal(label, target)` (find tasks). Goals change only on a reload (or a click): a Save keeps what the last reload saw.
- **Probes** (`SandboxSpec.probes`): scripted looks at the app that run in the check run once it has loaded, in order, on the same page: `{ click: selector, times?, settle? }` (like a customer; `times: 2` clicks twice back to back, a double click; then the app gets 20 ms to react, and with a backend until every request it sent is answered, at most 3 s; `settle: false` goes on after the 20 ms while the answers are on their way, a customer who clicks on), `{ type: selector, value }` (typing: the field's value becomes `value`, then an `input` and a `change` event, then 20 ms; answers are not waited for), `{ wait: ms }` (a customer's pause, at most `MAX_PROBE_WAIT_MS`, 2 s; nothing is waited for), `{ settle: true }` (until every request is answered, at most 3 s, then 20 ms: what the customer sees once the page is quiet; chapter 4's races are `type`, `wait`, `type`, `wait`, `settle`, then a read), `{ text: selector }` (whitespace collapsed), `{ count: selector }`, and with a backend `{ requests: 'POST /api/orders' }` (how many requests went there: a path on the shop, or a whole URL; the query does not count) and `{ sent: 'POST /api/orders', json?: 'items.0.quantity' }` (the last body sent there, or the JSON value at that path; null when there is none; a number stays a number, so `3` and `"3"` differ). **Layout probes** (chapter 3), from the browser's own layout: `{ tap: selector }` (a tap where a finger would: at the element's centre, scrolled into view vertically, on whatever is on top there, so a covering element gets it), `{ style: selector, property }` (a computed value: `'none'`, `'rgb(122, 62, 18)'`), `{ visible: selector }` (`'visible'`, or why not: `'display: none'` (also `'display: none on section.basket'`), `'visibility: hidden'`, `'opacity: 0'`, `'no size'`, `'off screen'`: its centre is outside the page's width or above it), `{ hit: selector }` (what a tap at its centre lands on: `'itself'` (it or something inside it), else the element on top, `'div.toast-area'`; `'no box'`, `'off screen'`, `'nothing'`), `{ overflows: selector }` (`'overflows'` when it is wider inside than its box, else `'fits'`; `html`: the page scrolls sideways), `{ contrast: selector }` (its text colour against the backgrounds behind it over a white page, WCAG's ratio, two decimals; colours the browser computes as `rgb()`/`rgba()`, background images ignored). **Typing like a customer** (chapter 6): `{ keys: selector, value, gap? }` (letter by letter: per letter a `keydown`, the letter added with an `input` event unless the keydown was prevented, a `keyup`, then `gap` ms, 80 by default; no `change`, never the focus) and `{ press: selector, key }` (a `keydown` and a `keyup`; Enter in an `<input>` also commits it with a `change`, as in the browser; no form is submitted, the sealed frame has none). **Performance probes** (chapter 6, levels with `sandbox.performance`; see "The profile" below): `{ changes: selector }` (how many nodes of the page the app changed inside the first element that matches since this probe started: elements and non-blank texts added or removed, one per attribute or text set; Built by `observe(messages)` from the messages that came over the check run's own port (`bridgeLink`): the bridge's alone.
- **Solutions** (`DebugStep`): `{ save: path, replace: [from, to] }` (the file with the first occurrence replaced; `editedText` throws when the text is not there), `'reload'` (the check run on the saved files), `{ pick: path, line }`, and in chapter 7 `{ rollback: deployId }` and `{ pickDeploy: deployId }`. `playSolution(level, run)` replays them; `run` is the check (a real browser in `e2e/debugging-levels.spec.ts`, the table of `test/unit/levels/debugging/expected.ts` in the unit tests).

### The fake backend

ADR 0007, update 2026-11-13 (chapter 2); `shared/levels/debugging/backend.ts`, tests in `test/unit/levels/debugging/backend.test.ts`. A level declares its server in `sandbox.backend`; the bridge answers the app's `fetch` with it inside the sealed frame, for the app you see and for every check run, each load with a fresh one (a sequence starts over). Nothing leaves the frame: its Content-Security-Policy still refuses every request (`connect-src 'none'`), and anything that is not `fetch` (an image, `XMLHttpRequest`) is refused as before.

- **Routes** (`BackendRoute`): `{ method? (GET), path, query?, body?, respond }`. `path` is `/api/menu` on the shop's own address (`https://cornerbakery.shop`) or a whole URL on another origin; routing ignores the query unless the route has a `query` pattern (below). `body` is a regular expression's source: only requests whose body matches take the route (2.3's server reads `"quantity":3` differently from `"quantity":"3"` and from a missing field), else the next route for the address does. `query` is one too, tested on the query as sent without `?` (`q=cro`): 4.2's search answers `^q=cro$` slowly and `^q=croi` fast, so the answer and its delay depend on the request and a race is the same on every run. `respond` is one answer or a list answered call by call, whose last answer repeats (2.2: a `500`, then a `201`).
- **Answers** (`BackendAnswer`): `{ status, json? | text?, headers?, delay? }` or `{ fail: 'network', delay? }`. The status must be one in `STATUS_TEXT` (its reason phrase becomes `statusText`), `json` sets `content-type: application/json; charset=utf-8` (`text`: `text/plain`), the level's headers win; `delay` defaults to 30 ms (`DEFAULT_DELAY_MS`), at most 3 s. `backendConfig` checks all this (the level tests run it on every level) and hands the frame plain data.
- **What the app gets**: a real `Response` (`ok`, `status`, `statusText`, `headers`, `json()`, `text()`, `url`, `type` `basic` or `cors`) after the delay; `fetch` rejects only as the browser would: `TypeError: Failed to fetch` (made where `fetch` was called, so its trace points at the app's line) for a failed connection or a CORS refusal, `fetch`'s own `TypeError` for a request it refuses (a body on a GET, an address it can't parse), the signal's `AbortError` when aborted. An unknown path on the shop answers `404` with the server's HTML error page (Express's "Cannot GET /api/products"), so `response.json()` fails the way it does for real ("Unexpected token '<'"); an unknown host fails to connect (`net::ERR_NAME_NOT_RESOLVED`).
- **CORS, like the browser**: a request to another origin is refused unless its answer has `Access-Control-Allow-Origin` with `*` or the shop's origin. A request that needs a preflight (a method other than GET, HEAD, POST, or a header that is not safelisted, e.g. `Content-Type: application/json`) also needs `Access-Control-Allow-Methods` / `-Headers` (the route's answer stands in for the preflight's). `mode: 'no-cors'` gets an opaque answer (status 0, empty body). The Console gets Chrome's lines: "Access to fetch at '…' from origin 'https://cornerbakery.shop' has been blocked by CORS policy: …" (the reason, as Chrome words it), then `GET … net::ERR_FAILED 200 (OK)` (without the status after a refused preflight).
- **The browser's own lines** (`netlog` messages): a 4xx or 5xx answer logs `GET https://cornerbakery.shop/api/products 404 (Not Found)`, a failed connection `GET … net::ERR_CONNECTION_REFUSED`; each links the line that sent the request. They count as errors for "No errors in the Console", which is why a level whose server keeps failing on purpose (2.2) has no such goal.
- **For the Network panel** the backend posts each request when it is sent (`request`: method, URL, headers as the browser sets them, the body as text, the call stack) and its answer when it arrives (`response`: status, headers, body, `failure` `cors` / `network` / `aborted`, the time); a CORS refusal shows the status the server sent but no body. A body that is not text shows as `(binary, n bytes)`, form data as `name=value&…`, an object as `[object Object]` (what the browser sends).
- **For probes** it counts requests by address (`count`) and keeps the last body sent there (`sent`). That record lives in an object without a prototype and is written and read only with built-ins the backend took when it was made (before the app's code ran; the URL's own getters, string methods, `JSON.parse`, and a JSON writer of its own that asks nothing for a `toJSON`), so a built-in the app replaced can't change what those probes read. The routes come as data without prototypes too (the bridge's copy of its config): an `Access-Control-Allow-Origin` the app puts on `Object.prototype` is no header of the server's.

### The Elements panel

ADR 0007, update 2026-11-13 (chapter 3); `shared/levels/debugging/css.ts`, `elements.ts` and `inspector.ts`, tests in `test/unit/levels/debugging/css.test.ts`, `elements.test.ts`, `messages.test.ts` and `e2e/debugging-elements.spec.ts`. A level with `sandbox.elements` gets the panel (how it looks: docs/features/ui.md, "Elements"). The work is split so the cascade is pure and tested: **the browser says what matches, Grindstone works out the rest from the level's own CSS**.

- **The page's rules** (`css.ts`): `styleSheets(files)` lists the stylesheets in document order as the browser applies them (each `<link rel="stylesheet">` to a level file except a `disabled` one, each `<style>` block of index.html from the line it starts on; nothing inside `<!-- -->`; a `media` attribute becomes a condition of every rule of that sheet, linked to its line in index.html), `parseCss` reads each into `CssRule { path, line, selector, selectors, conditions, declarations }` (the line of the selector and of every declaration, the `@media` / `@supports` conditions around it with their lines), `cssRules(files)` all of them in cascade order (at most `MAX_CSS_RULES`, 2000). Forgiving like the browser: comments, strings, `!important`, custom properties with blocks; other at-rules (`@keyframes`, `@font-face`, `@layer`, `@container`) and nested rules are skipped; broken text never throws. It runs on the page's main thread twice per load, so it is linear in the text (no per-character trims or backtracking regexes), reads at most `MAX_CSS_LENGTH` (300,000 characters) of a sheet and follows `@media` / `@supports` and `:is(…)`-like selectors `MAX_CSS_NESTING` (32) deep; `css.test.ts` times hostile inputs (100 KB of whitespace, 200 KB without a `{`, 40,000 spaces before `!important`, 5000 nested `@media` and `:is(`, thousands of unclosed tags). `specificity(selector)` (ids, classes, types; `:is`/`:not`/`:has` take their most specific argument, `:where` counts nothing, `:nth-child(… of S)` adds S, legacy `:before`), `longhandsOf` (what a shorthand sets: `margin`, `background`, `border`, `font`, `flex`, `overflow`, `inset` …), `isInherited` (`color`, `font*`, `visibility`, `pointer-events`, `white-space`, custom properties …).
- **What the bridge gets** (`sandboxDocument(files, { elements: true })`, the app you see only, never a check run): the rules' selectors, conditions and declarations, the linked stylesheets' names (their `href` is a data URL in the frame) and the computed properties to read (`COMPUTED_PROPERTIES`: display, visibility, opacity, position, z-index, pointer-events, color, background-color, width, height, min-width, overflow, text-overflow, white-space).
- **The inspector in the frame** (`INSPECTOR_SOURCE`, part of the bridge, plain JavaScript in a string): a **snapshot** of the DOM (`dom`: elements in document order with their parent, tag, at most 12 attributes cut at 120 characters, their own text cut at 80, `shown` (it has a box) and `overflows` (wider inside than its box); at most `MAX_DOM_NODES`, 600; what Grindstone put on the page is left out, a stylesheet's data URL shows as its file, a module script as its `src`) after each load and on request (Refresh, a pick); **inspect** (`inspected`: for the element and each ancestor up to `<html>`, which rules match through which selectors (`matchMedia` / `CSS.supports` for their conditions, `element.matches` per selector), its style attribute; the declarations `CSS.supports` refuses; the box (content size, padding, border, margin); the computed values; scroll and client sizes); **highlight** (DevTools' four boxes and a label, in a closed shadow root on top of everything, `pointer-events: none`, following scrolls); **pick mode** (`hovered` while the pointer moves, `picked` after a fresh snapshot on the click, `pickEnd` on Escape; the click and the presses around it never reach the app).
- **The cascade** (`elementStyles(rules, inspected)`): the style attribute first (`element.style`), then the matching rules from the most specific and latest; each declaration `active`, `overridden` (it wins for nothing it sets: by !important, the style attribute, specificity, order, a later declaration in the same rule; a shorthand only when everything it sets lost) or `invalid` (the browser refuses it); `missing` lists the `var(--x)` without a fallback that nothing on the element or above it defines. **Inherited**: each ancestor with inherited declarations (only those), nearest first; struck through when something nearer sets it.
- **The tree** (`treeRows(nodes, expanded)`, `startExpanded` (`<html>`, `<body>` and what is in it open, the head closed), `treeMove` (WAI-ARIA tree keys), `withAncestors`, and `nodePath` / `nodeAtPath` to find the selected element again in the next snapshot, also after a reload), `nodeLabel` (`button#order.order`), `boxNumber` (a dash for 0).
- **Messages** (`readBridgeMessage`): `dom`, `inspected`, `hovered`, `picked`, `pickEnd`, each plain data with caps (a snapshot over 600 elements is cut and marked `truncated`; tags, attribute names and numbers checked; a malformed one is dropped whole). The page asks with `dom`, `inspect` (with a `seq`), `highlight` and `pick`, which the bridge takes only over the page's port (like Console input).

### The recording

ADR 0007, update 2026-11-13 (chapter 5); `shared/levels/debugging/instrument.ts`, `recorder.ts`, `recording.ts` and `condition.ts`, tests in `test/unit/levels/debugging/instrument.test.ts`, `recording.test.ts`, `condition.test.ts`, and in a browser `e2e/debugging-breakpoints.spec.ts`, `e2e/debugging-instrumented.spec.ts` and `e2e/debugging-levels.spec.ts`. A level with `sandbox.debugger` gets the Debugger (how it looks: docs/features/ui.md, "Debugger"). Nothing is paused: Record reloads the app you see with its code **instrumented**, the run is recorded step by step, and the panel moves through what already happened. The check runs (the goals) never run instrumented code, and no other level ever does.

- **Instrumentation** (`instrumentFiles(files)`, loaded lazily with acorn, its own chunk): every JavaScript file is parsed with acorn (ES latest, modules) and only has text inserted, never a line break, so every line, stack trace, Console link and find answer stays where it was. Before each statement a step call (`__gs$.on&&__gs$.s(point, call, [()=>a, ()=>b, …])`: the point's number, the running call's token and a reader per variable it can see); a loop's test gets one every round; a braceless body gets braces; a function body a `try`/`finally` that tells the recorder the call started and ended; `await x` and `yield x` become `__gs$.r(call, await __gs$.w(call, x))` (the call is paused, then back); an arrow's expression body becomes a block that returns it; a module's top level is a call of its own ("(anonymous)", like Chrome), its first call after a hashbang (at the start of line 2). A `for` statement whose test starts on its line is marked `testFollows` (a breakpoint stops at the test, see Stepping). What each point can see is worked out from the syntax tree: block scopes (let, const, class, a loop's variables, catch), the function's own (parameters, `var`, function declarations, `this` but not in an arrow), each enclosing function's (Closure) and the module's (imports and top-level names), innermost first, a shadowed name only once, at most `MAX_SCOPE_NAMES` (64). The **points** (file, line, column, function, scopes) and **functions** (name as JavaScript infers it: a declaration, `const f = () =>`, a method, `get total`) stay on the page; the frame only posts numbers and values. A file is left as written (and runs without steps, the Debugger says why) when acorn can't read it (a syntax error, which then fails in the browser as before), it is over `MAX_INSTRUMENT_SOURCE` (100,000 characters), nests over 400 levels (acorn's own "Not enough stack space" too), uses the name `__gs$`, the app passes `MAX_POINTS` (5000) statements, or a body the `try` would break (`clash`: in a block a function's own function declarations are lexical, so a `var` of the same name anywhere in that body, or a function declared twice in it, would become a SyntaxError). Linear; never throws. `withoutInstrumentation(text)` gives code back as written (exact for whole files: the tests round-trip every level's files; its lexer tells a regex literal from division by what comes before the `/`, so `/[)]/` or `/}/` stay as they are; linear on hostile text): Firefox and Safari quote code in some error messages (`(In 'slots.map(…)')`), and the Console shows those through it during a recording.
- **The recorder** (`RECORDER_SOURCE`, part of the bridge, run only in a recorded load as the global `__gs$`, set up before any module runs): a call stack from the calls it is told about (a call starts, ends, waits, is back; after the code that runs now has finished, a microtask clears it, which also catches a module's top level and a call that threw past an `await`), a call back from an `await` keeps the frames that started it as **async** frames. At each step it reads each variable (a reader that throws is a variable in its temporal dead zone: `<uninitialized>`) and keeps it as plain data (`RecordedValue`): strings cut at 200 characters (with their full length), objects `maxDepth` (3) levels below the variable and `maxEntries` (40) properties or `maxItems` (50) items wide, with an id per object and a cycle as a reference; a getter is never called (`(...)`), functions (`ƒ applyDiscount(total)`), elements (`button.add`), errors, dates, regexps and promises are one line; at most `maxNodes` (400) values opened per step. Only built-ins captured before the app ran are used. A Proxy can't be told from its target, so its traps run while it is read (`getPrototypeOf` for each `instanceof`, `ownKeys`, `getOwnPropertyDescriptor` per property; a trap that throws ends that value's entries): a known limit (ADR 0007). It posts the steps in batches (`steps`, 100 at a time or after 50 ms, never a message per step) and stops on its own (`recordEnd`) after `maxSteps` (2000: "the most it keeps") or once reading values has taken `maxMs` (3 s in all: "too slow"), or on the page's Stop (`recordStop`, over the page's port only); the app runs on (the inserted calls are a property check once it stopped).
- **Reading steps** (`readSteps`, in `readBridgeMessage`): a `steps` message is kept only when every step is well formed (`[point, call, frames, asyncAt, values]`, whole numbers, the value shapes above, at most 500 steps a message, 40 frames, 80 values, 6 levels and 1200 values a step, texts cut at 500); else it is dropped whole. The page keeps steps only while it is recording (or waiting for the last ones after Stop, at most 600 ms), only those whose point, functions and number of values fit the instrumentation (`fittingSteps`), at most `maxSteps`.
- **Stepping** (pure, `recording.ts`): `stepInto` (the next step), `stepOver` (the next step of the same call, past the calls its line makes, and after an `await` where the function goes on; when the call has no more steps, the first step after it ended), `stepOut` (the first step whose stack no longer has the call), `stepBack`; `nextHit` / `previousHit` (Resume to the next or previous step a breakpoint stops at, its condition holding; none: the end or the start, and the panel says so), `hitCounts`, `atBreakpoint` (a step on the line that is not a second statement of that line right after the first in the same call, so a loop's line stops once per round; a `testFollows` step never stops and stands aside for its test, so a `for` line stops at the test every round, round 0 with `i` in the Scope), `frameStep` (a caller's values: its own last step up to now), `scopeAt` / `scopeValues`, `recordedLines`. Previews like the browser's Scope: `valuePreview` (`"Rye loaf"`, `24.999999999999996`, `(3) [{…}, {…}, {…}]`, `{name: 'Rye loaf', grams: 0.75}`, `Map(1) {'croissant' => 2.4}`), `valueChildren` (an array also its `length`), `isExpandable`, `valueTone`.
- **Conditions** (`compileCondition(text)`, `condition.ts`, lazily loaded with the instrumentation): read with acorn as one expression (at most 300 characters) and evaluated by Grindstone on a step's recorded values: names (innermost scope first), `this`, literals, template literals, arrays of values, member access (also optional), `!`, `typeof`, arithmetic, comparisons, `&&`, `||`, `??`, `? :`, and calls of a few pure built-ins (`isNaN`, `Number`, `String`, `Boolean`, `parseInt`, `parseFloat`, `Number.isNaN`, `Number.isInteger`, `Math.round` and its kin, `Array.isArray`, a string's `startsWith`, `includes`, `toLowerCase`, …, a number's `toFixed`, an array's `includes`, `indexOf`, `at`). Refused when read: assignments ("A condition can't change values: use === to compare"), other calls, `new`, functions, `delete`, regexp literals, `constructor` and `__proto__`. At a step where it reads what the recording did not keep (an object too deep, a cut string, a getter, a name the step can't see: "unknown is not defined at this step", Chrome's "Cannot read properties of undefined (reading 'name')") it does not hold. `===` on objects is identity (their ids); other operators on objects are refused (they would run the app's `valueOf`). Never throws.

### The profile

ADR 0007, update 2026-11-13 (chapter 6); `shared/levels/debugging/recorder.ts` (counting), `profile.ts` and the bridge's page watch and server clock (`bridge.ts`, `backend.ts`), tests in `test/unit/levels/debugging/counting.test.ts`, `profile.test.ts`, `backend.test.ts`, and in a browser `e2e/debugging-performance.spec.ts` and `e2e/debugging-levels.spec.ts`. A level with `sandbox.performance` gets the Performance panel (how it looks: docs/features/ui.md, "Performance"). The numbers are **counted, never timed**, so the same run gives the same numbers in Chromium, Firefox and WebKit and on CI.

- **Work** (the cost model): one unit is one statement of the app's code that ran, from chapter 5's instrumentation (same `instrumentFiles`, same inserted text) with the recorder **counting** instead of reading values (`countingLimits('check' | 'profile')`, `profile: 1 | 2` in its limits): a unit goes to the function running it (**self**) and once to every function on the call stack (**total**; a recursive one too; the 256 innermost calls only, so a call below a deeper recursion misses those units in its total); **calls** are counted when a function starts. A built-in (`sort`, `find`'s own loop, `toFixed`) counts as part of the statement that calls it, and a callback it calls counts as its own function under the caller. Counting stops at `PROFILE_LIMITS.maxWork` (1,000,000 units; the app runs on).
- **Renders**: what the app changed on the page, from a MutationObserver the bridge starts once the page is parsed (`readyState` `interactive`, before any module runs). A change counts **nodes**: the elements and non-blank texts a `childList` record adds or removes, or one for an attribute or a text set. The counting recorder looks at the observer's records (`takeRecords`) before each statement and when a call ends, waits or comes back, so a change belongs to the statement that ran since the last look (a call's current statement; a callback a built-in calls makes its own); a **render** is a call of a function whose own statements changed the page, counted once per call. What changes the page outside the app's code (the browser, a check run) belongs to nothing.
- **The server's clock**: time moves only when an answer arrives, to the moment its request went out plus its scripted delay (`hooks.sent`, `hooks.arrived`, `hooks.aborted` of the fake backend). A request sent when the clock says 400 starts at 400, whatever real time it is; requests sent together start together, so `Promise.all` shows side by side and awaits in turn show as stairs. In a Performance level a check run's "quiet" also needs 50 ms without a request sent or answered, so the moment between an answer and the next request of a waterfall is not taken for the end.
- **Actions** (a recorded profile only): the page's load, then each click, typing (`input`), `change`, Enter (`keydown`) or form the bridge sees in the frame (capturing listeners set before the app's); the events of one press in one task (a checkbox's click, input and change) are one action. An action counts everything that ran from it until the next one (answers arriving meanwhile included), with when it started on the server's clock, its label (a button's text, a field's value cut at 40, `checked`, `Enter`) and the requests sent during it. At most `maxActions` (100); later ones count into the last (`more`).
- **What the frame posts** (`count: 'profile'`, Record): a `profileTick` (work so far) at most every 250 ms while recording, and the **profile** once, at Stop or at the cap: `{ reason, work, actions: [{ kind, target, label, at, work, more, fns: [[fn, calls, self, total]], dom: [[point, updates, nodes]], renders: [[fn, renders, nodes]], requests }], requests: [[id, start, end]] }`, at most 500 rows a table (the first ones), 200 requests. A check run (`count: 'check'`) posts nothing: its `work` probes read the count.
- **Reading it** (`readProfile`, in `readBridgeMessage`): whole numbers up to 10⁹, the action kinds above, texts cut (target 120, label 60), the caps above; anything else drops the profile whole; never throws. `fittingProfile` keeps only rows whose function or point the instrumentation has.
- **The panel's tables** (pure): `functionRows(profile, map, action)` (one action or all of them, null: the most total first, then self, then file and line; a file's top level is `module`), `renderRows` (the most nodes first, each function with its lines that changed the page), `requestRows(profile, entries, action)` (in order sent, times from the view's start; `after`: in the same action, sent the moment that request's answer arrived, a waterfall; `repeats`: an earlier request of the recording with the same method, address and body), `timelineEnd`, `profileSummary` (work, renders, nodes, requests, server time until the last answer), `profileLines` (every line the panel links: functions, changed lines, Sent from; find tasks are answered there).
- **Counted check runs**: a level whose probes read the work (`needsCounting`) runs its check instrumented to count (the play page loads the chapter 5 tools for it); any other probe reads what it reads as written, and the levels e2e checks that every chapter 6 app does the same counted as written (values, errors, requests). A file that runs as written (instrument.ts skipped it: a syntax error, a clash, the recorder's name …) leaves every `work` probe without a value and says why (`withUncounted`), so leaving code out of the count never passes a goal. A counting check run's policy has no `'unsafe-eval'` (`COUNTING_CSP`): `eval`, `new Function` and string timers would run code nothing counts, so there they fail (the Console of the app you see keeps eval). Still not counted (known limits): a module the app makes at runtime from a blob, and a `<script>` written into index.html or added by the app (inline scripts must run: the bridge is one). The recorder can't be switched off by the app's code (`on` is a getter, the api frozen); a counting check run stopped any other way reads no number. A profile whose request ids repeat, or that has more than the recorder keeps, is dropped whole.

- **The level's logs** (`LogsSpec`): `now` (the server's clock when the app loads, `'09:41:00.000'`), `firstRequest` (the id of a load's first request: 4127 makes `req-4127`, each request after it counts up), `history` (what the server logged before you came, oldest first, at most `MAX_LOG_HISTORY` (200) lines of `{ at, level, route, request, message, stack? }`; `incident-shop.ts` has short ways to write them: `accessRow`, `deployRow`, `pastLines`). An answer of the backend may script what the server logs while it answers (`BackendReply.log`: `{ level, message, stack? }`, `{body}` in a message is the request's body cut at 300 characters, `{query}` its query). `checkLogs` checks all of it (times as `HH:MM:SS.mmm`, oldest first and not after `now`, request ids before the first of a load, routes as `METHOD /path`, levels, messages up to 2000 characters, stacks up to 12 lines); the level tests run it on every level.
- **Request ids and the server's reports**: in a level with logs every answer of the shop's own server carries `x-request-id: req-<n>` (another origin's server is not the shop's, and a failed connection reached no server), so a page can show it to the customer; and the backend posts a `serverlog` when it answers: numbers only (the request's id, which route and answer, the status, when on the server's clock, how long it took). `readBridgeMessage` keeps it when every number is whole and in range. The page builds the lines itself from the level's data and the request it already has (`liveEntries`): the answer's scripted lines, then the **access line** (`POST /api/orders 500 Internal Server Error · 40 ms`; level error for a 5xx, warn for a 4xx, else info). The report carries no text; what the request sent (method, path and query, body) comes from the frame through the request message, each cut at 300 characters. A forged report can only repeat the level's own lines for a request of this load, once per request (a second report for an id is dropped), at most `MAX_LOG_LINES` (500) a load. Why build them on the page: the lines are level data, unit-tested; the frame stays the one that says what happened, not what it means.
- **The server's clock** (`clockText`): a line's time is `now` plus when its answer went out, on the chapter 6 rule (an answer at its request's start plus its delay; time moves only then), so the same run reads the same times in every browser.
- **Stacks**: a stack line `at fn (file.js:14:9)` (or `at file.js:14:9`) whose file is one of the app's links its line (an error a customer's browser reported to the server, 7.1's find task); server code (`server/orders.js`) stays text: you can read it, not run it.
- **Filtering** (`filterLogs`): a level and worse (all, warnings and errors, errors) and a text anywhere in the time, route, request id, message or stack, in any case; linear.

### The deploys

ADR 0007, update 2026-11-13 (chapter 7); `shared/levels/debugging/deploys.ts`, tests in `test/unit/levels/debugging/deploys.test.ts`, `incidents.test.ts`. A level with `sandbox.deploys` gets the Deploys panel (docs/features/ui.md, "Deploys").

- **A history** (`deployHistory(base, specs)`): the files before the first deploy listed, and each deploy as `{ id (7 hex digits), author, at, message, edits }` whose edits replace the first occurrence of a text (like a solution's saves). It keeps every version's files (`Deploy.files`); a level's starting files are the live (newest) one's (`liveFiles`), which the level tests check. It throws for an id that is not 7 hex digits or listed twice, an unknown file, a text that is not there, a deploy that changes nothing, more than `MAX_DEPLOYS` (8). The base is not a version you can roll back to.
- **Diffs** (`deployChanges`): each changed file with git's line diff (`diffLines`, `splitLines` from `shared/git/diff.ts`, the same LCS as `git diff`) grouped into git's hunks with three lines of context (`@@ -1,3 +1,4 @@`), every line with its number before and after and `at`, the line of the file after the deploy to show for it (a removed line: where it was).
- **Finding a line again** (`lineIn(from, line, to)`): where a line of one text is in another (the longest common subsequence; a line that is gone maps to the place after the last line kept before it), so a diff line opens where it is in the saved code now, also after your edits or a rollback. The code is whatever the player typed: past `MAX_MAP_CELLS` (4,000,000 lines times lines) a line keeps its number instead of freezing the page.
- **Versions**: `versionOf(history, files)` names the newest deploy whose files are exactly these (the panel's "your saved code"), `differingPaths` what a rollback changes.
- **Roll back** (the engine's `rollback`): every file becomes the deploy's (also files you changed that the deploy didn't touch: a rollback deploys a whole version), as one counted action like a save. The play page puts the files in the editor too and asks first (what changes, which files hold your own saved code, which unsaved edits are dropped). When the saved code was no version of the list, it keeps a copy, and **Undo roll back** (`restoreFiles`, counted like a save; only a file set with exactly the app's files) brings it back; a save after the rollback drops the copy, so Undo never throws a newer save away.
- **The files a check ran**: `reload(session, level, observation, ran)` records them as `checked` (the play page passes the files the check started with), so a save made while the check ran is not taken for checked code.

## Level file format

Scenarios: one file per scenario in `shared/levels/<track>/NN-slug.ts`, exporting a `Scenario`. Practice tasks: grouped per chapter in `shared/levels/<track>/practice/<chapter>.ts`, each exporting a `PracticeTask`.

| Field | Content |
| --- | --- |
| `id` | a scenario `<track>-NN-slug` (`git-04-merge-conflict`), a practice task `<track>-practice-slug` (`git-practice-stage-one-file`); the URL is the id without the track |
| `track`, `kind`, `title` | `'git'` or `'debugging'`, `'scenario'` or `'practice'`, a short title |
| `difficulty`, `minutes` | 1-3; the time estimate (a practice task about 0.5) |
| `story` | scenario: 1-3 short paragraphs (joined with a blank line), second person, the situation and what to do |
| `task`, `practises`, `why` | practice task: the task in one or two sentences (one line); the id of its scenario; one line on why it works, shown once solved |
| `setup` | `() => S`, the environment's state; git: a `GitState` built with `repo()` / `folder()` from the git model; Debugging: `{ files, observed: null, picked: null }`, the files from `orderSite()` (`bakery.ts`) plus the level's own; must be deterministic |
| `sandbox`, `teaches` | Debugging only, see "The Debugging environment" |
| `goals` | `{ id, label, check({ state, history }) }`; `label` is one checklist line (`backticks` become code) |
| `teammates` | optional `{ id, author, trigger, apply, notice }`; `trigger` is `{ afterCommands: n }`, `{ beforeCommand: 'git push' }` or `{ when: state => boolean }` (right after the command that makes the check pass, e.g. your branch reached origin); `apply` usually calls `teammateCommit` or `teammateMerge` on origin |
| `hints` | a scenario: exactly three (nudge, concept, exact commands in backticks); a practice task: one |
| `debrief` | scenario: `{ title, paragraphs }`, 2-4 short paragraphs on why it works |
| `solution` | the steps that solve it (a practice task: 1-3), `SolutionStep = string \| { save: string }`: a terminal line, or saving the file git waits for in the editor with this text (`rebase -i`: the todo list, then the message); the tests replay them through `playStep` |

Goal helpers for git levels live in `shared/levels/git/checks.ts`: `conflictFullyResolved(state, rev)`, `treeOf`, `treeHasConflictMarkers`, `changedIn(state, rev)` (paths a commit changed against its first parent), `gitInvocations(history)` (every `git ...` command, also inside chains), `ran(history, command, matches?)` (a successful `git <command>` in the history), `hasFlag(args, short, long?)` (also bundled: `-am` has `-a`), `isBareForcePush`, `isLeasePush`, `isMergeOf(state, rev, first, second)` (a merge commit with exactly these parents), `ranAfter(history, command, after, matches?)` (e.g. a `git log` after the last `git merge`), `ranBefore(history, before, matches)` (a matching command before the first successful one of `before`, e.g. a look before the sync), `logRevisions(args)` (what a `git log` includes and excludes, as typed: `a..b`, `^a`), `logsOnlyOn(args, on, notOn)` (`git log origin/main..main` and its spellings) and `committedOn(state, id, branch)` (HEAD's reflog shows the commit made on that branch, also after the branch is deleted). `ignoreMatcher` from the git model checks a committed `.gitignore`.

Conventions:

- Goals check outcomes in the state, not the commands typed. Use `history` only when the *how* is the lesson (level 6: `--force-with-lease`, never a bare `--force`) or when the command changes nothing (`diff`, `log`: "You looked at both sides").
- A goal that is trivially true at the start is fine when it guards against a wrong path (e.g. "no merge commits", "dist/ and .env are still on your disk"), but it must be listed in the test's `initialGoals` table.
- Every scenario has at least one wrong path in the test's `wrongPaths` table (the obvious shortcut that must not solve it), and every practice task its obvious one.
- Conflict files are written in the solution with `echo ... >` and `echo ... >>` (chained with `&&`), since the editor panel is UI-only.
- A solution that needs a commit id computes it from the deterministic setup (1.4 Read the history, the todo lists of 4.4 and its practice task).
- Editor steps of `git rebase -i` are `{ save: text }` in the solution, one per file git opens: `['git rebase -i main', { save: 'reword 1a2b3c4 ...
fixup ...' }, { save: 'Add gift cards to the shop' }]`. In the app they are Start rebase and Save message; each counts as one command, like the line it replaces.

### Adding a Debugging level

1. Add its row to `test/unit/levels/debugging/expected.ts` (probe values, errors and where the first error points, before and after the fix; with a backend the Network panel's rows and the Console lines the texts quote, `says`) and its lines to `POINTED_AT` in `levels.test.ts`: red. A find task whose answer is not on the trace or a request's initiator is marked `answerOffTrace` (every Elements find task: its answer is a rule's line); a chapter 5 find task whose answer the recording stops on is marked `answerStep`, a chapter 6 find task (its answer a line the Performance panel links) `answerProfile`, each with `before` holding what the customer does while recording. Every goal must fail on the starting files: a guard ("the message still shows") goes into one `probesGoal` with what the fix changes.
2. Write the file (a scenario in `shared/levels/debugging/NN-slug.ts`, a practice task in `practice/<chapter>.ts`) and list it in its chapter in `shared/levels/debugging/index.ts`.
3. `pnpm test`, then `pnpm exec playwright test e2e/debugging-levels.spec.ts`: the real app must do what the table says, every goal must fail on a reload of the starting files and with a file the fix edits emptied or deleted, the other fixes in `fixes.ts` must pass and its non-fixes fail, and the solution must solve it on its last step.
