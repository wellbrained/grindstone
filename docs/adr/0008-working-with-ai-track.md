# 0008 · Third track: Working with AI

Status: accepted, 2026-11-14. Nik delegated the design to Claude's recommendations ("go with your recommendations"), as with the Debugging chapters (0007). Each chapter still gets an Opus review before it ships.

## Which track and why

- **Working with AI** (`/ai`, registry id `ai`), before Web fundamentals and Framework deep dives. It is the most original of the four (the side-project brief found no dedicated tool for it), it is what employers ask about right now, and it reuses most of the Debugging environment. Web fundamentals overlaps the Debugging track (CORS, the event loop, performance are already levels); Framework deep dives stays next.
- **Tagline**: "Lead the assistant, then check its work."

## No live AI

- Every level is **scripted**: the assistant's pull requests, answers and claims are written into the level, like Git's teammates. No model is called, nothing leaves the browser, no account, no cost, and every run is the same (testable, fair). The UI never pretends otherwise: the assistant is a character.
- **The assistant**: Sous, Corner Bakery's coding assistant (a sous-chef). Confident, fast, usually right, sometimes wrong in the ways real assistants are wrong.

## Two mechanics

1. **Review** (chapters 1–6): Sous opens a pull request (title, description with its claims, a diff over the shop's files). You review it like on GitHub: comment on a line or a range with a **category** (bug, security, missing test, false claim, scope, unclear), then **Approve** or **Request changes**. The level's **planted issues** are known: a comment counts when it touches the issue's lines with a fitting category. **Solved** = every planted issue found and the right verdict. A comment that finds nothing is a **false alarm**: it doesn't fail the level, but it counts against the best run. You can **run the PR**: the changed app runs in the Debugging sandbox (App, Console, later Tests), so you review with evidence, not just by reading.
2. **Steer** (chapter 7): you write the review that makes Sous fix it. Sous's next commit follows your comments: each planted issue has the feedback that fixes it, and vague feedback ("this looks wrong") gets a plausible but wrong fix. Scripted by matching the comment's category and lines, not free-text understanding.

- **Best run**: fewest hints, then fewest false alarms.
- **Practice tasks**: "spot it" (one small diff, one issue, one comment) and "verdict" (approve or request changes, with a one-line why), about 30 s.

## Chapters

1. **Read the diff** — plain bugs in small PRs (off-by-one, wrong variable, inverted condition, a missing case).
2. **Claims vs. code** — the description says one thing, the code does another ("handles empty baskets", "no behaviour change").
3. **Tests that lie** — tests that assert nothing, mock the thing under test, or were changed to pass. Brings a **Tests** panel (run the PR's tests in the sandbox).
4. **Invented APIs** — functions, options or packages that don't exist, deprecated calls; the Console proves it when you run the PR.
5. **Security** — HTML injection, a secret in code, a missing check on who may do something, trusting the client.
6. **Scope and size** — unrelated changes, a rewrite where a line would do, a PR that should be two.
7. **Steer the assistant** — write the review that gets the right fix.

First release: chapter 1 with the review mechanic, then one chapter at a time, each reviewed and deployed. A cheat sheet after chapter 7 ("what to check in an AI pull request").

## Update 2026-11-14: chapter 1, Read the diff (built as 0.3.3)

The first release: the review environment, its play page, chapter 1 (5 scenarios, 10 practice tasks; chapters 2 to 7 show as coming) and the overview radar on home. docs/features/levels.md ("The review environment", "The Working with AI levels") and docs/features/ui.md ("Working with AI play page", "Home") have the details. Decisions made while building:

- **An environment of its own, `shared/levels/review/`, registered as the track `ai`**: state, counted actions (add, edit, delete a comment; send the review), checks and levels, with Debugging's shop files reused (`debugging/bakery.ts`) and nothing of its engine. Run the PR reuses the sandbox on the page's side only.
- **Where a comment sits is lines, not rows**: a comment covers one stretch of rows of one hunk (at most 12) and is stored as the lines those rows have on each side (`head` after the change, `base` before it; an unchanged row has both). Why: a level names its planted issues by line numbers alone (`lines`, or `removed` for lines the change took out), the matching is plain interval overlap, and the diff can change its grouping without breaking a level. Editing a comment changes its category and text, never its lines (as on GitHub).
- **Matching**: a comment finds every planted issue it touches with a category the issue accepts; an issue may name **other places** a reviewer would rightly point at (`also`: 1.4's locker line next to the `switch` that never handles it). A comment on an issue's lines with another category is **near**: not found, and not a false alarm either (it saw something). Only a comment that touches no issue is a false alarm.
- **An approval flags nothing**: every comment has a problem category, so approving with comments is not the right verdict (`flaggedApproval`, said in the review's status line). That makes "only false alarms" fail on a pull request that should be approved too.
- **Verdict tasks need a reason, which is not read**: the one-line reason is the review's summary, required before a verdict task can be sent and never checked (Grindstone reads no free text; the page says so). Where the verdict is Request changes, the planted issue must still be found by a comment, so the reason that is checked is the comment's line; where it is Approve, the reason makes you say why before you click. A verdict task has one goal, the whole review, and its status line never says how many problems there are (that is the question). Considered and dropped: a multiple-choice reason (a quiz beside the review, not a review).
- **False alarms count once per comment per attempt**: each comment that was a false alarm in a sent review is counted once (`alarmed`), however often it is sent again or edited; a deleted and rewritten comment counts again. Why: with resubmits allowed, counting only the solving review would let you delete what the feedback called a false alarm and come out clean. The count rides in the run as `falseAlarms` (the core's `act` takes `falseAlarms` like `reloads`; a review sets it even when 0), no new progress version: 0.3.2 data loads unchanged and 0.3.2 reads a 0.3.3 file (`core.test.ts`).
- **Feedback per comment after sending**: "Found: <the issue's title>", "Something is wrong on these lines, but it isn't …" (near), "Nothing wrong here: <why>" on a tempting spot (or that no problem touches these lines). A comment whose category changed since says so until the next review. The review's status line says how many problems were found (not where), whether the verdict is right, and the false alarms.
- **Run the PR starts on demand**, App and Console as in Debugging, and switches between **This PR** and **main** (each a fresh load), so the bug shows next to the code that does not have it. The components and the bridge are used as they are; `useDebuggingPlay` got a `runOnly` option (a session kept by the component, nothing recorded) and the app is a Debugging level made for the moment (`runLevel`: the side's files, no probes, no goals). Every scenario runs; practice tasks are one file and say there is nothing to run. Considered: a Code panel for the run (not needed: the diff is the code), linking Console traces into the diff (left for later).
- **Syntax colours were cheap**: the editor's lezer parsers (`@codemirror/lang-javascript`, `-css`, `-html`, already their own chunks) run over each whole file once and are cut into lines of tokens with the editor's theme colours as classes; rendered as text. The diff turns ligatures off, so `>=` and `<=` read as typed.
- **The overview radar leaves the coming tracks out** (Nik's "your call"): three live tracks make a triangle; dashed axes for Web fundamentals and Framework deep dives would only dent the shape with nothing you can practise. It shows on home once you have progress (it is your radar), with the tracks as its legend; axis colours are the live tracks' places (Git 0, Debugging 1, Working with AI 2).
- **Track page tags**: a scenario's mistake (`off-by-one`, `wrong variable`, `inverted condition`, `missing case`, `units`), a practice task's kind (`spot it`, `verdict`); the best run reads "best: no hints, 1 false alarm".
- **Chapter 1 as built**: 1.1 an off-by-one in `canAddMore` with a correct `>=` guard as the tempting false alarm (and the call site, where the symptom shows); 1.2 the wrong variable (the basket's item count for a row's quantity), right in the one case Sous tested; 1.3 an inverted condition (a show-condition assigned to `hidden`); 1.4 a missing case (a new value, a `switch` without it, NaN), its debrief also says why no `break` is missing; 1.5 two issues, a unit slip (a percentage used as a share) and a rounding slip (whole euros), with a correct `count < BULK_FROM` as the tempting spot. Ten practice tasks, a spot it and a verdict per scenario; two verdicts are fine and should be approved (a loop rewritten the usual way, a double negative removed). Every scenario's debrief says how you would have caught it (read the diff with the description in mind, run it, try the edge), and the e2e checks that running it shows what the debrief says.
- **Known limits**: matching is by lines and categories, so a wrong reason on the right lines counts (a "missing break" comment of the kind bug on 1.4's `switch` finds the missing case); no "expand context" in the diff and no unchanged files to open; a comment can't be moved to other lines (delete it and write a new one).

## Review 2026-11-14 (Opus, before deploy)

- **Every level could be solved without reading the diff**: a comment found an issue whenever it overlapped its lines, and 12-row comments of the kind bug over every hunk (plus Request changes) solved all 13 PRs with problems, 11 of them without a false alarm. Fixed with a **focus rule**: a comment finds an issue only when at most 2 of its rows (`FOCUS_SLACK`) belong to no planted issue (rows of another issue don't count, so a comment over two issues side by side finds both). A wider comment over an issue and context lines finds nothing and is told to narrow it down (free); a wider one that also covers changed rows with nothing wrong in them is a false alarm ("broad"). `levels.test.ts` replays the blanket (12- and 10-row comments, every one full size) on every level and none is solved; in every scenario any tiling blanket of 1 to 12 rows that solves costs false alarms. A practice task's whole diff is a handful of lines, so two small comments over it can find its one problem by chance; that is close to reading it. Every solution and the e2e still pass unchanged.
- **The category**: in chapter 1 every issue accepts bug (its problems are plain bugs), so there the category barely grades and the focus rule does the work. From chapter 2 on, issues accept the kind they are (a false claim, a missing test, security, scope), not always bug; `levels.test.ts` fails a later chapter whose every issue accepts bug.
- **Reset laundered false alarms**: blanket, read the feedback, Reset, send only the finders: 0 false alarms. Reset now keeps the false alarms like hints (the core's `restart`): the feedback named the right comments, which is as good as a hint. Debugging's reloads stay as they were (Reset starts them at 0): a reload's lesson is the fix you wrote, and Reset takes the files back to the start, so doing it again needs the skill again; git's commands, the same. Play again (a fresh attempt) still starts every count at 0, as it does for hints.
- **A hint quoted a line the diff did not show** (the medium coffee's `return 2.2 + EXTRA[size]`, one line past the hunk's context): the file lost a blank line, so the price is in the context, and the hint quotes it. `levels.test.ts` now checks every hint's quoted code against the rows of the diff (not the files), and every line `POINTED_AT` names is in the diff.
- **Keyboard picking with the form open** started from the form's first row, and Enter threw away what was typed: picking with Shift and the arrows starts from the focused row, the picked rows are what is lit, and Enter (or a click, Shift+click) moves the open form there with its category and text. Editing another comment no longer closes it either.
- **Console links in Run the PR did nothing** (they open Code, which Run the PR does not show): a file:line link now shows that line in the diff, by the side's numbers, and focuses it; a line the diff does not show is said so.
- **Phones could only comment on one line** while the how-to spoke of Shift and drag: touch screens (`pointer-coarse`) get their own how-to ("Tap a line number…; one line is enough"). Chosen over a two-tap range: every planted issue is found by one line, and a second mode on the same tap would be guesswork.
