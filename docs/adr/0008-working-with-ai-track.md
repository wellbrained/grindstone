# 0008 · Third track: Working with AI

Status: accepted, 2026-11-14. Nik delegated the design to Claude's recommendations ("go with your recommendations"), as with the Debugging chapters (0007). Each chapter still gets an Opus review before it ships.

## Which track and why

- **Working with AI** (`/ai`, registry id `ai`), before Web fundamentals and Framework deep dives. It is the most original of the four (the side-project brief found no dedicated tool for it), it is what employers ask about right now, and it reuses most of the Debugging environment. Web fundamentals overlaps the Debugging track (CORS, the event loop, performance are already levels); Framework deep dives stays next.
- **Tagline**: "Lead the assistant, then check its work."

## No live AI

- Every level is **scripted**: the assistant's pull requests, answers and claims are written into the level, like Git's teammates. No model is called, nothing leaves the browser, no account, no cost, and every run is the same (testable, fair). The UI never pretends otherwise: the assistant is a character.
- **The assistant**: Sous, Corner Bakery's coding assistant (a sous-chef). Confident, fast, usually right, sometimes wrong in the ways real assistants are wrong.

## Two mechanics

1. **Review** (chapters 1–6): Sous opens a pull request (title, description with its claims, a diff over the shop's files). You review it like on GitHub: comment on a line or a range with a **category** (bug, security, missing test, false claim, scope, unclear), then **Approve** or **Request changes**. The level's **planted issues** are known: a comment counts when it touches the issue's lines with a fitting category. **Solved** = every planted issue found and the right verdict. A comment that finds nothing is a **false alarm**: it doesn't fail the level, but it counts against the best run. You can **run the PR**: the changed app runs in the Debugging sandbox (App, Console, later Tests), so you review with evidence, not just by reading.
2. **Steer** (chapter 7): you write the review that makes Sous fix it. Sous's next commit follows your comments: each planted issue has the feedback that fixes it, and vague feedback ("this looks wrong") gets a plausible but wrong fix. Scripted by matching the comment's category and lines, not free-text understanding.

- **Best run**: fewest hints, then fewest false alarms (and in chapter 7, then fewest rounds: update below).
- **Practice tasks**: "spot it" (one small diff, one issue, one comment) and "verdict" (approve or request changes, with a one-line why), about 30 s.

## Chapters

1. **Read the diff** — plain bugs in small PRs (off-by-one, wrong variable, inverted condition, a missing case).
2. **Claims vs. code** — the description says one thing, the code does another ("handles empty baskets", "no behaviour change").
3. **Tests that lie** — tests that assert nothing, mock the thing under test, or were changed to pass. Brings a **Tests** panel (run the PR's tests in the sandbox).
4. **Invented APIs** — functions, options or packages that don't exist, deprecated calls; the Console proves it when you run the PR.
5. **Security** — HTML injection, a secret in code, a missing check on who may do something, trusting the client.
6. **Scope and size** — unrelated changes, a rewrite where a line would do, a PR that should be two.
7. **Steer the assistant** — write the review that gets the right fix.

First release: chapter 1 with the review mechanic, then one chapter at a time, each reviewed and deployed (chapter 2 since 0.3.4, chapter 3 since 0.3.5, chapter 4 since 0.3.6, chapter 5 since 0.3.7, chapter 6 since 0.3.8, chapter 7 since 0.3.9; the track counts as complete since 0.4.0). The cheat sheet came with chapter 7 ("what to check in an AI pull request", `/ai/cheat-sheet`).

## Update 2026-11-14: chapter 1, Read the diff (built as 0.3.3)

The first release: the review environment, its play page, chapter 1 (5 scenarios, 10 practice tasks; chapters 2 to 7 show as coming) and the overview radar on home. docs/features/levels.md ("The review environment", "The Working with AI levels") and docs/features/ui.md ("Working with AI play page", "Home") have the details. Decisions made while building:

- **An environment of its own, `shared/levels/review/`, registered as the track `ai`**: state, counted actions (add, edit, delete a comment; send the review), checks and levels, with Debugging's shop files reused (`debugging/bakery.ts`) and nothing of its engine. Run the PR reuses the sandbox on the page's side only.
- **Where a comment sits is lines, not rows**: a comment covers one stretch of rows of one hunk (at most 12) and is stored as the lines those rows have on each side (`head` after the change, `base` before it; an unchanged row has both). Why: a level names its planted issues by line numbers alone (`lines`, or `removed` for lines the change took out), the matching is plain interval overlap, and the diff can change its grouping without breaking a level. Editing a comment changes its category and text, never its lines (as on GitHub).
- **Matching**: a comment finds every planted issue it touches with a category the issue accepts; an issue may name **other places** a reviewer would rightly point at (`also`: 1.4's locker line next to the `switch` that never handles it). A comment on an issue's lines with another category is **near**: not found, and not a false alarm either (it saw something). Only a comment that touches no issue is a false alarm.
- **An approval flags nothing**: every comment has a problem category, so approving with comments is not the right verdict (`flaggedApproval`, said in the review's status line). That makes "only false alarms" fail on a pull request that should be approved too.
- **Verdict tasks need a reason, which is not read**: the one-line reason is the review's summary, required before a verdict task can be sent and never checked (Grindstone reads no free text; the page says so). Where the verdict is Request changes, the planted issue must still be found by a comment, so the reason that is checked is the comment's line; where it is Approve, the reason makes you say why before you click. A verdict task has one goal, the whole review, and its status line never says how many problems there are (that is the question). Considered and dropped: a multiple-choice reason (a quiz beside the review, not a review).
- **False alarms count once per comment per attempt**: each comment that was a false alarm in a sent review is counted once (`alarmed`), however often it is sent again or edited; a deleted and rewritten comment counts again. Why: with resubmits allowed, counting only the solving review would let you delete what the feedback called a false alarm and come out clean. The count rides in the run as `falseAlarms` (the core's `act` takes `falseAlarms` like `reloads`; a review sets it even when 0), no new progress version: 0.3.2 data loads unchanged and 0.3.2 reads a 0.3.3 file (`core.test.ts`).
- **Feedback per comment after sending**: "Found: <the issue's title>", "Something is wrong on these lines, but it isn't …" (near), "Nothing wrong here: <why>" on a tempting spot (or that no problem touches these lines). A comment whose category changed since says so until the next review. The review's status line says how many problems were found (not where), whether the verdict is right, and the false alarms.
- **Run the PR starts on demand**, App and Console as in Debugging, and switches between **This PR** and **main** (each a fresh load), so the bug shows next to the code that does not have it. The components and the bridge are used as they are; `useDebuggingPlay` got a `runOnly` option (a session kept by the component, nothing recorded) and the app is a Debugging level made for the moment (`runLevel`: the side's files, no probes, no goals). Every scenario runs; practice tasks are one file and say there is nothing to run. Considered: a Code panel for the run (not needed: the diff is the code), linking Console traces into the diff (left for later).
- **Syntax colours were cheap**: the editor's lezer parsers (`@codemirror/lang-javascript`, `-css`, `-html`, already their own chunks) run over each whole file once and are cut into lines of tokens with the editor's theme colours as classes; rendered as text. The diff turns ligatures off, so `>=` and `<=` read as typed.
- **The overview radar leaves the coming tracks out** (Nik's "your call"): three live tracks make a triangle; dashed axes for Web fundamentals and Framework deep dives would only dent the shape with nothing you can practise. It shows on home once you have progress (it is your radar), with the tracks as its legend; axis colours are the live tracks' places (Git 0, Debugging 1, Working with AI 2).
- **Track page tags**: a scenario's mistake (`off-by-one`, `wrong variable`, `inverted condition`, `missing case`, `units`), a practice task's kind (`spot it`, `verdict`); the best run reads "best: no hints, 1 false alarm".
- **Chapter 1 as built**: 1.1 an off-by-one in `canAddMore` with a correct `>=` guard as the tempting false alarm (and the call site, where the symptom shows); 1.2 the wrong variable (the basket's item count for a row's quantity), right in the one case Sous tested; 1.3 an inverted condition (a show-condition assigned to `hidden`); 1.4 a missing case (a new value, a `switch` without it, NaN), its debrief also says why no `break` is missing; 1.5 two issues, a unit slip (a percentage used as a share) and a rounding slip (whole euros), with a correct `count < BULK_FROM` as the tempting spot. Ten practice tasks, a spot it and a verdict per scenario; two verdicts are fine and should be approved (a loop rewritten the usual way, a double negative removed). Every scenario's debrief says how you would have caught it (read the diff with the description in mind, run it, try the edge), and the e2e checks that running it shows what the debrief says.
- **Known limits**: matching is by lines and categories, so a wrong reason on the right lines counts (a "missing break" comment of the kind bug on 1.4's `switch` finds the missing case); no "expand context" in the diff and no unchanged files to open; a comment can't be moved to other lines (delete it and write a new one).

## Review 2026-11-14 (Opus, before deploy)

- **Every level could be solved without reading the diff**: a comment found an issue whenever it overlapped its lines, and 12-row comments of the kind bug over every hunk (plus Request changes) solved all 13 PRs with problems, 11 of them without a false alarm. Fixed with a **focus rule**: a comment finds an issue only when at most 2 of its rows (`FOCUS_SLACK`) belong to no planted issue (rows of another issue don't count, so a comment over two issues side by side finds both). A wider comment over an issue and context lines finds nothing and is told to narrow it down (free); a wider one that also covers changed rows with nothing wrong in them is a false alarm ("broad"). `levels.test.ts` replays the blanket (12- and 10-row comments, every one full size) on every level and none is solved; in every scenario any tiling blanket of 1 to 12 rows that solves costs false alarms. A practice task's whole diff is a handful of lines, so two small comments over it can find its one problem by chance; that is close to reading it. Every solution and the e2e still pass unchanged.
- **The category**: in chapter 1 every issue accepts bug (its problems are plain bugs), so there the category barely grades and the focus rule does the work. From chapter 2 on, issues accept the kind they are (a false claim, a missing test, security, scope), not always bug; `levels.test.ts` fails a later chapter whose every issue accepts bug.
- **Reset laundered false alarms**: blanket, read the feedback, Reset, send only the finders: 0 false alarms. Reset now keeps the false alarms like hints (the core's `restart`): the feedback named the right comments, which is as good as a hint. Debugging's reloads stay as they were (Reset starts them at 0): a reload's lesson is the fix you wrote, and Reset takes the files back to the start, so doing it again needs the skill again; git's commands, the same. Play again (a fresh attempt) still starts every count at 0, as it does for hints.
- **A hint quoted a line the diff did not show** (the medium coffee's `return 2.2 + EXTRA[size]`, one line past the hunk's context): the file lost a blank line, so the price is in the context, and the hint quotes it. `levels.test.ts` now checks every hint's quoted code against the rows of the diff (not the files), and every line `POINTED_AT` names is in the diff.
- **Keyboard picking with the form open** started from the form's first row, and Enter threw away what was typed: picking with Shift and the arrows starts from the focused row, the picked rows are what is lit, and Enter (or a click, Shift+click) moves the open form there with its category and text. Editing another comment no longer closes it either.
- **Console links in Run the PR did nothing** (they open Code, which Run the PR does not show): a file:line link now shows that line in the diff, by the side's numbers, and focuses it; a line the diff does not show is said so.
- **Phones could only comment on one line** while the how-to spoke of Shift and drag: touch screens (`pointer-coarse`) get their own how-to ("Tap a line number…; one line is enough"). Chosen over a two-tap range: every planted issue is found by one line, and a second mode on the same tap would be guesswork.

## Update 2026-11-14: chapter 2, Claims vs. code (built as 0.3.4)

Sous's description makes claims and the code doesn't keep them. 5 scenarios and 10 practice tasks; docs/features/levels.md ("The review environment", "The Working with AI levels") and ui.md ("Working with AI play page") have the details. Decisions:

- **A comment can sit on the description** (Nik left it open, with yes as the recommendation): the description is shown as numbered lines like a file, each paragraph one line and then each claim one line (`descriptionFile`, path `description`), and it is drawn and picked by the same `ReviewFile` as the diff (one number column, prose). Why: a false claim lives in the claim, and pointing at it is what a reviewer does on GitHub ("this isn't true"); with lines it is the same mechanic as the diff (places, matching, keyboard, phones), with no second kind of comment. Considered: claims as checkboxes to tick as false (a quiz beside the review), comments only on code (then "Fixes #142", whose code is fine, has nowhere to be pointed at).
- **A claim issue is found from the claim or from the code that breaks it, with false claim**: the issue's lines are the code, the claim it breaks is one of its `also` places (`claimAt(pr, index)`, never a line number by hand). Chapter 2's claim issues accept false claim only, so a bug comment on the right line is near ("isn't a problem of the kind Bug"): the chapter's point is to name the broken promise, and it keeps `levels.test.ts`'s rule that a later chapter doesn't accept bug everywhere. 2.4 also has a plain bug (bug only), so the category is a choice there, not a habit.
- **On the description only false claim fits, and only the claim itself**: no other kind of problem can be wrong with a sentence of Sous's (another kind is near), and its focus slack is 0 (`DESCRIPTION_SLACK`): a line is a whole statement, there is no context around a claim. (Built as: a comment over a claim and another line is wide, never broad; changed by the review below to broad, a false alarm.) The blankets cover the description too, of the kind bug, false claim or both on every stretch: none solves any of the 30 levels, and in a scenario any tiling blanket that solves costs false alarms.

## Update 2026-11-14: chapter 3, Tests that lie (built as 0.3.5)

The Tests panel and 5 scenarios with 10 practice tasks; docs/features/levels.md ("The review environment", "The Working with AI levels") and ui.md ("Working with AI play page") have the details. Decisions:

- **Grindstone's own tiny runner, Jest's words**: test files use `test`, `expect` and `vi` as globals (as Jest does, Vitest with `globals`), with eleven matchers, `.not`, `vi.fn` and `vi.spyOn`, and failures worded like Jest's. Why: what the levels need is small, and a familiar surface makes the lesson the test, not the tool. No `describe`, hooks, timers or module mocks: no level needs them. `toMatchInlineSnapshot` compares text without quotes (simpler than Vitest's serialiser, enough for a receipt). The runner counts **checks** (matchers that ran) per test and the panel shows them, so "passed without checking anything" is evidence you can see (3.1). Considered: bundling Vitest's `expect` (too big for a static page, and it brings its own module system).
- **"main" runs the pull request's tests on main's code** (not main's own tests): the question a reviewer asks of a test is "would it fail without this change?" A test that passes on main too can't be the one that checks the change (3.1, 3.2), one bent to the bug fails there and shows main's right value (3.3, 3.5), and a test of a new file can't run there (3.4, said as a test runner would). The panel says which code it ran on.
- **The runner runs in a worker inside the sealed frame**, behind a watchdog: a test that runs 2 s without reporting is "did not finish", the worker is stopped and a fresh one goes on with the next test (at most 5 times; a file that hangs while loading is left out). Why a worker: an endless loop in the frame's own thread would freeze Grindstone's tab (Debugging's known limit), and a worker can be stopped from outside. A classic worker, because a module worker can't start in the frame's opaque origin (checked in Chromium); it `import()`s the blob modules, which works in Chromium, Firefox and WebKit, as does the watchdog. Modules are linked in the frame as blob URLs in dependency order (a worker has no import map), so circles of imports can't run (said so). Results come over the bridge port like every other message, cut to `TEST_LIMITS` in the worker, the frame and the page (100 tests, 2000-character messages, 300-character values). The runner guards liveness and size, not integrity: tests are level data, never the player's.
- **Categories by file**: an issue in a test file accepts missing test (and false claim where the description says it is tested), never bug; an issue in the code accepts bug, never missing test. So the category is a choice of which file is wrong, and 3.3's "bug" on the bent test is near. `levels.test.ts` checks it for the chapter; the blankets now include missing-test comments (and bug with missing test), and none solves any of the 45 levels.
- **Chapter 3 as built** (Nik's plan, adjusted where noted): 3.1 "All tests pass", `expect(total)` with no matcher on a half-dozen deal that is right (the plan's code-is-wrong-too went to 3.2 to 3.5, so the opener teaches one thing: untested is not wrong, and still not mergeable; the `if` around the expect became its spot it); 3.2 "Mocked the thing under test", `vi.spyOn(pricing, 'applyDiscount').mockReturnValue(21.6)` then checking 21.6 (the function is a method of `pricing` so it can be spied on in the browser's modules), plus the discount starting at eleven; 3.3 "Fixed the failing test", `Math.floor` makes 3 × 2.80 cost 8.39 € and the test's name and number changed to match; 3.4 "100 % coverage", shares rounded one by one (6.50 € between three is 6.51 €) and tests that only split even totals; the coverage claim is true and a tempting spot (empty basket went to the practice task *A number, every time*); 3.5 "Snapshot updated", a receipt line printing one item's price and the inline snapshot updated to it. Every pull request's tests pass on its own code (pinned on Node, `TEST_OUTCOMES`). Practice: five spot it, five verdicts, three of them honest and approved (`toBe` on a string, a mock of the till, a snapshot changed by the line asked for), two not (a "flaky" test deleted, `toBeCloseTo(8.4, 0)`). Practice tasks still don't run (their test files are read, like chapter 1 and 2's code).
- **Known limits**: one test file's tests share its module state across tests (as in Jest within a file); a test that blocks forever in a native call stops only through the watchdog; the panel shows no console output of the tests (it never reaches the page).

## Review 2026-11-14 of chapter 3 (Opus, before deploy)

No security or high issues. Fixed:

## Update 2026-11-14: chapter 4, Invented APIs (built as 0.3.6)

5 scenarios and 10 practice tasks; docs/features/levels.md ("The review environment", "The Working with AI levels") and ui.md ("Working with AI play page") have the details. Decisions:

- **A category of its own, `invented-api` ("Invented API")**, not `bug`: "It calls a function, option, export, file or package that doesn't exist, or a deprecated one." (wording after the review: names exports and files, for 4.3 and Which file?) Why: with `bug` the category would grade nothing here (every chapter 4 issue is also "it does the wrong thing"), and the kind is what a reviewer tells the assistant: a bug is fixed in the logic, an invented API by looking the real one up. So every scenario's issue accepts `invented-api` (and `false-claim` with the claims it breaks), never `bug`, and a bug comment on it is near, as a bug comment on a bent test is in chapter 3; the made-up package also accepts `security` (installing a name an assistant made up is how slopsquatting gets in). The other way round is taught too: a real API used the wrong way is a bug, not an invented API (*Sorted, but where?*, `toSorted`'s copy thrown away, `bug` only), and *Which file?* (`./products` without its `.js`, a bundler's habit) accepts both, since it is as much a wrong path as a made-up module. Everywhere: `CATEGORIES` (the form lists it after false claim), its label and one-line meaning, CONTEXT.md; `levels.test.ts` fails any issue outside chapter 4 that accepts it (chapters 1 to 3 call real APIs), and the blankets now include invented-API comments (and bug with invented API): none solves any of the 60 levels. Considered: reusing `bug` (simpler, and the chapter's category would be decorative), a `deprecated` category of its own (one more choice for two levels; a deprecated call is one the assistant should not have made, the same fix: look it up).
- **No new panel**: Run the PR's Console is the evidence (the chapter's line in this ADR), the trace's link shows the line in the diff. 4.2 is the exception on purpose: an unknown option is ignored, so the Console stays empty and only the one price the change is about shows it, unchanged, as on main.

## Update 2026-11-14: chapter 7, Steer the assistant (built as 0.3.9)

5 scenarios and 5 practice tasks, and the cheat sheet; docs/features/levels.md ("The review environment": Steer levels, "The Working with AI levels") and ui.md ("Working with AI play page", "Working with AI cheat sheet") have the details. The track is complete: every chapter is live, the radar draws all seven axes solid. Nik delegated the design ("design it concretely and record the decisions"); the suggested shape was kept, with these decisions:

- **Rounds, not a free-form conversation**: a steer level's pull request has rounds. Round 1 is Sous's pull request; a request for changes before the last round is answered by **Sous's commit**, the next round; you review the whole pull request again (comments start empty, the review and Sous's answers move into the commit). Solved = the approval of a round with nothing open, with no comments. Scenarios take 3 rounds (a perfect review is done in round 2, one misleading kind can still be put right in round 3), practice tasks 2 (one comment, one commit, the approval: a misleading kind's wrong fix lands in the last round, and Reset is the way back). In the last round a request for changes is graded like any review and gets no commit. A request for changes without a comment is refused: Sous changes only what comments point at, and a commit that changes nothing would only use up a round. An approval too early is the wrong verdict and says how many problems are left, as any review says how many it found.
- **Scripted by the existing matching**: each round is graded by `checkReview` as a review is (lines, categories, the focus rule, false alarms), and `sousAnswers` turns that into Sous's commit: per open problem the first comment that finds it gets the **fix**; else the first near one (its lines, a kind that doesn't fit) gets the **wrong fix** scripted for that category (`misread`, by category class: each lists the categories it answers), or nothing for a kind none names (Sous: "I don't see that kind of problem there"); per fine place with an **overreach**, the first false alarm on it makes Sous "fix" the fine code into a new small problem. A comment too wide to point at a line and a false alarm elsewhere change nothing (Sous says so). Why: no free text is read, the reactions follow the chapters' own matching, and every comment gets an answer you can learn from. Considered: a reaction per comment text (no: Grindstone never reads it), a wrong fix for every category of every problem (a lot of writing for little: the kinds that mislead are few, and the rest leave the code as it is, which teaches the same).
- **Problems by text, rounds from commits**: commits move lines, so a problem names its place by text (`at: { path, text }`, or `removed` text of main's file), resolved per round; a reaction is text edits (or a file put back as main has it, for taking an extra out) and the problems it leaves in place of its own (`becomes`: none for a fix, a new problem for a wrong fix or an overreach). The session keeps only Sous's answers per commit; a round's files, open problems and fine places are worked out from them (`steerRound`, cached per level and commits). Fine places stay fine only while their text is there and no open problem covers them (a claim that holds until a commit breaks it). **Every path ends in a defined state**: `steer.test.ts` walks every round each level can reach (every fix, wrong fix and overreach in every combination) and checks that the edits apply, every open problem and fine place is where a comment can sit, every problem can happen, and from every round with one left, one right comment per problem fixes them all.
- **The commit is shown, not only described**: a timeline between the description and the diff, as on GitHub's conversation tab: your review per round, Sous's answer under each comment (confident whatever it did: the wrong fix has to be seen in the code), the commit's short id (a hash of the answers, the same every time) and **what it changed** (a read-only diff from the round before, the latest open). The diff you comment on is always the whole pull request as it is now; comments never sit on the commit's diff (one place to comment, the matching unchanged). Run the PR starts over in each round on that round's files, so a wrong fix can be seen running (7.1's saving still reads 2.3999999999999986 € after Sous escaped it).
- **Best run: fewest hints, then false alarms, then rounds**: `rounds` (commits Sous pushed in the attempt) joins the run like `falseAlarms`, as an optional count, so no new progress version (0.3.8 reads a 0.3.9 file and ignores it). Why a third count: a misleading kind is near, never a false alarm, so without it a wrong fix would cost nothing in the best run.
