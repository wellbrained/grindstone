# 0009 · Fourth track: Web fundamentals

Status: accepted, 2026-11-17. Grilled with Nik (Q1–Q9, all on Claude's recommendations: "yes, run it with your recommendations"). Each chapter gets an Opus review before it ships.

## Scope

- **Web fundamentals** (`/web`, registry id `web`): the rules the browser enforces that bite in production. Seven chapters:
  1. **Same-origin & CORS**: simple vs. preflighted requests, `Access-Control-Allow-Origin` / `-Credentials` / `-Headers` / `-Methods`, `*` with credentials.
  2. **Cookies & sessions**: `SameSite` (Lax, Strict, None), `Secure`, `HttpOnly`, `Domain`, `Path`; CSRF from another site.
  3. **Auth & tokens**: where a token lives (cookie vs. storage), XSS vs. CSRF, expiry and refresh, logout.
  4. **HTTP caching**: `max-age`, `no-cache`, `no-store`, `ETag` and 304, a CDN in between, a stale deploy.
  5. **The event loop**: tasks, microtasks, rendering; predicting order, not hunting async bugs.
  6. **Accessibility**: names, roles, state, focus order, keyboard, live regions.
  7. **Security headers & CSP**: `Content-Security-Policy`, `frame-ancestors`, the headers a shop sends.
- **Not here**: performance (Debugging chapter 6) and async bugs (Debugging chapter 4). The home card's text drops "performance".

## Mechanic: predict, then fix

- A **scenario** starts with a **prediction**: before the app runs, a card asks one question in one of three forms: **pick one** (what happens), **order the lines** (the console's order), **pick lines** (which requests carry the cookie). Answering runs the app and shows who was right, with one sentence on the rule. A wrong prediction never blocks: you go on to **fix** it (the app's code or the server's).
- A **practice task** is prediction only (one question, or a set of three).
- **Best run**: fewest wrong predictions, then fewest hints, then fewest reloads.

## The environment

- The Debugging sandbox (sealed frame, fake backend, Console, Code, Network) plus an **editable server**: `server.js` in Code next to the app's files, routes and the headers they send. The fake backend runs it.
- **A modelled browser** for CORS, cookies and caching (the frame has no network, so no real cross-origin request happens): our own model, following the Fetch and cookie specs where a level needs them, like the Git track's own git. Predictable, and the Network panel can name every block's reason. **Real browser** for CSP (a real policy) and accessibility (the real DOM).
- **Model scope**: CORS (simple vs. preflight, the four `Access-Control-*` headers, `*` with credentials); cookies (`SameSite`, `Secure`, `HttpOnly`, `Domain`, `Path`); caching (`max-age`, `no-cache`, `no-store`, `ETag`/304, a CDN). Left out: cross-origin redirects, Private Network Access, partitioned cookies (CHIPS), `Vary` edge cases. A "what the model simplifies" section in the feature doc, as for git; an edge case comes in only with a level that needs it, with a test against the spec text.
- **Panels**, each with the first chapter that needs it: request/response **headers** in Network and a blocked line that names its reason, and an **address bar** with the page's origin (chapter 1); **Application** (cookies per site with their flags, the cache with age and hits) and the **attacker site** `cheap-flour.example`, readable, not editable (chapter 2); **Accessibility** (the tree: role, name, state; what a screen reader reads) (chapter 6).
- **Accessibility checks** use **axe-core** (MPL-2.0), loaded only on accessibility levels (check frames and the panel). Goals check concrete facts ("the Buy button has a name", "focus reaches the dialog"), never "axe finds nothing", so silencing the checker solves nothing.

## Other decisions

- **World**: Corner Bakery grows up: an API on its own origin (`api.cornerbakery.shop`), customer logins, a CDN.
- **Release**: one chapter at a time, each Opus-reviewed and deployed (patch versions from 0.4.1); the cheat sheet at the end; 0.5.0 when Nik calls the track complete.
- **Radar**: the track gets its own radar and an axis on the home overview, as the registry gives every live track.

Decisions made while building:

- **An environment on Debugging's state, not a new one**: `web` registers `DebugState`/`DebugRecord` (with two optional additions, `predicted` and the record `predict`, which Debugging levels never use) and its own step (`{ predict }`), and `WebFields` = Debugging's + `prediction`. Debugging's engine is typed on `SandboxLevel`, the shape both share, and the Debugging play page takes `DebugLevel | WebLevel`. Why: the sandbox, the panels, the check runs and Reload are the same thing; a second state type would have meant casts through every panel or a second copy of a 1000-line composable. The Debugging levels and their tests are unchanged.
- **The prediction is a counted action, and the app waits for it**: answering records `{ kind: 'predict', question, right }` (a goal, "Predict …", ticks on any answer), a wrong answer adds 1 to `wrongPredictions` (`act`'s new count, like `falseAlarms`; no progress version 4: 0.4.0 reads a 0.4.1 file and drops it). No load exists before the last answer (the App says so, Reload is off); the last answer starts the app, uncounted. **Reset keeps the wrong count and asks again** (the answer was shown, as with false alarms); Play again starts at 0. **Best run**: fewest wrong predictions, then hints, then reloads, as planned.
- **The radar counts a solve with a wrong prediction half** (beyond the ADR's text, in its spirit): a prediction-only practice task is solved by any answer, so a wrong guess would otherwise fill the radar like knowing it. The best run is chosen by wrong predictions first, so it is the cleanest solve: a level counts 1 once that run had no wrong prediction and did without the last hint (it only goes up). Other tracks' credit is unchanged.
- **Predictions are checked against what the model does**: every option may carry a **fact** the run shows (a Network row, a server.js access line, a Console line, a preflight's asked header); the unit tests check the right options' facts hold and the wrong ones' don't against the table of every app's run (`expected.ts`, order questions in the answer's order), and the e2e checks the facts and the table against the real run in Chromium, Firefox and WebKit. A practice task's app runs too (to show who was right); its files are read-only.
- **The CORS model is JavaScript in a string, run in the frame**, like Debugging's backend: the decision has to be made inside the sealed frame while `fetch` is pending, and the page can't be part of every request without a round trip through the bridge for every check run. The same source is unit-tested on Node, each rule beside the Fetch spec's text, Chrome's order of looking (Chromium's `cors.cc`: `*` first, then a missing header, then several values, an invalid value, another origin; a preflight's Allow-Origin before its status) and Chrome's words for each refusal. Considered: a TypeScript model shipped into the frame with `Function.prototype.toString` (one source for the page and the frame, but a minifier or a helper could break it unseen in production only).
- **server.js runs in a worker inside the sealed frame**, never on Grindstone's page: an Express subset (routes, `:params`, middleware, `express.json()`, Express 5's own OPTIONS answer and 404 page, errors as 500, headers checked as Node does), the prelude on line 1 so server.js keeps its lines. A **watchdog** stops a request that runs 1 s (a loop, a route that never answers: `net::ERR_EMPTY_RESPONSE`, the worker replaced, at most 3 times a load); a throw at server.js's top level is a crash (every request then fails to connect, as when Node stops). Firefox and WebKit tell a frame nothing about a worker's syntax error, so the frame compiles server.js once more with `new Function` (never calling it) for the engine's message and line. Everything the worker posts is read field by field and capped; the worker gets server.js and limits, never the load's token, and the frame calls the Worker's own `postMessage`/`terminate`, taken before the app runs (the bridge test still finds one `postMessage(` to the page). Considered: running server.js in the frame's own thread (an endless route would freeze Grindstone's tab, Debugging's known limit), a Node-ish module system (`require('express')` is enough).
- **Cookies as SameSite=Lax does them, with one cookie**: Lena's session goes with a credentialed request from the same site only. So the credentials guard in 1.3 to 1.5 asks a page on **`promo.cornerbakery.shop`** (an old Christmas page: same site, another origin, her cookie goes along) whether it can read her basket; a page on another site can't get the cookie under Lax, so echoing any origin is caught where it really hurts. The texts say so, and that `SameSite=None` (chapter 2) would open it to every site.
- **The Network panel shows what the server sent for a refused request** (Chrome shows its headers but no body): the lesson of 1.1 and 1.5 is that the server answered and the browser kept it, so the response section says "what the server sent, kept from the page"; a request refused at its preflight says "Never sent". Preflights are rows of their own, tagged and linked to their request.
- **A Server panel** (not in the ADR's panel list): server.js's access lines, its console and its errors with links to their lines, like the terminal that runs `node server.js`. Why: "which requests reach the server" is a prediction (1.4) and the point of 1.5, and a learner editing server.js needs to see it crash. Capped at 300 lines a load, text only.
- **New probes** for goals that can't be faked by the page: `read` (the app read the body of a readable answer: a menu written into the page, or read from an opaque no-cors answer, reads none), `arrived` (the request reached server.js), `fetchFrom` (a page on another origin asks; nothing in the panels), and `meets`' `{ not }`. ## Review 2026-11-17 of chapter 1 (Opus, before deploy)

Isolation held. Fixed:

- **The credentials guard could be cheated** (serious): keeping `*`, having the route take anyone for Lena and dropping `credentials: 'include'` from the page solved 1.3 to 1.5, and so did echoing every origin but the promo page's. The basket goals now ask four times (`basketGuards`): the promo page with Lena's cookie and without it, a page on a subdomain no text names (`old.cornerbakery.shop`, so no server.js can single it out) and the shop's own page without her cookie; each must get anything but `read`. The real fixes and their alternatives pass, both cheats are non-fixes in `fixes.ts` (each fails on exactly the new guards), and the texts say the basket is only for her page and her cookie.
- **A header value outside Latin-1 hung the fetch** (a `new Response` that threw in the backend's timer): the runtime now refuses it as Node does (`Invalid character in header content`, a 500 and an error naming the line), the host refuses it too, and an answer the page's `Response` still can't carry fails that fetch with "Failed to fetch".
- **Chrome's words**: Chromium 158 has no "If an opaque response serves your needs…" tail any more, and the three Allow-Origin value errors end at "Have the server send the header with a valid value."; `foo:bar` is "not equal to the supplied origin" (anything with a scheme is a URL to Chrome). Header values are read without spaces and tabs at their ends, as the HTTP layer does.
- **`*` with Authorization**: the model keeps the spec's rule, Chromium lets `*` cover it without credentials; listed under "What the model simplifies", and 1.4's debrief no longer says `*` allows any header.
- **The runtime**: `res.statusCode = 99` is a RangeError where it is set (it was dropped and then reported as a hang); `express.json()` with options says in the Server panel that this subset takes none (it reads `application/json` only, so 1.2's debrief stays true, and says so); a rejected promise nobody catches is reported ("Unhandled rejection: …"); `req.rawBody` is gone.
- **The verdict's focus target** is a group named by the verdict and described by the rule.
- **Hardening, in #522's class**: the CORS model, the web backend and the server's host now take every built-in the decision path and the probes use before the app runs (string and pattern functions, the URL's and Request's getters, Headers' `forEach`, the Promise, the Worker's members and its events' getters, `addEventListener`), and walk lists by index. Three patches that let 1.1's page read the menu without the server's yes (`URL.prototype.origin`, `MessageEvent.prototype.data`, a Worker's `onmessage`/`addEventListener`) are e2e cases now and get nothing. The app still shares the frame's world for what it shows itself.
- **Bundle** after the review (against 0.4.0, as above): the shared levels chunk +117 KB (+31 KB gzipped), the play page's +16 KB (+4 KB), CSS +1 KB; all JavaScript and CSS +139 KB (+37 KB gzipped), the review's share about 13 KB (3 KB gzipped: the built-ins taken by hand, the guards). No new chunk.

## Update 2026-11-17: chapter 2, Cookies & sessions (built as 0.4.2)

Built on Claude's recommendations ("go with recommendations"): 5 scenarios, 5 practice tasks, a cookie model, other sites, the Application and Other site panels. docs/features/levels.md ("The cookie model" with "What the model simplifies", "Other sites", "The Web fundamentals levels") and docs/features/ui.md ("Web fundamentals play page") have the details. Decisions made while building:

- **A real cookie jar replaces chapter 1's one-cookie rule** (`shared/levels/web/cookies.ts`, `COOKIE_SOURCE`, JavaScript in a string run in the frame like the CORS model and tested on Node beside RFC 6265bis's text): Set-Cookie parsing (5.6, the cookie-date algorithm, the last attribute wins, over-long attribute values ignored), the storage model (5.7: host-only and Domain cookies, public suffixes and other sites refused, default-path, Secure only over https, `SameSite=None` only with Secure, SameSite cookies refused from a cross-site answer that is no top-level navigation, "Leave Secure Cookies Alone", replace by name, domain, host-only flag and path, deletion by an expiry in the past) and retrieval (5.8.3: domain, path, Secure, SameSite by the site context, the header's order). Chrome where it departs from the draft: no SameSite is Lax, **Lax+POST** (a cookie set without SameSite at most 2 minutes ago still goes with another site's top-level POST: Chromium's `kSameSiteDefaultChecksMethodRigorously` is still off by default), an expiry at most 400 days away, 4096 characters of name and value, 1024 of an attribute, 180 cookies per site (then the 30 used longest ago go) and 3300 in all. Chapter 1's `session` is now a seed: the cookie the browser kept since 09:12 (`Secure; HttpOnly`, no SameSite), stored through the same rules; chapter 1's levels behave as before (their tables and fixes pass unchanged in three browsers).
- **The scripted clock stands still**: every load runs at Tuesday 17 November 2026, 09:41 GMT (`WEB_CLOCK`), so expiries and Lax+POST are the same on every run; `res.cookie`'s Expires counts from it too.
- **Chrome's words, checked against DevTools' source** (`front_end/core/sdk/NetworkRequest.ts`, as shipped: the code marks without backticks, typographic apostrophes, most without a final full stop): every blocked Set-Cookie and every cookie a request did not carry, in the Network panel, and the refused ones in the Application panel. Where Chrome says nothing (a document.cookie write it ignores, a cookie from an answer to a request without credentials, a cookie sent only by Lax+POST) the texts are Grindstone's own and say what happened.
- **CORS and cookies together, as Fetch has it**: cookies go and are kept only with credentials (`include`, or `same-origin` to the page's own origin; a navigation always), are stored before the CORS check (a refused answer's cookie is kept), never go with a preflight, and Set-Cookie is never shown to the page (also on a same-origin answer). Requests now carry a Referer (strict-origin-when-cross-origin), and a no-referrer page's form POST says `Origin: null`.
- **Other sites are data, not frames** (`shared/levels/web/sites.ts`): a site is its page's actions (an image, a fetch, a form that submits itself, a link Lena clicks), run by the web backend through the same cookie and CORS models, each request in the Network panel tagged with the site and its kind (page, image). The page's HTML is written from those actions, so what the Other site panel shows is what runs. Considered: a second sealed frame per site (a real page, but it would need the jar and server.js across frames, and a navigation the frame can't make). A form or a link ends the page, as navigating away does.
- **A scene**: what happens in every load once the page is ready (Lena signs in, opens another site), in the app you see and the check runs alike, so the panels show who was right as soon as the prediction is answered, and the probes start from the same state. The Other site panel's **Visit as Lena** runs a site again in the load you see (over the page's port; only a site the level shows).
- **document.cookie through the model**: the bridge defines it on the frame's document before the app runs, not configurable; it reads without HttpOnly cookies and writes by the rules (an HttpOnly one, or one that would replace one, is refused). The browser's own getter still throws (Chromium, Firefox) or reads nothing (WebKit): the opaque origin has no cookies.
- **Probes**: `visit` (a site's page runs; the status of its last navigation), `navigate` (a link from a site, nothing in the panels; `credentials: 'omit'` is a browser without Lena's cookies), `carried` (requests to an address that carried a cookie), `leaked` (requests to another site with a text in them), `readable` and **`stolen`**: a script reads every cookie it can (any path of the page's origin) and an attacker replays them elsewhere as the Cookie header; blind to names and values, so renaming the cookie or taking the widget out never passes for HttpOnly. Every account level keeps two guards (`accountGuards`): nothing of Lena's for the shop's page without her cookie, and a stolen document.cookie is no session; the CSRF levels also run the attack from a site no text names (no Referer, `Origin: null`).

## Review 2026-11-17 of chapter 2 (Opus, before deploy)

Fixed:

- **Inherited setters and getters** (serious): an app could change what the check measured, and read an HttpOnly cookie, through setters it put on `Object.prototype` or `Array.prototype`: writes into new list indices and into fields an object didn't have yet ran them (a `url` setter sent 2.2's attacks elsewhere and solved it; setters on array indices caught the jar's session and marked it HttpOnly, solving 2.3; the same setters let the widget read the solved 2.3's session). The cookie model, the CORS model, the web backend and the server's host now define every list element with a descriptor that has no prototype (`defineProperty` reads `get` and `set` through the chain too), build every spec, context and result whole, read fields that may be left out as own only (a context's `script`, `topLevel`, `credentials`, `created`; an answer's `fail`; an other site's action) and never hand out a live cookie. The three cheats are e2e cases in Chromium, Firefox and WebKit, and a unit test runs the jar with setters and getters on both prototypes.
- **2.3 solved by throwing the session away**: the goal now also needs Lena's order to go through after the widget ran; the page deleting the cookie after sign-in is a non-fix.
- **The `stolen` replay was easy to recognise** (a Cookie header and nothing else): it now carries the page's own Origin and Referer, so only the cookie decides; "the session stored reversed and taken only with an Origin" is a non-fix.
- **Loose Origin and Referer checks passed 2.2**: a second unnamed guard site, `cornerbakery.shop.bread-offers.example`, sends a normal Referer and a real Origin that start like the shop's (2.2 and 2.5 visit it); `startsWith(SHOP)`, `includes('cornerbakery.shop')`, a name block that also refuses `null`, and a Referer checked with `startsWith(SHOP)` are non-fixes; the debrief says why.
- **Chromium where the model differed**: an overwrite keeps the creation time only for the same value (the header's order, a new Lax+POST window); an Expires year before 1601 is clamped to 1601 (the cookie goes); the last `Domain` wins, an empty one making the cookie host-only; `Max-Age=+5` is read. The docs no longer call the kept creation time browser behaviour.
- **Other site tabs**: `aria-controls`, and the content is a tab panel labelled by the chosen tab.
- **2.5's debrief**: Lax is the simple fix; `None` is safe only next to an exact Origin check or a token on every order (which the goals accept), no longer "None brings the forged orders back".

## Update 2026-11-18: chapter 3, Auth & tokens (built as 0.4.3)

Built on Claude's recommendations ("go with your recommendations"): 5 scenarios, 5 practice tasks, Web Storage, signed tokens, a clock that moves and a thief. docs/features/levels.md ("The storage model", "Tokens", "The thief", "What the model simplifies", "Chapter 3: Auth & tokens") and docs/features/ui.md ("Web fundamentals play page") have the details. Decisions made while building:

- **Web Storage through the model, as document.cookie** (`shared/levels/web/storage.ts`, `STORAGE_SOURCE`, tested on Node beside the HTML standard and WebIDL): the sealed frame has no storage of its own, so in a level whose `WebSpec` has `storage` the bridge defines `window.localStorage` and `window.sessionStorage` before the app runs (not configurable), each a Proxy over an area that behaves as WebIDL's legacy platform object with named properties (an item is a property unless the prototype chain has that name; any string set on it is an item; `Object.keys` and `JSON.stringify` see the items) with Storage.prototype as its prototype, whose members the model installs (the browser's own refuse a Proxy: "Illegal invocation"). Chromium's quota (10 MiB of UTF-16 per area) and its QuotaExceededError words. One tab, so sessionStorage is per origin of it. Each load starts from the level's items, as cookies do: a Reload is a new visit with what the browser kept, never what the last load wrote, so a check run is the same every time. Chapters 1 and 2 have no storage, as before.
- **Real HS256 tokens, not a pretend signature** (`shared/levels/web/tokens.ts`, `JWT_SOURCE`): `require('jsonwebtoken')` gives server.js the package's `sign`, `verify` and `decode`, its options, claims, errors and words, signing with a SHA-256 and HMAC of its own (checked against FIPS 180-4's and RFC 4231's vectors, Node's crypto and jwt.io's example token). Considered: a modelled hash (simpler, but then "decoding shown" and a token pasted into jwt.io would disagree, and the docs would have to claim less than a real JWT). Only HS256 and string secrets. `cookie-parser` and a scripted `crypto.randomUUID` (the same ids every run) came with the levels that read cookies and rotate refresh tokens.
- **The clock moves when a level says** (`{ later: minutes }`, in a scene or a probe): the jar, server.js (each request carries the moment it is answered at) and, in a level with `time`, the page's and server.js's `Date` tell the scripted time. It jumps, like a laptop that slept: timers don't fire early, which is also why a refresh on a 14-minute timer is a non-fix in 3.4. A scene's click in such a level waits for 50 ms without a request starting or ending, so the clock never moves between an answer and the page's next request (a race found while building: it made 3.3's `GET /orders` run at 10:01 now and then).
- **A thief instead of one probe per trick** (`copy`, `issued`, `replay` in the web backend): the goals ask whether anything an attacker could get works as Lena's session from outside the browser. What it has: what a script on the page could take now (`'script'`: document.cookie, the page's storage, the headers and query of every request the page's code sent, every answer it could read), a copy of the browser's cookies (a HAR file, an extension on the library's computer), what reached another site, or what a sign-in answered minutes ago. What it tries, name- and value-blind: the cookies, each header set, each string as a Bearer token, as a raw Cookie and under each cookie name the API uses, each query; a copy keeps the cookies an answer gives it (a rotated refresh token); `forge` makes tokens without the secret. So renaming a key, base64, sessionStorage, a token in memory, a widget taken out, the thief refused by its Origin all fail for the right reason, and the HttpOnly cookie passes because no script ever has it.
- **3.1 decides the suggested question: the HttpOnly cookie passes, keeping the token in memory does not.** A script on the page reads what the page's code hands to `fetch` (the `Authorization` header) or reads (the login's answer); signing Lena out on every reload would be a cost on top, not the reason. The cookie then needs SameSite (3.1 keeps chapter 2's unnamed CSRF sites as guards), and the debrief says neither is safe by itself: an XSS still acts as Lena while she is on the page.
- **XSS that acts, not only reads**: 3.2's review is an `<img onerror>` (`innerHTML` doesn't run `<script>`, every other element's handler runs) that changes Lena's email with her HttpOnly, SameSite=Lax cookie, so the chapter's core lesson is played both ways (3.1: a readable token is taken; 3.2: an HttpOnly cookie is ridden by a script on the page). The goal reads the DOM (no element inside a review, each review's text exactly as written) and the requests the page sent, and the check run posts two more reviews no text names (a capital `IMG`, spaces around `=`, a `<script>` among them), so any sanitising regex, deleting the review, refusing `<` or turning off the email route fails.
- **Facts the run shows**: `storage` (the page's origin keeps that key) and `replayed` (a thief's request the Server panel shows got that answer); the Server panel shows a scene's replays as lines of their own (who, what it sent, the answer, the token's claims), and the Application panel shows Local and Session storage per origin and decodes any token in a cookie or a value, with its times on the scripted clock.
- **Chapter 3 as built**, deviations from the suggested plan: 3.1 *The token the widget took* (above); 3.2 *A review that runs* (stored XSS that changes the email; `textContent`, `innerText` and escaping before `innerHTML` pass); 3.3 *The token that never expires* (a cookie with Max-Age 15 minutes holding a token without `exp`; the copy is Lena's HAR file; `expiresIn`, `exp` in the payload or `verify`'s `maxAge` pass; `jwt.decode`, `ignoreExpiration`, a day, a new secret don't); 3.4 *Signed out every 15 minutes* (refresh tokens under `Path=/auth`, rotated, no reuse detection: no level needs it); 3.5 *Signed out, still signed in* (both halves revoked; Sam, signed in before Lena signs out, keeps "sign everyone out" from passing; the session token carries a `jti`, since two sign-ins in the same scripted second would otherwise sign the same token). Practice: *What can a script on the page read?*, *Which of these run?*, *Which tokens does the server take?*, *Which requests carry the refresh token?*, *What still works after this sign-out?*. The readable CSRF token chapter 2 deferred is no level of its own: the thief shows the rule (a CSRF token any script can read, beside an HttpOnly session, is no session: `auth-backend.test.ts`), and 3.1's debrief names CSRF defence beside HttpOnly.

## Update 2026-11-19: chapter 4, HTTP caching (built as 0.4.4)

Built on Claude's recommendations ("go with recommendations"): 5 scenarios, 5 practice tasks, the browser's HTTP cache, a CDN, Express's ETag and other customers' browsers. docs/features/levels.md ("The cache model", "What the model simplifies", "The server", "The web backend", "Chapter 4: HTTP caching") and docs/features/ui.md ("Web fundamentals play page") have the details. Decisions made while building:

- **Two caches, each read by its own authority** (`shared/levels/web/cache.ts`, `CACHE_SOURCE`, JavaScript in a string run in the frame like the cookie model, tested on Node beside RFC 9111 and Chromium's code): Lena's browser is a private cache that reads an answer as Chrome's network stack does (`GetFreshnessLifetimes`: `Pragma: no-cache` and `Vary: *` count as no-cache, the 10 % heuristic only for 200/203/206, 300/301/308/410 fresh for ever; `GetCurrentAge`; a 304 that keeps the copy's own ETag and content headers), the CDN a shared cache as RFC 9111 has it (`s-maxage`, `private`, `Authorization`, `Vary`, `Age`, freshening, invalidation by an unsafe request). Why both: the chapter's lessons are about the difference (Pragma means something to Chrome and nothing to a CDN; `s-maxage` the other way round), and each side's behaviour is the one a learner meets.
- **Express's ETag is real**: server.js's `res.send` gives a body the `etag` package's weak ETag (its own SHA-1, checked against Node's crypto and the package's empty-body tag) and answers with 304 when the `fresh` package would, so `no-cache` works the way it does on a real Express server, a fixed ETag or `app.set('etag', false)` break what they break, and a `Cache-Control: no-cache` in the request (a reload) gets the whole answer. Only in a level with a cache: chapters 1 to 3's tables stay as they are (documented). A 204 or 304 now loses its Content-Type everywhere, as Express 5's `res.send` strips it.
- **The browser's cache sits in the page's fetch, as Fetch's HTTP-network-or-cache fetch**: the request's `cache` mode (read with the Request's own getter) and the headers Fetch adds for it, a page's own condition making a request no-store (so *The page asks itself* gets the bare 304), a page's own `Cache-Control`/`Pragma` read as Chromium does, the preflight first; a revalidation is posted with its `If-None-Match`, so the Network panel shows what really went; a copy used without a request is a row tagged **disk cache** with Chrome's "200 OK (from disk cache)". Only the page's own requests use it (no partitioning modelled; documented).
- **Other customers instead of a second frame** (`other`): another browser (its own empty cache, its own cookie, a page on `from` or an app with `from: null`) sends a request through the CDN; `like` sends exactly what the page's last request to that address sent, so a page that dodges the CDN with a query of its own (`/account?t=…`, `/menu?from=shop`) is caught by the same request from Sam's phone or Mia's page. The kitchen's price changes are `other` requests too, visible in the Server panel as access lines.
- **The CDN's log** is what the learner reads for 4.3 and 4.4 (who asked, HIT/MISS/REVALIDATED/PASS, the copy's age, why), in the Application panel's **Cache** beside both caches' copies (age, freshness, ETag, Cache-Control, who fetched them, uses). It ignores a request's own Cache-Control, as RFC 9111 allows and most CDNs do, so a page can't fix a shared cache.
- **Probes and facts**: `fromCache`, `notModified`, `reached` (requests from anyone that reached server.js past the CDN: the "the CDN still answers" guards) and `other`; facts `cdn` ('Sam GET https://…/account HIT'), `server` with `times` (a whole 200 again) and a row '… 200 (disk cache)'.
