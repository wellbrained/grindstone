## Skill radar

- **One radar per track**, its axes are the track's chapters. Shown on the track page next to the chapter list and in the debrief, where the axis that grew moves once (not under reduced motion). A chapter that is still coming is a dashed axis.
- **An axis** = the share of the chapter's levels you solved (scenarios and practice tasks). A solve that needed the last hint (the one that gives the answer away) counts half; a later solve without it counts full. Replays can raise an axis, nothing lowers it. No command weighting, no skill decay.
- **No overview radar** across tracks until three tracks are live (two axes are a line, not a shape). **No placement check.**
- **Look**: the logo's radar mark (0005), filled in the track's accent, each axis ending in its chapter's colour dot and name. Empty: the outline and "Solve levels to fill your radar". Screen readers get a list ("Basics: 4 of 11 solved").
- Needs from progress: whether a solve used the last hint (stored with the best run).

## Debugging track

- **Name and address**: "Debugging", `/debugging`, tagline "Find the bug before your customers do." Live on home and in the menu once chapter 1 ships.
- **Environment (sandbox)**: each level is a small, real app (HTML, CSS, plain JavaScript modules) that runs in a sealed iframe. Grindstone's own panels read what it does: **Console** (logs, warnings, errors; stack traces with clickable lines that open the file at that line; an input line that runs an expression inside the app; no filters or groups yet), **Code** (the existing editor), **Reload** (restarts the app after an edit), and with later chapters Network, Elements and more. A scripted **fake backend** answers the app's requests (a 500 or a slow answer on cue), so levels are repeatable and there is still no server. Not chosen: a fully simulated browser (you would never fix real code) and the browser's own DevTools (Grindstone can't check goals, no phones).
- **Solved** = the app behaves: goals check what you can observe ("no errors in the console", "the order button sends one request", "the total shows 12.50"). The debrief explains why.
- **Best run** = fewest hints, then fewest reloads before it worked. No clock (it would push guessing).
- **Practice tasks**: one or two per scenario, about 30 s, two kinds: **find** (click the line that throws) and **quick fix** (one line in a tiny app). Shown on a side branch as in 0006.
- **Language**: plain JavaScript in the early chapters, so traces are clear. Vue apps may come in a later chapter.
- **World**: Corner Bakery's ordering website; colleagues report the bugs in the story. No colleague events during play in chapter 1; they come with Incidents. Triggers stay generic for that.
- **Chapters**: 1 Reading errors (console, stack traces, `undefined is not a function`, typos, wrong imports), 2 Network (failed requests, status codes, payloads, CORS), 3 Elements & CSS, 4 State & async, 5 Breakpoints & stepping, 6 Performance, 7 Incidents (logs, the latest change, rollback). First release: chapter 1 with about five scenarios and their practice tasks; the rest show as coming.
- **Phones**: playable, panels stacked as tabs (App, Console, Code); designed for desktop first.
- **Cheat sheet**: none in the first release; a "reading errors" sheet may come with chapter 2.

## Update 2026-11-13: the engine split (built as 0.2.7, step 2 part 1)

The level engine is split from git, with no visible change for Git (docs/features/levels.md, "Environments"; docs/features/ui.md, "Play page").

- **One core, generic over an environment**: `shared/levels/` (types, engine, progress, track, radar) is track-agnostic and generic over a level's state, what its history records and its solution steps; it never imports an environment (a test checks the imports). Git is one environment in `shared/levels/git/` (its engine with the trainer commands, `CommandRecord`, `SolutionStep`, `levelCommands`, checks, levels) on the git model in `shared/git/`. Why generic functions over an environment object: the core stays plain functions over plain data, as before, and an environment calls them with its own actions (`act`, `undoLast`, `restart`, `takeHint`) and words the result itself; Debugging's input is clicks, saves and reloads, not a terminal.
- **Environments register by declaration merging** (`interface Environments` in the core, filled from each environment's folder), so `Level` is the union of the registered environments' levels (git's alone today, which keeps every existing type and test as it was) and `Level<'git'>` is one of them, told apart by `track`. Why not a plain `Level<unknown>`: every git level, test fixture and UI component would need casts, and goals would lose their state type.
- **Best run is a per-track measure** (`Track.bestRun`, an ordered list of run counters): Git `['commands', 'hints']` (unchanged), Debugging `['hints', 'reloads']`. A run gets an optional `reloads`; `commands` stays the count of counted actions in every track. **No progress version 4**: the field is optional and git runs never carry it, so 0.2.6 data and backups load and save back unchanged, and 0.2.6 still reads a newer file (it ignores `reloads`). `fewestHints` and the radar are untouched.
- **The play page dispatches by track**: `[level].vue` hands the level to its track's play component (`GitPlay`); shared are `usePlaySession` (session in memory, goals, recording with the track's measure, stats events, spark, debrief, Again), `PlayFrame` (the three-column frame), `LevelPanel` and `DebriefDialog` (the radar; each track's run in its `stats` slot, git's `GitRunStats`). Git's are `useGitPlay`, `GitWorkbench` and its panels.
- **Left for chapter 1**: Debugging's seven chapters stay out of the registry until its levels arrive (the tests pin a coming track to no chapters); its environment, play component and panels; a measure-aware best-run line on the track page's rows (it shows commands, right for Git only); Debugging's tagline and description from this ADR.

## Update 2026-11-13: Debugging chapter 1 (built as 0.2.8, step 2 part 2)

Built from the approved preview (`.impeccable/mocks/previews/debugging-preview.html`): the Debugging environment, its play page and chapter 1, Reading errors (5 scenarios, 8 practice tasks); chapters 2 to 7 show as coming. docs/features/levels.md ("The Debugging environment", "The Debugging levels") and docs/features/ui.md ("Debugging play page") have the details. Decisions made while building:

- **Sandbox**: `srcdoc` with `sandbox="allow-scripts"` only (an opaque origin: no storage, cookies, parent DOM, navigation, popups, forms). Module files run from **blob URLs made inside the frame** (blob URLs of the parent are another origin), through an **import map**. A blob URL has no folder, so `./cart.js` can't resolve against it: relative imports of the level's files are rewritten to the files' names on the same line (Chrome then says `'money.js'` where it would say `'./money.js'`). index.html keeps every line: the bridge, a `<base href="https://cornerbakery.shop/">` and a Content-Security-Policy go on its `<head>` line. `connect-src 'none'`: no request leaves the frame; the fake backend will answer inside it (the bridge wraps `fetch`; the hook is there, the backend is not). Verified in Chromium, Firefox and WebKit (Playwright) before building on it.
- **Goals are decided by a check run**, a second hidden sealed frame started by every Reload, with the level's **probes** (scripted clicks and reads). The probes never touch the app you see. Goals change only on a reload (find tasks: on a click), never on Save, so "Save, then Reload" is the loop, and the app shows "Reload to run them" while saved changes are not running. "No errors in the Console after a reload" includes errors the probes' own clicks cause (1.1's Add), so it fails on the starting files.
- **The run counted for Debugging** is reloads; saves and find-task clicks count as actions but cost nothing in the best run (fewest hints, then fewest reloads). Loading the page, Reset and Again restart the app without counting a reload.
- **Hints** show in the level panel (Debugging has no terminal to print them in): a scenario lists those revealed so far, a practice task shows its one hint in place as in git.
- **Find tasks**: the editor is read-only and a click on any line (or its number, or Enter) is an answer; in the Console every source link and frame is too. A wrong click shows why it isn't that one and marks the line; the right one solves it. Some answers accept two lines where the mistake sits between them (1.5's missing brace) or the frame and the line that registers the handler (the three-frame trace).
- **Track page rows**: a Debugging scenario is tagged with the error it teaches (`TypeError`), a practice task with its kind (`find`, `quick fix`), as in the preview. The best run reads "best: no hints, 1 reload"; Git's row is unchanged ("best 3 cmds").
- **Registry**: Debugging is listed second (Git, Debugging, then the coming tracks), so the home page shows the live tracks first. The nav gets a Debugging menu with Levels only (no cheat sheet in the first release).
- **Environments may add level fields** (`fields` in the registration; Debugging's `sandbox` and `teaches`), so `Level<'debugging'>` carries them without casts; git adds none and none of its types changed.
- **Texts quote Chrome's error wording** where the hints need it; Firefox and Safari word errors differently but point at the same file and line (checked). Safari gives no location for a missing named export (1.2's practice task), so there the Console shows the message without a source link.
- **Deviations from the preview's sample**: 1.1's bug is on `cart.js:17` (the preview showed 14) and the app logs "3 products" (the preview: 6). "Which file and line? Read a three-frame trace" asks for the frame that handled your click (the bottom one), so it teaches the order of frames rather than repeating the task before it. The preview's footer line "Its requests go to a scripted bakery backend" says "it can't reach Grindstone or your progress, and its requests are blocked" until chapter 2 brings the backend. Not "the network": the CSP blocks requests, but the frame can still navigate itself to an outside page (still sandboxed, still unable to reach Grindstone); review 2026-11-13.
- **Known limit**: the app runs in Grindstone's tab, so an endless loop in a learner's code freezes the page like a real tab; the check run gives up after 5 s and counts as not finished.

## Update 2026-11-13: Debugging chapter 2, Network (built as 0.2.9)

The first chapter of "Finishing the Debugging track": the fake backend, the Network panel and chapter 2 (5 scenarios, 7 practice tasks), built without a preview as planned. docs/features/levels.md ("The fake backend", "The Debugging levels") and docs/features/ui.md ("Network") have the details. Decisions made while building:

- **The backend runs inside the frame, from plain data**: `backendConfig` (TypeScript) checks a level's routes and hands the bridge plain JSON; `BACKEND_SOURCE` (plain JavaScript in a string, like the bridge) answers `fetch` from it. Why: the frame can only run what the bridge carries, and the unit tests run that very source on Node's `Request`/`Response` with fake timers, so routing, sequences, delays and the CORS and failure shapes are tested without a browser; the e2e checks every level in Chromium. The app gets real `Response` objects, so `response.json()` fails with the browser's own wording. The CSP stays `connect-src 'none'`: only `fetch` is answered, nothing else leaves the frame (checked in the e2e).
- **CORS is decided like the browser, not scripted as a failure**: a request to another origin is refused unless the route's answer allows the shop (`Access-Control-Allow-Origin`; for a preflighted request also `-Methods` / `-Headers`, the route's answer standing in for the preflight's); `mode: 'no-cors'` gets an opaque answer. Why: the lesson is that the server decides, so the level's data says what the server sends, and the wrong fixes a learner tries (`no-cors`, a header on the request) fail the real way. Only `{ fail: 'network' }` is scripted.
- **An unknown path answers the server's HTML 404 page** (Express's "Cannot GET …"), an unknown host fails to connect. So a wrong address produces the classic chain: a 404, then `Unexpected token '<' … is not valid JSON`.
- **The browser's own Console lines for failed requests** (`GET … 404 (Not Found)`, the CORS lines, `net::ERR_…`) are shown, link the line that sent the request, and count as errors (`kind: 'network'`), because Chrome shows them red. A level whose server keeps failing on purpose (2.2) therefore has no "no errors" goal instead of a goal that ignores them.
- **Every load gets a fresh backend**: a sequence of answers starts over with every Reload and in every check run, so what you see after a reload is what the goals saw.
- **Probes for requests and the timing they need**: `{ click, times }` (a double click), `{ requests }` (a count by address), `{ sent, json }` (the last body, or a value in it, so `3` and `"3"` differ). With a backend the check run waits after loading and after each click until every request is answered (at most 3 s), so slow answers (2.5: 900 ms) need no fixed waits. A probe goal now also needs a finished check run (no chapter 1 goal changes: they all had "no errors", which already did).
- **The Network panel** is a tab next to the Console (from lg a small Console/Network tab set above the two; on phones the tabs become App, Console, Network, Code), only in levels with a backend. A listbox (Up, Down, Home, End) and the selected request's details; side by side from 36rem of panel width, below that the details follow the list (first built as "details replace the list", dropped: selecting with the keyboard hid the list it was moving in). Bodies are text in a `<pre>`, JSON indented. **Sent from** (the browser's initiator column) opens the line that sent the request.
- **Find tasks stay line answers**: "click the request with the wrong status" became "click the line that sent the failing request", answered in the editor, by the Console's red line or by Sent from. Why: one answer mechanism (lines), and it teaches the initiator, the step from "which request" to "which code".
- **Track page tags** are the status or problem a scenario teaches (`404`, `500`, `payload`, `CORS`, `double POST`), spoken "Teaches: 404" (was "Teaches reading a TypeError").
- **`api.md`**: the Network apps that need it carry Ben's list of the server's paths as a file of the app (Markdown in the editor), the way a real project documents its API; 2.1, 2.3 and 2.4 are solved by comparing the request with it.
- **Deviations from Nik's level plan**: 2.1's wrong URL is a renamed endpoint (`/api/products`, now `/api/menu` in `api.md`) rather than a typo, so it teaches comparing with the API's paths and reading the status before the louder SyntaxError. 2.2's server answers a `500` and then a `201`, and the goals are "the customer reads the server's message" and "the basket stays" (the plan's "show an error message", plus not losing the basket). 2.3 sends `qty` where the API reads `quantity`; the server silently takes 1 and answers `201`, so nothing is red and only the payload shows it; the "string" variant became its practice task (a `400`). 2.4 keeps the title "Works on my machine" (Jonas tested with curl); its practice task adds the preflight wording. 2.5 as planned, with idempotency keys in the debrief. Seven practice tasks: two finds (the line that builds the address, the line that sent the failing request) and five quick fixes.
- **Known limits**: `XMLHttpRequest` is not answered (refused by the CSP like in chapter 1); the backend's answers are fixed per route and body pattern, it computes nothing from the request; response headers are not filtered for cross-origin reads (`Access-Control-Expose-Headers`).

## Update 2026-11-13: Debugging chapter 3, Elements & CSS (built as 0.2.10)

The second chapter of "Finishing the Debugging track": the Elements panel, layout probes and chapter 3 (5 scenarios, 10 practice tasks), built without a preview as planned. docs/features/levels.md ("The Elements panel", "The Debugging levels") and docs/features/ui.md ("Elements") have the details. Decisions made while building:

- **The browser says what matches, Grindstone works out the cascade**: Grindstone reads the level's own CSS (`css.ts`: rules with the line of every selector, declaration and media query, specificity, shorthands, inheritance) and hands the bridge the rules; the inspector in the frame answers only which rules and selectors match the element and its ancestors (`element.matches`, `matchMedia`, `CSS.supports`), which declarations the browser refuses, the box and a few computed values. Struck through, inherited and "not defined" are worked out on the page's side (`elementStyles`). Why: every rule and declaration links its real line (the stylesheet runs from a data URL, so the browser's CSSOM has no lines), the declarations show as written (`var(--brown)`, not the browser's serialisation), and the cascade logic is plain data, unit-tested; the e2e checks it against the real browser.
- **Snapshots, not a live tree**: after each load, on Refresh and on a pick (capped at 600 elements, 12 attributes, short texts); the selected element is found again by its place in the tree, also after a reload. Why: a live tree means a stream of mutations from a frame the learner's code controls; a snapshot is one capped message the page asks for (the page reads `dom` and `inspected` only when it asked, `hovered` and `picked` only in pick mode).
- **The outline and pick mode live in the frame**: the outline is drawn by the bridge in a closed shadow root on top of the page (`pointer-events: none`, so it never takes a click and the app's queries don't find its boxes); pick mode swallows the click and the presses around it, so the app never sees them. The overlay's colours are the browser's (margin orange, border yellow, padding green, content blue); the panel's box diagram uses the theme's warning, neutral, success and info tints.
- **Layout probes and widths**: `tap` (a click where a finger would: on whatever is on top at the element's centre; the old `click` keeps calling the element directly), `style`, `visible`, `hit`, `overflows`, `contrast`. The check run's frame stays a phone (390 × 700); a probe may ask for another `width` and gets a frame of its own (3.4 checks a phone and a laptop), the observations are put together (each error once). Why a frame per width instead of resizing one: a resize mid-run would let the earlier probes' state leak into the next width.
- **Guards share a goal** (`probesGoal`): the rule that every goal fails on the starting files (e2e) holds, so "the free coffee message still shows" or "the other prices keep their brown" go into the goal with what the fix changes, not into a goal of their own.
- **Find tasks stay line answers** (as in chapter 2): "pick the element that covers the button" became "pick it, then click the rule that puts it over everything" (the rule's selector or the lines that place it), answered by a rule's link in the Elements panel or in the editor. Every Elements find answer is a line the panel links (a test checks it).
- **The panel is a tab next to the Console, Elements first** (like the browser's), and open first in chapter 3, where the Console stays quiet. The App's header shows its width in pixels in these levels, since media queries hold by it; the app's frame is at most 416px wide at every window size, so 3.4's bug shows there.
- **Deviations from Nik's level plan**: 3.1 is the wrong variable (`var(--brown)`), not the inherited colour, which became its find task (the basket's text inherits a pale colour from `.basket`); its goals are a contrast of at least 4.5 : 1 and the brown background (so "black text on nothing" does not count). 3.2 uses a transparent message area over a fixed checkout bar (position, z-index, pointer-events; the goal also keeps the message and its ✕ working, so `pointer-events: none` needs its `auto` on the message). 3.3 is specificity; the selector typo became its quick fix ("a rule that is not listed doesn't match"). 3.4 is a media query turned the wrong way (`min-width` for a phone rule), checked at 390 and 1024 px. 3.5 as planned (`min-width: 0` on a flex item with a `nowrap` name). Ten practice tasks, two per scenario.
- **Review 2026-11-13** (Opus, before deploy): the App frame is capped at 26rem (416px) and centred at every window size (between 640 and 1023px it was full width, so 3.4 showed the laptop layout and 3.5 no overflow); throwing the stylesheet away no longer solves 3.2 or its banner task (`style` guards keep the bar and message area `fixed` and the banner `absolute`; the levels e2e reloads every chapter 3 fix level with `style.css` emptied and deleted); the CSS reader is linear, caps a sheet at 300,000 characters and nesting at 32, and never throws (timed tests); 3.2's debrief names fixes that work (a higher `z-index` for the bar, the area moved up; a shorter area at the bottom does not); declarations are links too, so every find answer can be given from the panel; `<!-- -->`, `disabled` and a `media` attribute on `<link>` / `<style>` are read like the browser; Stop in pick mode no longer leaves a snapshot request open. A Firefox run found a real editor bug: after a line was marked (opened from a link), clearing the mark with a transaction of its own mid-edit ended Firefox's composition, so text inserted that way was lost and an empty `style.css` got saved; the mark now goes in the edit's own transaction (Firefox passes `debugging-elements.spec.ts`). A synthetic paste event stays empty in Firefox with or without a mark: that one is a test-tool limit.
- **Known limits**: the browser's default styles are not listed (Computed shows the result); `@layer`, `@container` and nested rules are not read (a rule inside them does not show), pseudo-elements and states (`:hover`) only show when they match right now; `margin-inline` and its kind assume left-to-right; the style attribute's declarations are not checked for validity; the contrast probe ignores background images and `opacity`.

## Update 2026-11-13: Debugging chapter 4, State & async (built as 0.2.11)

The third chapter of "Finishing the Debugging track": chapter 4 (5 scenarios, 10 practice tasks), built without a preview as planned and, as planned, without a new panel: the Network panel's times show races, the Console shows promises and `Uncaught (in promise)`. docs/features/levels.md ("The Debugging levels", "The fake backend") and docs/features/ui.md ("Console") have the details. Decisions made while building:

- **Answers that depend on the request**: a route may take only requests whose query matches a pattern (`query`, like `body`), so 4.2's search answers `?q=cro` in 1.5 s and `?q=croissant` in 120 ms, and the race happens the same way on every run and in the goals' check run. Why not a backend that computes answers (a real search, a basket total): the backend stays plain data from the level, checked by `backendConfig`, and nothing a level ships runs on the page's side. That is also why 4.1 asks the server for each product's price, not for a basket total (every basket would need its own scripted answer).
- **Probes that let things overlap**: `{ type, value }` (typing; answers are not waited for), `{ wait: ms }` (a customer's pause, at most 2 s), `{ settle: true }` (until every answer is in), and `{ click, settle: false }` (a click that does not wait). A race is "type `cro`, pause 450 ms, type `croissant`, pause 600 ms, settle, read": the first pause is longer than a usual debounce, so a debounce alone (no fix for a race) does not pass, and the second lets a debounced request go out before the page is read.
- **`probesGoal(…, { clean: true })`**: 4.2's goal also needs nothing red, so cancelling the old request with an `AbortController` counts only when its `AbortError` is caught (the browser's Console turns red otherwise). Its own goal would pass on the starting files, which have no error.
- **The Console takes a top-level `await`** (as in the browser's DevTools) and previews a promise inside an object as `Promise` (Chrome's `price: Promise`): 4.1's hints have the player look at `cart.items[0]` and `await priceOf('croissant')`.
- **Fixes are proven, not only the solution**: `test/unit/levels/debugging/fixes.ts` lists other edits for chapter 4: the fixes the debriefs name (`.then` for `await`, a counter and a caught `AbortController` for the race, `let` or `for…of` for the closure, `structuredClone` or copy-on-write for the shared object, `async`/`await` for the chain) must pass, the tempting non-fixes must not (`await` without `async`, an uncaught abort, a debounce alone, `let i` alone, `Object.assign`, a spread of last week's order, only logging in the catch, no catch, a catch that always thanks). The e2e runs them in the browser. Review lessons from chapter 3, made general: **every** fix level of every chapter is reloaded with each file its solution edits emptied and deleted, and not every goal may pass (it holds for chapters 1 to 4; the chapter 3 `style.css` check is part of it now). Guards sit in the goals for that: 4.4 checks that the first loaf is sliced next to "the second stays whole", 4.5 that a turned-down order still says sorry next to the thank-you.
- **The check frame keeps one pixel in the viewport** (found running the new e2e in WebKit): WebKit all but stops the timers of a cross-origin frame that lies wholly outside the viewport (50 timers of 10 ms did not finish in 20 s at `left: -10000px`; at 1px inside, as fast as on screen), so in Safari 4.5's check run (two orders, each waiting for the server) never finished and the level could not be solved; shorter runs only scraped by. The hidden check frame now sits at `left: 1px - width`, transparent and `pointer-events: none` (`checkFrameStyle`, used by the play page and the e2e helper alike). Chromium and Firefox never throttled it, and WebKit does not throttle a frame that is only `display: none` (a phone's hidden App tab).

## Update 2026-11-13: Debugging chapter 5, Breakpoints & stepping (built as 0.2.12)

The fourth chapter of "Finishing the Debugging track": the Debugger, its recording and chapter 5 (5 scenarios, 10 practice tasks), built without a preview as planned. docs/features/levels.md ("The recording", "The Debugging levels") and docs/features/ui.md ("Debugger", "Code") have the details. Decisions made while building:

- **Recorded, not live, as planned; the run is the app you see**: Record reloads the app from the saved files with its code instrumented, you use it, Stop ends it (or a cap). Why not a scripted run of the probes: the lesson is to reproduce the bug yourself and then look; and the check runs (the goals) stay untouched, never instrumented. Record costs nothing in the best run (it is no reload and starts no check run); any other load (Reload, Reset, Again) ends the recording, because its lines belong to the code it ran; breakpoints stay while you are on the page.
- **Instrumentation inserts text only, with a real parser** (acorn, 8.18, MIT, no dependencies; already in the tree through ESLint, now a direct dependency). Why acorn: a hand-written JavaScript reader would not survive what learners type, and the larger parsers (Babel, TypeScript) are several times its size. It loads lazily, in its own chunk with the instrumentation and the condition reader, on the first Record or condition in a chapter 5 level. Nothing ever adds a line break, so traces, Console links and find answers keep their lines; function bodies get a `try`/`finally`, `await`/`yield` a pause/back call, braceless bodies braces, arrow expression bodies a block. What each statement can see is worked out from the syntax tree on the page's side (the frame only posts numbers and values), read through one small reader per variable (a reader that throws is the temporal dead zone: `<uninitialized>`). A file the parser can't read runs as written (a syntax error still fails like before), and so does one where the `try` would break valid code: in a block, a function's own function declarations are lexical, so a `var` of the same name or a function declared twice in one body would become a SyntaxError. A hashbang stays first (the module's first call goes at the start of line 2). Verified: every app of all five chapters runs instrumented with the same probe values, errors (and their lines) and requests as written, in Chromium, Firefox and WebKit (`e2e/debugging-instrumented.spec.ts`, `e2e/debugging-levels.spec.ts`), and the unit tests run the instrumented code on Node with the very recorder of the frame.
- **A step is the moment before a statement runs**, like a paused debugger's line; a loop's test is a step every round (5.2's off-by-one shows as the round that never comes); a breakpoint stops once each time its line runs (not again for a second statement of that line in the same call); on a `for` line it stops at the loop's test, every round, so round 0 already has `i` in the Scope (the `for` statement itself runs before the loop's variables exist). Step over follows the call (after an `await`, to where the function goes on once it is back, as Chrome does), step out leaves it, step back and "back to the previous breakpoint" go backwards: the reason to record.

## Update 2026-11-13: Debugging chapter 6, Performance (built as 0.2.13)

The fifth chapter of "Finishing the Debugging track": the Performance panel, its profile and chapter 6 (5 scenarios, 10 practice tasks), built without a preview as planned. docs/features/levels.md ("The profile", "The Debugging levels") and docs/features/ui.md ("Performance") have the details. Decisions made while building:

- **Counted, never timed (the cost model)**: wall-clock times differ per machine and run, so levels on them would be flaky. Work is one unit per statement of the app's code that ran, from chapter 5's instrumentation (no new parser, the same inserted text) with the recorder **counting** instead of reading values: self for the function running the statement, total once for every function on the recorder's call stack (so recursion, and callbacks a built-in calls, come out right), calls when a function starts. Why statements: the same run gives the same numbers in Chromium, Firefox and WebKit and on CI (checked: every chapter 6 app and the panel's e2e read identical numbers in all three), and they are what the code does, which is what the learner changes. A built-in counts as part of the statement that calls it, and the panel says so.
- **Renders from the page itself**: a MutationObserver, started once the page is parsed (before any module runs), counts **nodes** (elements and non-blank texts added or removed, one per attribute or text set). The counting recorder takes its records before each statement and when a call ends, waits or comes back, so a change belongs to the statement that ran since the last look; a render is a call whose own statements changed the page. Why not wrapping the DOM's methods: the observer sees every way of changing the page (innerHTML, textContent, append, classList), and the app's objects stay untouched.
- **The server's clock**: a request's times are the fake backend's scripted delays on a clock that moves only when an answer arrives (to its request's start plus its delay; new hooks `sent`, `arrived`, `aborted`). Requests sent together start together, awaits in turn make stairs. Why not real times: they jitter by milliseconds per run and browser, so a waterfall would be close but never exact. In a Performance level a check run's "quiet" also needs 50 ms without a request sent or answered, else the moment between an answer and a waterfall's next request looked like the end (other chapters' timing is unchanged).
- **Actions**: a profile is grouped by what the customer did (the page's load, each click, letter typed, change, Enter), from capturing listeners the bridge sets before the app's; the events of one press in one task are one action. An action counts what ran from it until the next one, answers arriving meanwhile included, and the panel says so. Why: "for one Add", "for one key" is the question the levels ask, and grouping by time needs no guess at what caused what. In the same action, a request sent the moment another's answer arrived is "sent once X answered" (a waterfall); one with the same method, address and body as an earlier one is "the same request again".
- **Goals stay behavioural**: new probes `keys` (letter by letter: keydown, input, keyup, never the focus), `press` (Enter in an input also commits it with `change`, as browsers do; no form is submitted in the sealed frame, which has no `allow-forms`), `changes` (nodes changed inside an element since the probe started), `work` (`load`: until the loaded page was quiet; `here`: since the probe started) and `waited` (server time); `probesGoal` takes bounds (`{ atMost }`, `{ atLeast }`). Every goal pairs what it costs with guards that the page still shows the right thing, so removing the feature, caching wrong data or hiding output fails; `fixes.ts` proves it in the browser: searching only from nine letters on, a debounce shorter than a key, checking a voucher only from eight letters on, not drawing the menu, nothing drawn on Add, a cache inside `formatPrice` (the loop around it stays), the first label kept for every product, the menu and specials together but the hours after, the hours left out, one answer kept for both tabs, only the menu kept. A counting check run uses the same instrumentation; the levels e2e checks that every chapter 6 app does the same counted as written (values but the work, errors, requests). ## Update 2026-11-14: the bridge's own port (built as 0.3.1)

CoreHub todo #522: the app's own code could read the load's token from the bridge's script in the page and post a check run's results and `done` to the page itself, which solved any Debugging level (confirmed on 6.4). It only fooled the player, but it emptied the goals. Decisions:

- **A port only the bridge holds, handed over before the app runs**: the bridge makes two `MessageChannel`s and its first and only message to the window (`window.parent.postMessage`) hands the page one port to read the load from and one to write to it, with the load's token. The page (`bridgeLink`) takes only the first such hello from that load's iframe with that token and two ports, then reads the load from that port alone; nothing posted to the window counts any more. The port to the page lives only in the bridge's closure and is only used through a `postMessage` bound before any of the app's code ran, so no later replacement of `MessagePort.prototype`, `Function.prototype` or anything else reaches it. Why the frame makes the channel, not the page (the suggested design): the page can't know when the frame's document exists, so a port posted into it would arrive after the app's code started, and would have to get past the app's own `message` listeners and `window.event`; the bridge's hello is first by construction, and a hello the app makes later (it found the token) comes second and is ignored. Two channels, not one: the bridge's handler for what the page sends runs while Console input is evaluated, and code running then can see that event's port through `window.event`; that port only leads back to the page's sending end, which reads nothing. The token stays only to tie the hello to its load; the bridge takes its own script text (the config with the token and the probes) off the page first.
- **Nothing of the level's files runs before the bridge**: the base, the policy and the bridge now go in front of everything of index.html but its doctype (on that line, so no line moves), no longer after the first `<head>` text: a script before `<head>`, or a `<head>` inside a comment or a script, used to come first (or bury the bridge, its policy with it, in a comment). The parser makes the `<head>` for them and lays the page's own `<html>` and `<head>` tags onto it, attributes kept; every level's checks, the Elements panel and the traces are unchanged (all levels e2e in Chromium, Firefox, WebKit).
- **The probes read with the browser's own functions**: the same app could still have made the bridge post what it wanted by replacing what the probes used (`Array.prototype.slice` on a probe's steps, a `textContent` getter, `instanceof ErrorEvent` to hide an uncaught error). The bridge now takes the DOM getters and methods, `getComputedStyle`, the event constructors, `dispatchEvent`, the timer and the regular expression and string functions it needs before the app runs, copies its config into data without prototypes, and runs the probes as callbacks on the kept timer (no promise, no array method); its listeners for errors, rejections, load and links are capturing listeners on the window set before any of the app's, read the events with the kept getters, and only the browser's own `load` starts the probes, once. The fake backend's record for the `requests` and `sent` probes and the page watch's record for `changes` are kept and read the same way; messages are made whole and never changed (a setter on `Object.prototype` never sees one).
- **Known limits** (docs/features/ui.md, "What it does not protect against"): the app shares the bridge's JavaScript world, so it can still change the real page (show the expected text, written into the code), behave differently while checked, or catch its own errors; the rest of the fake browser (routing, CORS, the recorder's tables, previews, the Elements panel) still uses the frame's built-ins where it runs after the app, which changes only what the app itself gets or what the visible panels show. A full lockdown of the frame's built-ins (SES-style) would break ordinary code the levels teach (assigning `error.name` in a subclass once `Error.prototype` is frozen), so it is not used.
- **Tested**: unit tests for the hello and the reader (`messages.test.ts`), the page's link (`sandbox-host.test.ts`: only the first hello of its frame with its token, never the window, early sends kept, closed for good), where the bridge goes and that it takes its text off first (`sandbox.test.ts`); `e2e/debugging-cheat.spec.ts` runs a cheat that tries all of the above on 1.1 and 6.4 (and through 6.4's play page) in Chromium, Firefox and WebKit, and the same spec run against 0.3.0's bridge forged both levels' results.
