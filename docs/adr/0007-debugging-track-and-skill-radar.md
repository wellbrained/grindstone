## Skill radar

- **One radar per track**, its axes are the track's chapters. Shown on the track page next to the chapter list and in the debrief, where the axis that grew moves once (not under reduced motion). A chapter that is still coming is a dashed axis.
- **An axis** = the share of the chapter's levels you solved (scenarios and practice tasks). A solve that needed the last hint (the one that gives the answer away) counts half; a later solve without it counts full. Replays can raise an axis, nothing lowers it. No command weighting, no skill decay.
- **No overview radar** across tracks until three tracks are live (two axes are a line, not a shape). **No placement check.**
- **Look**: the logo's radar mark (0005), filled in the track's accent, each axis ending in its chapter's colour dot and name. Empty: the outline and "Solve levels to fill your radar". Screen readers get a list ("Basics: 4 of 11 solved").
- Needs from progress: whether a solve used the last hint (stored with the best run).

## Debugging track

- **Name and address**: "Debugging", `/debugging`, tagline "Find the bug before your customers do." Live on home and in the menu once chapter 1 ships.
- **Environment (sandbox)**: each level is a small, real app (HTML, CSS, plain JavaScript modules) that runs in a sealed iframe. Grindstone's own panels read what it does: **Console** (logs, warnings, errors; stack traces with clickable lines that open the file at that line; an input line that runs an expression inside the app; no filters or groups yet), **Code** (the existing editor), **Reload** (restarts the app after an edit), and with later chapters Network, Elements and more. A scripted **fake backend** answers the app's requests (a 500 or a slow answer on cue), so levels are repeatable and there is still no server. Not chosen: a fully simulated browser (you would never fix real code) and the browser's own DevTools (Grindstone can't check goals, no phones).
- **Solved** = the app behaves: goals check what you can observe ("no errors in the console", "the order button sends one request", "the total shows 12.50"). The debrief explains why.
- **Best run** = fewest hints, then fewest reloads before it worked. No clock (it would push guessing).
- **Practice tasks**: one or two per scenario, about 30 s, two kinds: **find** (click the line that throws) and **quick fix** (one line in a tiny app). Shown on a side branch as in 0006.
- **Language**: plain JavaScript in the early chapters, so traces are clear. Vue apps may come in a later chapter.
- **World**: Corner Bakery's ordering website; colleagues report the bugs in the story. No colleague events during play in chapter 1; they come with Incidents. Triggers stay generic for that.
- **Chapters**: 1 Reading errors (console, stack traces, `undefined is not a function`, typos, wrong imports), 2 Network (failed requests, status codes, payloads, CORS), 3 Elements & CSS, 4 State & async, 5 Breakpoints & stepping, 6 Performance, 7 Incidents (logs, the latest change, rollback). First release: chapter 1 with about five scenarios and their practice tasks; the rest show as coming.
- **Phones**: playable, panels stacked as tabs (App, Console, Code); designed for desktop first.
- **Cheat sheet**: none in the first release; a "reading errors" sheet may come with chapter 2.

## Update 2026-11-13: the engine split (built as 0.2.7, step 2 part 1)

The level engine is split from git, with no visible change for Git (docs/features/levels.md, "Environments"; docs/features/ui.md, "Play page").

- **One core, generic over an environment**: `shared/levels/` (types, engine, progress, track, radar) is track-agnostic and generic over a level's state, what its history records and its solution steps; it never imports an environment (a test checks the imports). Git is one environment in `shared/levels/git/` (its engine with the trainer commands, `CommandRecord`, `SolutionStep`, `levelCommands`, checks, levels) on the git model in `shared/git/`. Why generic functions over an environment object: the core stays plain functions over plain data, as before, and an environment calls them with its own actions (`act`, `undoLast`, `restart`, `takeHint`) and words the result itself; Debugging's input is clicks, saves and reloads, not a terminal.
- **Environments register by declaration merging** (`interface Environments` in the core, filled from each environment's folder), so `Level` is the union of the registered environments' levels (git's alone today, which keeps every existing type and test as it was) and `Level<'git'>` is one of them, told apart by `track`. Why not a plain `Level<unknown>`: every git level, test fixture and UI component would need casts, and goals would lose their state type.
- **Best run is a per-track measure** (`Track.bestRun`, an ordered list of run counters): Git `['commands', 'hints']` (unchanged), Debugging `['hints', 'reloads']`. A run gets an optional `reloads`; `commands` stays the count of counted actions in every track. **No progress version 4**: the field is optional and git runs never carry it, so 0.2.6 data and backups load and save back unchanged, and 0.2.6 still reads a newer file (it ignores `reloads`). `fewestHints` and the radar are untouched.
- **The play page dispatches by track**: `[level].vue` hands the level to its track's play component (`GitPlay`); shared are `usePlaySession` (session in memory, goals, recording with the track's measure, stats events, spark, debrief, Again), `PlayFrame` (the three-column frame), `LevelPanel` and `DebriefDialog` (the radar; each track's run in its `stats` slot, git's `GitRunStats`). Git's are `useGitPlay`, `GitWorkbench` and its panels.
- **Left for chapter 1**: Debugging's seven chapters stay out of the registry until its levels arrive (the tests pin a coming track to no chapters); its environment, play component and panels; a measure-aware best-run line on the track page's rows (it shows commands, right for Git only); Debugging's tagline and description from this ADR.

## Update 2026-11-13: Debugging chapter 1 (built as 0.2.8, step 2 part 2)

Built from the approved preview (`.impeccable/mocks/previews/debugging-preview.html`): the Debugging environment, its play page and chapter 1, Reading errors (5 scenarios, 8 practice tasks); chapters 2 to 7 show as coming. docs/features/levels.md ("The Debugging environment", "The Debugging levels") and docs/features/ui.md ("Debugging play page") have the details. Decisions made while building:

- **Sandbox**: `srcdoc` with `sandbox="allow-scripts"` only (an opaque origin: no storage, cookies, parent DOM, navigation, popups, forms). Module files run from **blob URLs made inside the frame** (blob URLs of the parent are another origin), through an **import map**. A blob URL has no folder, so `./cart.js` can't resolve against it: relative imports of the level's files are rewritten to the files' names on the same line (Chrome then says `'money.js'` where it would say `'./money.js'`). index.html keeps every line: the bridge, a `<base href="https://cornerbakery.shop/">` and a Content-Security-Policy go on its `<head>` line. `connect-src 'none'`: no request leaves the frame; the fake backend will answer inside it (the bridge wraps `fetch`; the hook is there, the backend is not). Verified in Chromium, Firefox and WebKit (Playwright) before building on it.
- **Goals are decided by a check run**, a second hidden sealed frame started by every Reload, with the level's **probes** (scripted clicks and reads). The probes never touch the app you see. Goals change only on a reload (find tasks: on a click), never on Save, so "Save, then Reload" is the loop, and the app shows "Reload to run them" while saved changes are not running. "No errors in the Console after a reload" includes errors the probes' own clicks cause (1.1's Add), so it fails on the starting files.
- **The run counted for Debugging** is reloads; saves and find-task clicks count as actions but cost nothing in the best run (fewest hints, then fewest reloads). Loading the page, Reset and Again restart the app without counting a reload.
- **Hints** show in the level panel (Debugging has no terminal to print them in): a scenario lists those revealed so far, a practice task shows its one hint in place as in git.
- **Find tasks**: the editor is read-only and a click on any line (or its number, or Enter) is an answer; in the Console every source link and frame is too. A wrong click shows why it isn't that one and marks the line; the right one solves it. Some answers accept two lines where the mistake sits between them (1.5's missing brace) or the frame and the line that registers the handler (the three-frame trace).
- **Track page rows**: a Debugging scenario is tagged with the error it teaches (`TypeError`), a practice task with its kind (`find`, `quick fix`), as in the preview. The best run reads "best: no hints, 1 reload"; Git's row is unchanged ("best 3 cmds").
- **Registry**: Debugging is listed second (Git, Debugging, then the coming tracks), so the home page shows the live tracks first. The nav gets a Debugging menu with Levels only (no cheat sheet in the first release).
- **Environments may add level fields** (`fields` in the registration; Debugging's `sandbox` and `teaches`), so `Level<'debugging'>` carries them without casts; git adds none and none of its types changed.
- **Texts quote Chrome's error wording** where the hints need it; Firefox and Safari word errors differently but point at the same file and line (checked). Safari gives no location for a missing named export (1.2's practice task), so there the Console shows the message without a source link.
- **Deviations from the preview's sample**: 1.1's bug is on `cart.js:17` (the preview showed 14) and the app logs "3 products" (the preview: 6). "Which file and line? Read a three-frame trace" asks for the frame that handled your click (the bottom one), so it teaches the order of frames rather than repeating the task before it. The preview's footer line "Its requests go to a scripted bakery backend" says "it can't reach Grindstone or your progress, and its requests are blocked" until chapter 2 brings the backend. Not "the network": the CSP blocks requests, but the frame can still navigate itself to an outside page (still sandboxed, still unable to reach Grindstone); review 2026-11-13.
- **Known limit**: the app runs in Grindstone's tab, so an endless loop in a learner's code freezes the page like a real tab; the check run gives up after 5 s and counts as not finished.

## Finishing the Debugging track (2026-11-13)

Nik delegated chapters 2–7 to Claude's plan ("go with your recommendations"), without previews, as with Git v1 (0006).

- **Order**: 2 Network → 3 Elements & CSS → 4 State & async → 5 Breakpoints & stepping → 6 Performance → 7 Incidents. One chapter at a time, each with an Opus review and deployed as a patch. About five scenarios per chapter plus find / quick-fix practice tasks, all in Corner Bakery's shop, written to the same rules as chapter 1.
- **Panels arrive with the chapter that needs them**, as tabs next to the Console, and a level shows only the panels it uses:
  - **Network** (ch 2): the scripted fake backend answers the app's `fetch` inside the frame (data, status codes, delays, CORS refusals as the browser would report them); the panel lists each request (method, URL, status, time) with its request and response body.
  - **Elements** (ch 3): the app's DOM tree; selecting an element shows its box and the styles that apply, with where each comes from. Read-only: fixes happen in the code.
  - **State & async** (ch 4) needs no new panel: Network delays and the Console are enough to show races, stale values and missing `await`.
  - **Breakpoints** (ch 5): no live pausing (a sandboxed frame can't be paused safely). The code is instrumented and one run is **recorded**; you set breakpoints on lines and step forward and back through the recording, seeing each variable's value at that moment. Recorded, not live, and the UI says so.
  - **Performance** (ch 6): from the same instrumentation, how often functions ran and renders happened, and the requests over time.
  - **Incidents** (ch 7): a **Logs** panel with the backend's log lines and a **Deploys** list (the last changes with their diffs and a Roll back); colleague events during play come back here.
- **Cheat sheet**: one Debugging sheet after chapter 7, covering every panel and the error types from the levels.

## Update 2026-11-13: Debugging chapter 2, Network (built as 0.2.9)

The first chapter of "Finishing the Debugging track": the fake backend, the Network panel and chapter 2 (5 scenarios, 7 practice tasks), built without a preview as planned. docs/features/levels.md ("The fake backend", "The Debugging levels") and docs/features/ui.md ("Network") have the details. Decisions made while building:

- **The backend runs inside the frame, from plain data**: `backendConfig` (TypeScript) checks a level's routes and hands the bridge plain JSON; `BACKEND_SOURCE` (plain JavaScript in a string, like the bridge) answers `fetch` from it. Why: the frame can only run what the bridge carries, and the unit tests run that very source on Node's `Request`/`Response` with fake timers, so routing, sequences, delays and the CORS and failure shapes are tested without a browser; the e2e checks every level in Chromium. The app gets real `Response` objects, so `response.json()` fails with the browser's own wording. The CSP stays `connect-src 'none'`: only `fetch` is answered, nothing else leaves the frame (checked in the e2e).
- **CORS is decided like the browser, not scripted as a failure**: a request to another origin is refused unless the route's answer allows the shop (`Access-Control-Allow-Origin`; for a preflighted request also `-Methods` / `-Headers`, the route's answer standing in for the preflight's); `mode: 'no-cors'` gets an opaque answer. Why: the lesson is that the server decides, so the level's data says what the server sends, and the wrong fixes a learner tries (`no-cors`, a header on the request) fail the real way. Only `{ fail: 'network' }` is scripted.
- **An unknown path answers the server's HTML 404 page** (Express's "Cannot GET …"), an unknown host fails to connect. So a wrong address produces the classic chain: a 404, then `Unexpected token '<' … is not valid JSON`.
- **The browser's own Console lines for failed requests** (`GET … 404 (Not Found)`, the CORS lines, `net::ERR_…`) are shown, link the line that sent the request, and count as errors (`kind: 'network'`), because Chrome shows them red. A level whose server keeps failing on purpose (2.2) therefore has no "no errors" goal instead of a goal that ignores them.
- **Every load gets a fresh backend**: a sequence of answers starts over with every Reload and in every check run, so what you see after a reload is what the goals saw.
- **Probes for requests and the timing they need**: `{ click, times }` (a double click), `{ requests }` (a count by address), `{ sent, json }` (the last body, or a value in it, so `3` and `"3"` differ). With a backend the check run waits after loading and after each click until every request is answered (at most 3 s), so slow answers (2.5: 900 ms) need no fixed waits. A probe goal now also needs a finished check run (no chapter 1 goal changes: they all had "no errors", which already did).
- **The Network panel** is a tab next to the Console (from lg a small Console/Network tab set above the two; on phones the tabs become App, Console, Network, Code), only in levels with a backend. A listbox (Up, Down, Home, End) and the selected request's details; side by side from 36rem of panel width, below that the details follow the list (first built as "details replace the list", dropped: selecting with the keyboard hid the list it was moving in). Bodies are text in a `<pre>`, JSON indented. **Sent from** (the browser's initiator column) opens the line that sent the request.
- **Find tasks stay line answers**: "click the request with the wrong status" became "click the line that sent the failing request", answered in the editor, by the Console's red line or by Sent from. Why: one answer mechanism (lines), and it teaches the initiator, the step from "which request" to "which code".
- **Track page tags** are the status or problem a scenario teaches (`404`, `500`, `payload`, `CORS`, `double POST`), spoken "Teaches: 404" (was "Teaches reading a TypeError").
- **`api.md`**: the Network apps that need it carry Ben's list of the server's paths as a file of the app (Markdown in the editor), the way a real project documents its API; 2.1, 2.3 and 2.4 are solved by comparing the request with it.
- **Deviations from Nik's level plan**: 2.1's wrong URL is a renamed endpoint (`/api/products`, now `/api/menu` in `api.md`) rather than a typo, so it teaches comparing with the API's paths and reading the status before the louder SyntaxError. 2.2's server answers a `500` and then a `201`, and the goals are "the customer reads the server's message" and "the basket stays" (the plan's "show an error message", plus not losing the basket). 2.3 sends `qty` where the API reads `quantity`; the server silently takes 1 and answers `201`, so nothing is red and only the payload shows it; the "string" variant became its practice task (a `400`). 2.4 keeps the title "Works on my machine" (Jonas tested with curl); its practice task adds the preflight wording. 2.5 as planned, with idempotency keys in the debrief. Seven practice tasks: two finds (the line that builds the address, the line that sent the failing request) and five quick fixes.
- **Known limits**: `XMLHttpRequest` is not answered (refused by the CSP like in chapter 1); the backend's answers are fixed per route and body pattern, it computes nothing from the request; response headers are not filtered for cross-origin reads (`Access-Control-Expose-Headers`).
